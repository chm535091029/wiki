- **调研纠正了原文档两处不准确认知**（重要，后续引用勿再犯）：
  1. 默认 500 响应**不是"无响应体"**，而是 `PlainTextResponse("Internal Server Error", 500)`；只有 `response_started` 为真（流式已发出首块）时该响应才被丢弃。re-raise 是设计意图，让服务器与 TestClient 能看到异常对象。
  2. `@app.exception_handler` 不是统一挂在一层：注册 `500`/`Exception` 落到最外层 `ServerErrorMiddleware`，注册具体异常类落到最内层 `ExceptionMiddleware`。因此 **ExceptionMiddleware 捕获不到用户中间件自身抛出的异常**（传播方向由内向外）。

- 沉淀的高价值结论：
  - WSGI 的根本局限不是"同步"，而是"单条请求路径 + 无 disconnect 通知"，这决定了 SSE/WebSocket/lifespan 全部不可能
  - ASGI `scope["state"]` 由服务器浅拷贝进每个请求，目的是避免依赖 contextvar 或全局可变状态
  - 流式生成器不含 `await` 则无法被取消，客户端断开后继续烧 token
  - `X-Accel-Buffering: no` 多层反代需逐级透传（第一层会消费掉）
  - sklearn 无关；`model_json_schema()` 喂 LLM 用 validation 模式，描述响应契约用 serialization 模式
  - MCP server 通常是独立 stdio 进程或独立服务，不是 Web 框架应用；FastAPI 只在自己实现 Streamable HTTP 传输时才介入
