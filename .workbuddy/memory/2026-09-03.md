## 后端服务基础章节展开（10 篇）

- 用户要求：对大纲第 3 章「后端服务基础」的 10 个知识点逐条联网调研，每个知识点单独成文。
- 产出目录：`knowledge/04-engineering/backend-fundamentals/`，含 README 索引 + 10 篇文档
  - README.md：章节索引表、三条贯穿主线、易被忽略的十个默认值速查表
  - 01-framework-responsibilities / 02-request-lifecycle / 03-middleware / 04-dependency-injection / 05-sync-vs-async / 06-concurrency-models / 07-connection-pool / 08-stateless-service / 09-configuration-management / 10-graceful-shutdown
- 文档统一结构：概念定义 → 工作机理 → 关键对比或参数表 → 常见陷阱与排查 → AI Agent 场景注意点 → 自测问题 → 参考来源（实际抓取的真实 URL，未找到可靠来源的条目在正文显式标注"不作断言"）
- 调研方式：3 个并行子代理分头抓取官方文档（FastAPI / Django / Express / Gin / Spring / Python asyncio / SQLAlchemy / PgBouncer / PostgreSQL / K8s / GKE / AWS / 十二要素 / OTel / HikariCP / httpx / aiohttp / Redis），再由主代理统一成文
- 沉淀的高价值结论（后续可直接复用）：
  - 路由是有序链表的线性匹配，不是最精确匹配，`/users/me` 必须声明在 `/users/{id}` 之前
  - 中间件不作为唯一访问控制边界（CVE-2025-29927 为实证）
  - 三条容量公式：容量硬约束（Σ池上限×worker×副本 ≤ max_connections − reserved）、性能软约束（core×2+spindle）、死锁下界（Tn×(Cm−1)+1）
  - PgBouncer transaction 模式下协议级 prepare 需 `max_prepared_statements` 非 0，否则间歇性失败
  - GIL 两条例外决定了多线程对 I/O 有效、对纯 Python CPU 无效；`workers=2×CPU+1` 公式出自同步 worker 语境
  - 多副本下内存限流实际阈值 = 设定值 × 副本数，随 HPA 漂移
  - K8s `terminationGracePeriodSeconds` 默认 30s 远小于 Agent 任务耗时，根本解法是任务外置
  - FastAPI 的 `Depends` 是请求内单例（use_cache 默认 True），非 Spring 容器级 singleton；长生命周期资源须放 `lifespan`
