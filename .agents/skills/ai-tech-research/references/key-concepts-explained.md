# 关键概念速览（附简单例子）

本文件用"生活化类比 + 最小可运行示例"解释 AI 技术调研中反复出现的几类抽象概念，配合 `SKILL.md` 的工作流使用。调研一项新技术前，可先扫一遍建立直觉，再去看论文正文就不会一头雾水。

---

## 一、AI 技术类概念（以推测解码家族为例）

### 1. 推测解码 / 投机解码（Speculative Decoding）

**一句话**：小模型先"起草"，大模型一次性"盖章验证"，能并行接受多个 token，从而在不损失质量的前提下加速。

**生活例子**：让资深翻译（大模型）逐字翻太慢。改成：让实习生（小模型）先快速起草整句，资深翻译一口气核对整句——对的整句收下，错的地方从那个词起重写。不用逐字等资深翻译，整体更快。

**最小示例**：
```
草稿序列:  [A, B, C, D]        ← 小模型一次生成
大模型验证: A✓  B✓  C✗(应为 X)   D 不再看
采纳结果:  [A, B, X]           ← 从 X 开始下一轮
```
> 关键指标：**平均接受长度**（每轮平均收下几个草稿 token）。越长越省时。

### 2. 半自回归生成（Semi-Autoregressive）

**一句话**：把序列切成 block，block 内多个 token 并行生成，block 之间顺序生成。

**生活例子**：写文章不是逐字写（纯自回归），也不是整篇同时想（纯并行）。而是先一口气想好"一段的 4 个要点"（block 内并行），再写下一段（顺序）。DSpark 的"并行主干"就是同一个 block 内并行出多个 token。

**最小示例**：
```
自回归:     词1 → 词2 → 词3 → 词4          (串行, 慢)
半自回归:   [词1 词2 词3 词4] → [词5 词6 词7 词8]   (block内并行, block间串行)
```

### 3. 置信度调度验证（Confidence-Aware Verification）+ 顺序温度缩放 STS

**一句话**：用一个"置信度头"估计每个草稿 token 被接受的概率，按校准后的温度决定本次草稿多长，使"期望接受数"最大。

**生活例子**：你让实习生一次起草几句话？他擅长这题（高置信）→ 一次多写几句再核对；他没把握（低置信）→ 少写几句。STS 就是那把"按把握大小决定一次写几句"的刻度尺，避免要么草稿太长浪费、要么太短没省到。

### 4. 硬件感知前缀调度（Hardware-Aware Prefix Scheduling）

**一句话**：把多个请求的共享前缀在 GPU 上合并计算，减少重复算力。

**生活例子**：三个人都问"基于这份 100 页手册，回答……"。与其各读一遍手册，不如先把手册读一次、结果三个人共用，再各自答自己的问题。省下的就是那重复的"读手册"算力。

## 二、调研工作流类概念

### 5. 信息源交叉验证（Cross-Validation）

**生活例子**：写新闻不能只听发布会（官方）。厂商说"快 3 倍"，但三家独立测评都只有"快 1.5 倍"→ 文档写："厂商宣称 3×，独立实测约 1.5×"，并标注口径，不盲目照搬。

**规则**：性能数字至少两源一致；冲突以官方为准；标注"名义值 vs 实测值"。

### 6. 仓库格式动态对齐（Dynamic Format Alignment）

**生活例子**：入职新团队，先翻几份老文档，看大家怎么写标题、插表格、用不用双链，然后照着写——而不是硬套自己上家的模板。

### 7. 双链反向链接（Backlinks）

**生活例子**：写了"DSpark"，文中说"它跑在 V4 上"。就回 V4 文档补一句"V4 上部署了 DSpark"。两篇互相指向，像维基百科的"参见"，形成知识网。

### 8. 数据口径陷阱（Nominal vs Actual）

**生活例子**：论文说"严格 SLA 下吞吐 +661%"。但同一档位下旧方案已接近崩溃（基线极低），这个"+"是相对一个很差的基线算的，并非真实日常收益。文档里必须写明口径，否则读者会误以为普遍快 6 倍。
