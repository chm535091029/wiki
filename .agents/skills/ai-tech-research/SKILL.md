# AI 技术调研

## Overview

将"搜索官方资料 → 社区解读交叉验证 → 对齐仓库格式 → 生成结构化技术文档 → 维护双链"这一端到端流程固化下来。适用于任何需要把一项 AI 技术（新模型、新框架、新论文、新方法）整理成正式、可读、与知识库风格统一的技术文档的场景。

## 关键概念速览（含简单例子）

调研 AI 技术时常遇到抽象理论，直接读论文容易劝退。下列概念在 `references/key-concepts-explained.md` 中有"生活化类比 + 最小可运行示例"，生成文档前可先扫一遍建立直觉：

- **推测解码**：小模型起草、大模型一次性验证，并行接受多 token（类比：实习生起草、资深翻译整段核对）。
- **半自回归**：block 内并行、block 间串行（类比：先想好一段的若干要点，再写下一段）。
- **置信度调度 / STS**：按把握大小动态决定草稿长度（类比：把握大就一次多写几句再核对）。
- **硬件感知前缀调度**：合并多请求的共享前缀算力（类比：三人共用一份手册，各答各的问题）。
- **信息源交叉验证**：官方宣称与社区实测冲突时以官方为准、标注口径（类比：不只听发布会，也看独立测评）。
- **格式动态对齐 / 双链反向链接**：照仓库现有风格写、补互链（类比：入职先学团队文档习惯、文间互相"参见"）。

## 工作流

### 阶段 1：信息源搜集（官方优先，社区交叉验证）

1. 优先定位官方一手资料：
   - 论文：在 arXiv 搜索 `<技术名>` 或 `<技术名> arxiv`，读取摘要页（`/abs/<id>`）与 HTML 正文页（`/html/<id>v1`）以获取公式、表格与架构细节。
   - 代码/仓库：搜索官方 GitHub 仓库（如 `deepseek-ai/<repo>`），读取 README、训练/评估流程、开源 checkpoint、使用注意事项。
   - 官方公告/博客：厂商技术博客、模型卡、发布说明。
2. 补充社区解读以辅助理解与交叉验证：知乎、CSDN、Medium、技术社区中的深度解析文章。
3. 关键数据（性能数字、接受长度、吞吐提升、架构参数）必须在至少两个来源间核对；若来源冲突，以官方论文/仓库为准，并在文档中注明口径。

### 阶段 2：数据核实与提取

1. 从论文正文中提取：核心方法公式、模块设计、训练设置（数据集、块长、层数）、基准表格（如 Table 1 的逐领域数值）、生产/部署实测数据。
2. 对"名义提升 vs 实际提升""严格 SLA 下的退化"等易误导口径，按论文原意标注，避免误读。
3. 记录引用来源（论文编号、仓库、博客链接），便于文档中标注与读者溯源。

### 阶段 3：仓库格式对齐（动态探测，不硬编码）

1. 先定位仓库中同类技术文档的目录（如 `knowledge/03-research/Foundation/`）。
2. 抽样阅读 2–3 篇现有文档，识别其约定：
   - frontmatter 字段（必须有 `aliases`、`tags`、`related` 三项；`related` 用路径式 `"./xxx.md"` 还是 Wiki 式 `"[[xxx]]"`，按仓库习惯）。
   - 章节分隔方式（`---` / `##` 层级）；
   - 表格、代码块、架构图的呈现风格；
   - 是否使用 Obsidian `[[双链]]` 互链。
3. 严格复用识别出的约定，使新文档与仓库风格统一。本技能附带 `references/obsidian-conventions.md` 与 `references/document-template.md` 作为常见约定参考（含 frontmatter 标准格式、ASCII/Mermaid 图表规范），但应以当前仓库实际为准。

### 阶段 4：结构化文档生成

1. 采用标准章节骨架（详见 `references/document-template.md`）：
   - 技术背景与动机
   - 核心架构设计（含 ASCII 架构流程图）
   - 关键技术原理（分模块、带公式/机制说明）
   - 性能对比分析（离线基准 + 生产实测 + 同类工作对比，表格化）
   - 应用场景
   - 局限性
   - 总结
2. 语言风格：正式、准确、逻辑清晰，面向技术人员；避免口语化与夸张表述。
3. 图表规范：
   - **简单架构/流程**（单链路、2–5 节点）：用 ASCII 框图。
   - **复杂图**（多组件、多层、含子图/队列/事件流/分支树）：用 **Mermaid**（` ```mermaid ` 代码块），Obsidian 原生渲染、比内联 SVG 稳；避开非法形状 `[("...")]`，用 `%%{init:{themeVariables:{...}}}%%` 锁定配色。
   - 对比数据用表格承载，公式用 LaTeX 或伪代码。
4. 在文档顶部或 frontmatter 记录来源（论文链接、仓库、解读文章），保证可溯源。

### 阶段 5：双链与反向链接维护

1. 若仓库采用双链，在本文档的 `related` 中列出关联技术文档——按仓库习惯用路径式 `"./xxx.md"` 或 Wiki 式 `"[[xxx]]"`。
2. 同步在关联文档的 `related` 中补回向链接，保持知识图谱一致性（例如本文档基于 V4 线上系统的某项技术，则在 `deepseek-v4` 文档中补 `[[deepseek-dspark]]` 或 `./deepseek-dspark.md`）。

## 输出物

- 一份符合仓库格式规范的 Markdown 技术文档，放置于仓库中技术文档对应的合适目录。
- 必要的双链反向链接更新。
