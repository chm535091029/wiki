# AI Agent 部署工程知识体系大纲

## 0. 这份大纲的定位与用法

### 0.1 目标人群与深度设定

面向从事 AI Agent 部署相关岗位、以 Vibe Coding 为主要生产方式的工程师。目标深度是**建立概念坐标系**，不是成为某一领域的实现专家。具体来说，学完应当达到三种能力：

1. **听懂**：别人讨论技术方案时，知道每个词指什么、处在架构的哪一层。
2. **判断**：面对一个需求，能判断该引入哪类组件、为什么现在需要、代价是什么。
3. **提问**：能用准确的术语向 AI 描述问题，让生成的代码不跑偏。

不需要达到的深度：手写高性能并发模型、调优数据库执行计划、从零实现分布式一致性协议。这些是"知道有这回事、知道什么时候该请专家"即可。

### 0.2 深度标记说明

文中每个知识点后带深度标记：

| 标记 | 含义 | 检验标准 |
|------|------|----------|
| 认知 | 知道概念是什么、解决什么问题 | 听到能反应过来，不陌生 |
| 理解 | 知道原理和取舍，能参与选型讨论 | 能说出"为什么这里用 A 不用 B" |
| 应用 | 能排查问题、能指导 AI 写出正确实现 | 出问题时能定位到具体环节 |

### 0.3 与已有知识库的关系

本目录下的 `03-research/Agent` 系列解决的是"Agent 如何思考"，本文解决的是"Agent 如何作为一个服务活在生产环境里"。两者是上下层关系，不重叠。

## 1. 全局心智模型

### 1.1 一条完整请求链路

所有知识点都挂在这条链路上，先建立主干，后面每一节都是对主干某一段的展开。

```
用户浏览器
  │  ① HTTPS 请求
  ▼
边缘层 / 反向代理（Nginx、CDN、网关）
  │  ② 转发、TLS 终结、限流
  ▼
后端服务（FastAPI 等）
  │  ③ 鉴权、校验、路由
  ├────────────► ④ 缓存层（Redis）— 命中则直接返回
  ├────────────► ⑤ 数据库（PostgreSQL）— 读会话历史、写状态
  ▼
Agent 编排层
  │  ⑥ 组装上下文（历史 + 记忆 + 工具清单 + 检索结果）
  ▼
模型推理服务（vLLM / 云 API / 模型网关）
  │  ⑦ 流式返回 token
  ▼
Agent 循环（思考 → 调工具 → 观察 → 再思考）
  │  ⑧ 工具调用走 MCP / 内部 API
  ▼
流式回传（SSE / WebSocket）
  │  ⑨ 逐块推送
  ▼
浏览器渲染（前端逐字显示）
  │
  ▼
旁路：日志、追踪、指标、成本记录
```

理解这条链路后，任何新技术的第一反应都应该是"它插在这条链的哪一节"。

### 1.2 Agent 后端与传统后端的六处本质差异

这是整个知识体系的立论基础，理解了差异，就知道为什么要单独学一套东西。

| 维度 | 传统后端 | Agent 后端 |
|------|----------|-----------|
| 响应时间 | 毫秒到百毫秒 | 秒到分钟级，长尾极长 |
| 确定性 | 相同输入相同输出 | 相同输入可能不同输出，需要评测而非单测 |
| 状态 | 多为无状态，状态在数据库 | 运行中有大量中间状态，需要持久化与断点续跑 |
| 失败模式 | 报错即失败 | 会"看起来成功但结果是错的"，需要语义层校验 |
| 成本 | 与请求数近似线性 | 单次请求的 token 成本差异可达百倍，需要预算控制 |
| 外部依赖 | 数据库、缓存，可控 | 依赖模型供应商，会限流、会抖动、会涨价 |

**由此推出的三条工程原则**（后面所有章节都是这三条的展开）：

- 原则一：长任务不能占用请求线程，必须异步化或流式化。
- 原则二：不确定性必须用可观测与评测来约束，而不是靠人工试。
- 原则三：任何自主循环都必须有预算、步数上限和人工兜底。

## 2. 网络与 Web 基础

### 2.1 互联网与协议层

| 知识点 | 要点 | 深度 |
|--------|------|------|
| 客户端-服务器模型 | 请求由客户端发起，服务端被动响应；服务端无法主动推 | 认知 |
| DNS | 域名到 IP 的解析；TTL、解析失败是常见故障源 | 认知 |
| HTTP 协议 | 方法（GET/POST/PUT/DELETE）、首部、主体、无状态特性 | 理解 |
| HTTPS 与 TLS | 加密通道；证书、握手开销；内网服务常在网关处终结 TLS | 理解 |
| 状态码 | 2xx 成功、3xx 重定向、4xx 客户端错、5xx 服务端错；429 限流、499 客户端断开 | 应用 |
| Cookie 与 Header | 会话标识与鉴权令牌的常见载体 | 理解 |
| CORS | 浏览器的同源策略与跨域放行；前后端分离时最先踩的坑 | 应用 |
| 反向代理与负载均衡 | Nginx、网关的作用；请求如何分发到多个实例 | 理解 |
| TCP 与 UDP | 可靠有序 vs 快速无连接；理解连接建立与断开的代价 | 认知 |

### 2.2 长连接相关概念（Agent 场景高频）

| 知识点 | 要点 | 深度 |
|--------|------|------|
| HTTP 长轮询 | 客户端反复询问，实现简单但浪费资源 | 认知 |
| 分块传输 | 响应分块发送，是流式的基础机制 | 理解 |
| SSE | 服务端单向推送，基于 HTTP，自带重连；Agent 流式输出默认选择 | 理解 |
| WebSocket | 全双工，适合需要打断、双向交互的场景 | 理解 |
| 心跳与保活 | 空闲时发心跳，防止代理层掐断连接 | 应用 |
| 代理缓冲 | Nginx 默认缓冲会毁掉流式效果，需要显式关闭 | 应用 |

## 3. 后端服务基础

### 3.1 服务端框架与请求生命周期

| 知识点 | 要点 | 深度 |
|--------|------|------|
| 框架职责 | 路由、参数解析、序列化、中间件、错误处理 | 理解 |
| 请求生命周期 | 接收 → 中间件链 → 路由 → 业务 → 响应，每一环都能出问题 | 应用 |
| 中间件 | 横切逻辑（鉴权、日志、限流、CORS）的统一挂载点 | 理解 |
| 依赖注入 | 把数据库连接等资源统一装配，便于替换与测试 | 认知 |
| 同步与异步 | I/O 密集场景用异步提高并发；Agent 服务几乎全是 I/O 等待 | 理解 |
| 并发模型 | 进程、线程、协程的区别与适用场景 | 认知 |
| 连接池 | 数据库与 HTTP 连接都有上限，耗尽即雪崩 | 应用 |
| 无状态服务 | 服务本身不存状态，才能水平扩容；状态外置到数据库与缓存 | 理解 |
| 配置管理 | 环境变量、十二要素应用原则、配置与代码分离 | 应用 |
| 优雅关闭 | 重启时先停止接收新请求，处理完在途请求再退出 | 应用 |

### 3.2 API 设计

| 知识点 | 要点 | 深度 |
|--------|------|------|
| REST 风格 | 资源导向的 URL 与方法语义；状态无关 | 理解 |
| 接口版本管理 | v1/v2 路径或首部版本；Agent 接口演进快，版本化必要 | 理解 |
| OpenAPI 规范 | 机器可读的接口描述，前后端与 MCP 工具都依赖它 | 理解 |
| 错误处理约定 | 统一错误码与结构，前端才能稳定处理 | 应用 |
| 分页与幂等键 | 列表接口分页；写接口支持幂等键防重复 | 应用 |
| GraphQL | 客户端按需取字段，减少往返；增加复杂度，按需引入 | 认知 |
| gRPC | 内部服务间高性能通信，跨语言契约 | 认知 |
| Webhook | 服务端反向回调你；异步任务结果的常见通知方式 | 理解 |

### 3.3 认证与授权

| 知识点 | 要点 | 深度 |
|--------|------|------|
| 认证与授权的区别 | 认证解决"你是谁"，授权解决"你能做什么" | 理解 |
| 会话与令牌 | Cookie-Session vs JWT；无状态令牌便于扩展但难以即时吊销 | 理解 |
| OAuth 与 OIDC | 第三方登录与身份标准；企业环境常见 SSO | 认知 |
| 权限模型 | RBAC 角色、ABAC 属性、最小权限原则 | 理解 |
| API 密钥管理 | 密钥轮换、范围限制、泄露应急 | 应用 |
| 密钥存储 | 环境变量、密钥管理服务、切勿入库或入镜像 | 应用 |
| 多租户隔离 | 数据按租户隔离，Agent 场景下尤其重要 | 理解 |

## 4. 数据库

### 4.1 关系型数据库核心

| 知识点 | 要点 | 深度 |
|--------|------|------|
| 关系模型 | 表、行、列、主键、外键、关系（一对一、一对多、多对多） | 理解 |
| SQL 基本能力 | 增删改查、连接、聚合、子查询；能读懂即可 | 理解 |
| 数据建模 | 范式化减少冗余，反范式化换取查询性能 | 理解 |
| 索引 | 加速查询的结构，代价是写入变慢、占空间；联合索引有顺序 | 理解 |
| 查询计划 | 数据库如何执行一条查询；慢查询排查的入口 | 认知 |
| 事务与 ACID | 原子性、一致性、隔离性、持久性 | 理解 |
| 隔离级别 | 读未提交到可串行化；脏读、不可重复读、幻读 | 认知 |
| 锁与竞态 | 并发写冲突；乐观锁与悲观锁 | 理解 |
| 连接池 | 连接数上限与耗尽问题 | 应用 |
| 迁移 | 表结构变更的版本化管理，可回滚 | 应用 |
| ORM | 对象与表的映射；方便但有性能陷阱 | 理解 |
| N+1 查询 | 循环里查库导致查询爆炸，最常见的性能问题 | 应用 |
| 读写分离与副本 | 主库写、从库读，注意复制延迟 | 认知 |
| 备份与恢复 | 全量、增量、时间点恢复；备份没演练过等于没有 | 理解 |

### 4.2 非关系型存储的选型逻辑

不必记产品，记**数据访问模式决定存储类型**这一条主线。

| 类型 | 典型产品 | 适用访问模式 | 不适用 |
|------|----------|--------------|--------|
| 键值 | Redis、Valkey | 按 key 精确取，极低延迟，可设过期 | 需要条件查询 |
| 文档 | MongoDB | 结构灵活、半结构化数据 | 强事务、复杂关联 |
| 列族 | Cassandra | 海量写入、按分区键读 | 灵活查询 |
| 图 | Neo4j | 多跳关系遍历 | 简单 CRUD |
| 时序 | TimescaleDB | 按时间范围聚合，如指标、对话流水 | 高频更新单条 |
| 向量 | pgvector、Milvus、Qdrant | 相似度检索 | 精确匹配、事务 |
| 对象存储 | S3、MinIO | 大文件、图片、模型权重 | 结构化查询 |
| 搜索引擎 | Elasticsearch | 全文检索、混合检索 | 作为主数据库 |

### 4.3 缓存

| 知识点 | 要点 | 深度 |
|--------|------|------|
| 缓存位置 | 客户端、CDN、网关、应用内存、分布式缓存 | 理解 |
| 缓存策略 | 旁路缓存、写穿、写回；读多写少最适合 | 理解 |
| 失效与一致性 | 缓存与数据库不一致是常态，控制 TTL 与主动失效 | 应用 |
| 穿透、击穿、雪崩 | 查不存在的 key、热点 key 失效、大批同时失效 | 理解 |
| 限流与计数 | 用缓存做速率限制，保护下游 | 应用 |
| 语义缓存 | 相同语义问题复用答案，Agent 场景降本利器 | 理解 |

## 5. Agent 场景的存储设计

这是本知识体系与传统后端分野最明显的一节。

### 5.1 三层记忆与存储的对应关系

| 记忆类型 | 回答的问题 | 数据特征 | 存储选择 | 深度 |
|----------|-----------|----------|----------|------|
| 短期记忆 | 本次会话刚说了什么 | 高频读、生命周期短、按会话 ID 精确取 | 键值存储（Redis），带 TTL | 理解 |
| 长期记忆 | 跨会话记住什么事实 | 结构化、需事务与关联、需审计 | 关系型数据表 | 理解 |
| 语义记忆 | 有什么内容与当前问题相关 | 向量、相似度检索 | pgvector 或专用向量库 | 理解 |
| 情节记忆 | 历史上发生了什么 | 时序流水、按时间范围查 | 关系表分区或时序库 | 认知 |

关键判断：**短期内不要一上来就引入独立向量数据库**。若数据量不大、检索不是核心瓶颈，PostgreSQL 加向量扩展能同时满足结构化查询与相似度检索，减少一个运维对象和一份一致性问题。只有当向量规模、检索延迟或并发写入成为明确瓶颈时，才独立出去。

### 5.2 状态持久化与断点续跑

| 知识点 | 要点 | 深度 |
|--------|------|------|
| 检查点 | 把 Agent 每一步的状态落库，进程重启后可从断点恢复 | 理解 |
| 持久执行 | 任务状态独立于进程生命周期，靠外部存储与队列保证 | 理解 |
| 状态版本化 | 状态结构变更时，老版本会话不能崩 | 应用 |
| 运行记录表 | 记录每次运行的输入、步骤、工具调用、耗时、成本 | 应用 |
| 幂等键 | 同一请求重复提交只执行一次，防重试风暴 | 应用 |
| 软删除与审计 | Agent 的写操作必须可追溯、可回滚 | 理解 |

### 5.3 混合检索

| 知识点 | 要点 | 深度 |
|--------|------|------|
| 关键词检索 | 精确匹配，适合专有名词、代码符号 | 理解 |
| 向量检索 | 语义相似，适合模糊表述 | 理解 |
| 混合检索 | 两路召回后融合排序，实际效果通常优于单路 | 理解 |
| 重排序 | 粗排后用更准的模型精排 | 认知 |
| 分块策略 | 文档切分方式直接决定检索质量 | 理解 |

## 6. 异步、队列与工作流编排

### 6.1 为什么必须异步

Agent 单次运行常达数十秒到数分钟，远超 HTTP 请求与网关的合理等待时间。同步阻塞会导致连接耗尽、超时中断、结果丢失。因此长任务必须脱离请求-响应路径。

### 6.2 核心知识点

| 知识点 | 要点 | 深度 |
|--------|------|------|
| 任务队列 | 生产者投递任务，消费者异步执行，削峰填谷 | 理解 |
| 工作者进程 | 独立运行的消费端，可单独扩容 | 理解 |
| 发布订阅 | 一对多广播，事件驱动架构的基础 | 认知 |
| 任务与结果 | 同步等待、轮询查询、回调通知三种取结果方式 | 理解 |
| 重试与退避 | 指数退避加抖动，避免重试风暴 | 应用 |
| 幂等设计 | 重试的前提是重复执行无副作用 | 应用 |
| 死信队列 | 反复失败的任务隔离出来人工处理 | 应用 |
| 定时任务 | 周期触发，注意分布式环境下的重复执行 | 认知 |
| 优先级与并发控制 | 重要任务优先，控制并发保护下游 | 理解 |
| 工作流编排 | 把多步骤流程显式建模，支持重试、补偿、人工介入 | 理解 |
| 持久工作流 | 流程状态持久化，可跨天暂停与恢复 | 理解 |
| 背压 | 下游处理不过来时反压上游，而非无限堆积 | 认知 |

### 6.3 选型直觉

简单后台任务用队列加工作者即可；需要暂停、恢复、人工审批、长周期的多步流程，才引入工作流编排引擎。不要过早引入。

## 7. 流式输出与实时交互

### 7.1 四种交互模式的选择

| 模式 | 适用场景 | 优点 | 代价 |
|------|----------|------|------|
| 同步一次性返回 | 短任务、批处理、程序化调用 | 实现最简单 | 长时间无反馈，易超时 |
| 轮询 | 后台长任务查进度 | 实现简单，兼容性好 | 有延迟且浪费请求 |
| SSE 流式 | 逐字输出、工具调用过程展示 | 单向推送够用，基于 HTTP 穿透性好，自带重连 | 客户端无法在同一连接上回传 |
| WebSocket | 需要打断、边说边改、双向实时 | 全双工、低延迟 | 连接管理复杂，代理与扩容更麻烦 |
| 异步回调 | 分钟级以上的任务 | 完全解耦 | 需要回调端点与结果存储 |

**默认选择**：Agent 对话界面用 SSE；需要"打断生成"或"边生成边输入"再上 WebSocket；跑批与超长任务用后台任务加轮询或回调。

### 7.2 工程细节

| 知识点 | 要点 | 深度 |
|--------|------|------|
| 事件类型设计 | 区分文本块、工具开始、工具结果、状态、错误、结束 | 应用 |
| 首字延迟 | 用户感知的延迟是首个 token 到达时间，而非总耗时 | 理解 |
| 断线重连与续订阅 | 连接断开后按任务 ID 重新订阅，不丢失已完成部分 | 应用 |
| 背压 | 客户端渲染慢时不能拖垮服务端，队列设上限并定义溢出策略 | 应用 |
| 心跳 | 空闲时发注释行保活 | 应用 |
| 代理配置 | 关闭缓冲、放宽读超时，否则流式会被攒成一次性返回 | 应用 |
| 中断与取消 | 用户停止时要能真正取消模型调用与工具执行 | 应用 |

## 8. 前端交互常识

目标不是写前端，是能看懂前端同学的方案、能判断交互设计的工程代价。

### 8.1 前端基础概念

## 14. 自测清单

能回答以下问题，说明该章节已达标。

**主干**：用户点发送后，数据经过哪几个环节回到屏幕？哪一环最容易成为瓶颈？

**后端**：4xx 与 5xx 的区别？为什么服务要无状态？连接耗尽会发生什么？

**数据库**：什么情况下加索引反而有害？事务解决什么问题？N+1 是什么？

**存储**：短期记忆与长期记忆为什么用不同存储？什么条件下才需要独立向量数据库？

**异步**：重试的前提是什么？幂等键怎么设计？什么任务需要工作流引擎而不是队列？

**流式**：SSE 与 WebSocket 怎么选？代理层为什么要特殊配置？用户中断后服务端要做什么？

**前端**：为什么密钥不能放前端代码？流式渲染为什么要有状态机？

**Agent 工程**：一个工具应该对外暴露哪些契约？Agent 死循环怎么防？上下文为什么会被污染？

**可靠性**：超时为什么必须层层收敛？追踪与日志的区别？评测集从哪来？

**部署**：滚动更新时正在执行的长任务怎么办？扩缩容按什么指标？

## 15. Vibe Coding 提问模板

掌握知识体系的实际用途是提出好问题。以下模板可直接复用。

**定位问题层**：把这个现象映射到链路的某一环，再描述。
> 我在用 SSE 做 Agent 流式输出，本地正常，经过 Nginx 后变成一次性返回。请检查缓冲相关配置。

> 我的 Agent 目前是同步接口，单次运行约 40 秒。请分析是否必须引入任务队列，还是先做流式就够了，并说明各自的复杂度代价。

> 会话状态存 Redis 还是 PostgreSQL？我的规模是日活百级、会话需保留 30 天、需要事后审计。请给出推荐并说明什么时候应该切换。

**让 AI 暴露假设**：
> 请先列出你这个实现隐含的假设（并发量、失败模式、成本量级），再给代码。

**要求可运维**：
> 补上结构化日志、请求 ID 贯穿、以及关键指标的埋点，不要只写业务代码。

## 16. 术语速查

| 术语 | 一句话解释 |
|------|-----------|
| 幂等 | 同一操作执行多次与执行一次效果相同 |
| 背压 | 下游处理不过来时向上游施加限制 |
| 检查点 | 运行中状态的持久化快照，用于恢复 |
| 断点续跑 | 中断后从上次状态继续，而非重头开始 |
| 熔断 | 下游持续故障时主动快速失败 |
| 降级 | 主能力不可用时提供简化替代 |
| 灰度 | 新版本先对小部分流量生效 |
| 编排 | 对多步骤流程的显式控制与调度 |
| 护栏 | 执行前的校验与拦截层 |
| 人在回路 | 关键决策交由人工确认 |
| 追踪 | 一次请求在所有服务中的调用链记录 |
| 跨度 | 追踪中的单个调用单元 |
| 冷启动 | 服务从零到可响应的初始化耗时 |
| 连续批处理 | 推理服务动态合并请求提高吞吐 |
| 提示缓存 | 复用相同前缀的计算结果 |
| 语义缓存 | 相似问题复用历史答案 |
| 上下文压缩 | 缩减输入长度以控制成本与保持质量 |
| 混合检索 | 关键词与向量两路召回融合 |
| 重排序 | 粗排后再次精排 |
| 对象存储 | 存放大文件的扁平存储服务 |
| 服务发现 | 动态实例的地址查找机制 |
| 就绪探针 | 判断实例能否接收流量的健康检查 |
