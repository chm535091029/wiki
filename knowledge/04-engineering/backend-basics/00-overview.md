# AI 应用后端知识地图

**定位**：面向 vibe coding 场景的后端知识梳理。目标不是独立手写生产级后端服务，而是在 AI 生成后端代码时能判断对错，并能用准确术语向 AI 提出约束条件。

## 一、先说清目标

补后端的动因通常是两类，混在一起学会很累：

| 目标 | 判据 | 本套笔记是否覆盖 |
|------|------|------------------|
| A：能看懂、能审查、能提约束 | AI 写出来能看出哪里不对 | 覆盖 |
| B：能独立写生产级服务 | 从零实现含数据库、鉴权、部署的完整服务 | 不覆盖 |

选择 A 的理由：AI 生成的后端代码，错误几乎都集中在它看不见的运行期约束上，包括连接池、事务边界、幂等、事件循环阻塞。这类问题不报错、本地能跑通、只在并发或线上暴露。不具备相应知识就无法发现，也不会在 prompt 里把约束写进去。

## 二、六个知识板块

| 板块 | 核心内容 | 在 AI 应用中的位置 | 笔记 |
|------|----------|--------------------|------|
| 数据与存储 | 从零讲起：磁盘存储、B+ 树索引原理、事务与并发更新 | 元数据、会话记录、向量、文件 | [01](./01-data-and-storage.md) |
| 并发与请求模型 | 协程、连接池、队列、流式 | 模型调用是最慢最贵的一段 | [02](./02-concurrency-and-request-model.md) |
| 服务与接口 | HTTP 语义、鉴权、接口设计 | 对外 API、网关层 | [03](./03-service-and-api.md) |
| 状态与缓存 | Redis、无状态服务、一致性 | 会话、限流计数、配置同步 | [04](./04-state-and-cache.md) |
| 可靠性与可观测 | 重试、限流、熔断、日志追踪 | 部分故障不整体崩塌 | [05](./05-reliability-and-observability.md) |
| 交付与运行 | 容器、配置、密钥管理 | 部署、多机、回滚 | [06](./06-delivery-and-runtime.md) |

## 三、优先级分层

| 层级 | 内容 | 判断标准 |
|------|------|----------|
| P0 必须懂 | 连接池、超时与重试、异步并发模型、事务边界、索引与慢查询 | 不然后端代码的对错无法判断 |
| P1 值得懂 | 缓存一致性、消息队列与任务异步化、鉴权体系、限流与背压、密钥管理 | 能显著提升架构判断力 |
| P2 知道存在即可 | 分库分表、分布式事务、Kubernetes、服务网格、多级缓存 | 能在需求描述里提出约束就行 |

## 四、案例锚点：New API 网关

本套笔记统一用 New API 作为概念锚点。选它的原因：它本身就是一个结构完整的标准后端，路由、连接池、缓存、限流、超时、重试、密钥、容器化全部齐备，且是本机正在使用的项目。

| 概念 | New API 中的落点 |
|------|------------------|
| 分层架构 | Router → Controller → Service → Model |
| 数据库连接池 | `SQL_MAX_OPEN_CONNS`、`SQL_MAX_IDLE_CONNS` |
| 日志库分离 | `LOG_SQL_DSN`（主库与日志库分开） |
| 缓存 | Redis + 内存混合缓存 |
| 限流 | `middleware/rate-limit.go`，API / Web / Critical 三层 |
| 超时 | `RELAY_TIMEOUT`（上游请求）、`STREAMING_TIMEOUT`（SSE 无数据块） |
| 资源保护 | `MAX_REQUEST_BODY_MB`、`STREAM_SCANNER_MAX_BUFFER_MB` |
| 重试 | 运营设置中的渠道重试次数 |
| 健康检查 | `controller.AutomaticallyTestChannels` |
| 鉴权与密钥 | `SESSION_SECRET`、`CRYPTO_SECRET`、`TRUSTED_PROXIES` |
| 可观测 | 独立日志库、Pyroscope、pprof |
| 容器编排 | `docker-compose.yml`：new-api + PostgreSQL + Redis |

> 说明：以上引用上游 `Calcium-Ion/new-api` 的公开结构，用于建立概念与真实代码的对应关系。本地 fork 可能已有改动，具体路径以实际源码为准。

## 五、学习路径

| 阶段 | 内容 | 产出 |
|------|------|------|
| 阶段一 | 板块 02（并发与请求模型） | 建立"哪里会崩"的判断力，投入产出比最高 |
| 阶段二 | 板块 01（数据与存储） | 能看懂表设计、索引与事务范围 |
| 阶段三 | 板块 04、05（状态缓存、可靠性） | 能判断架构是否会被自身故障拖垮 |
| 阶段四 | 板块 03、06（接口、交付） | 补齐边界知识，够用即可 |

不按教材顺序系统学。后端教材是按"造轮子"组织的，本套笔记按"能判断对错"组织，每个概念只需达到判断阈值。

**例外的两篇**：01 与 02 是唯一两篇讲到底层的。01 从"数据在磁盘上怎么放"讲起，是整套笔记里唯一从零起步的一篇，数据库基础薄弱时建议从此篇开始；02 讲清协程传染性与连接池，是 AI 应用最直接的能力项。其余四篇保持"能判断"的深度，不往下钻。

## 六、每篇笔记的统一结构

每篇包含五部分：概念要点、New API 中的落点、典型误写与修正、审查红灯信号、判断阈值。

其中两项是核心产出：

- **典型误写与修正**：给出成对代码片段，展示错误写法与正确写法的具体差异。判断力建立在对错对比上，抽象描述记不住。
- **审查红灯信号**：列出看到 AI 写出什么代码时需要停下来警觉。这是 vibe coding 场景下直接可用的检查清单。

## 七、边界说明

前端不在本套笔记范围内。vibe coding 场景下只需理解三件事：CORS 报错的原因、token 存放位置与传递方式、SSR 与 CSR 的区别。够用即可。

## 八、版本说明

本套笔记为后端知识的重写版本，取代此前的旧版内容。组织方式与旧版不同：旧版按知识点独立成文，本版按板块聚合，并统一采用"概念、案例、误写、红灯、阈值"五段结构，以便在 vibe coding 时直接对照使用。
