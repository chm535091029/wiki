# 板块 04：状态与缓存

**核心思想**：服务本身应当无状态，所有需要跨请求保留的状态放进 Redis 或其他外部存储。这一条能过滤掉 AI 生成代码中大量的架构级错误。

上级索引：[AI 应用后端知识地图](./00-overview.md)

## 一、无状态服务原则

**无状态指**：任何一台服务节点处理任何一次请求，结果都相同，节点之间不依赖彼此的本地内存。

为什么这是硬要求：

| 有状态的后果 | 表现 |
|--------------|------|
| 无法水平扩容 | 新节点没有旧节点的内存状态，请求分流即出错 |
| 节点重启丢数据 | 内存中的会话与任务全部消失 |
| 负载均衡受限 | 必须做会话保持，失去均衡意义 |
| 故障无法切换 | 节点挂了，其内存状态无法迁移 |

**违反这一原则的典型写法**：把用户上下文、任务进度、限流计数、待处理队列存在进程内的字典或全局变量里。这类代码单机测试完全正常，一上多节点就出问题。

**正确做法**：状态放 Redis。需要本地缓存时，本地缓存只能是"可丢失的加速层"，不能是唯一副本。

## 二、Redis 的四类典型用法

| 用法 | 数据结构 | 说明 |
|------|----------|------|
| 缓存 | String / Hash | 缓存数据库查询结果或上游响应 |
| 会话存储 | String / Hash | 多节点共享登录态 |
| 计数器与限流 | 带过期的计数键、有序集合 | 令牌桶、滑动窗口限流 |
| 分布式锁 | String 加过期时间 | 保证跨节点互斥 |

**分布式锁的三个必要条件**：加锁时必须带过期时间（否则持锁进程崩溃会死锁）；解锁时必须校验持有者（否则会释放别人的锁）；获取失败要有超时与重试。加锁与设置过期必须是原子操作。

**Redis 作为限流存储的关键点**：限流计数放在 Redis 才能在多节点间共享。若各节点用本地内存计数，总限额会被放大为"限额乘以节点数"。

## 三、缓存三件套

| 问题 | 现象 | 应对 |
|------|------|------|
| 缓存穿透 | 查询不存在的数据，每次都打到数据库 | 缓存空值，或用布隆过滤器前置拦截 |
| 缓存击穿 | 某个热点键过期瞬间，大量请求同时打到数据库 | 加互斥锁只让一个请求回源，或热点键不过期 |
| 缓存雪崩 | 大量键同时过期，数据库瞬间被压垮 | 过期时间加随机抖动，避免同时失效 |

三者名称接近，区分方法是看"查什么"：查不存在的数据是穿透，查单个热点键是击穿，大批键同时失效是雪崩。

## 四、缓存与数据库的一致性

**推荐策略**：更新数据库，然后删除缓存（而不是更新缓存）。

理由：更新缓存会有并发写覆盖问题，两个请求的更新顺序可能与数据库不一致；删除缓存让下一次读取自然重建，出错概率更低。

**仍存在的不一致窗口**：删除缓存失败、或删除后旧值被并发读回。因此要建立两个认识：

- 缓存一致性是最终一致，不是强一致。对强一致有要求的场景不要用缓存，或让缓存的读写在同一事务路径内。
- 缓存删除失败要有补偿机制，例如通过消息重试删除。

**过期时间是兜底**：无论采用什么策略，缓存都应设置过期时间。它保证即使某次不一致没被处理，也会在一段时间后自愈。

## 五、多节点下的状态一致问题

多节点部署时，以下几类状态必须共享，否则行为不一致：

| 状态 | 不共享的后果 |
|------|--------------|
| 会话密钥 | 登录状态在不同节点间跳来跳去 |
| 加密密钥 | 共享缓存中的密文无法解密，读取失败 |
| 限流计数 | 总限额被放大 |
| 后台定时任务 | 每个节点都执行一遍，产生重复操作 |

最后一条容易被忽略。定时任务必须在多节点中只有一个执行，通常通过角色配置或分布式锁实现。

## 六、New API 中的落点

| 概念 | 落点 |
|------|------|
| 混合缓存 | Redis 加内存缓存两层，Redis 未配置时退化为单机内存缓存 |
| 缓存配置 | `REDIS_CONN_STRING` 指定 Redis，`MEMORY_CACHE_ENABLED` 控制内存缓存 |
| 会话密钥共享 | `SESSION_SECRET`，多机部署必须各节点一致 |
| 加密密钥共享 | `CRYPTO_SECRET` 默认继承 `SESSION_SECRET`，多节点共享 Redis 时必须一致 |
| 分布式限流 | `middleware/rate-limit.go` 支持 Redis 或内存存储，文档中明确提示多节点若不用共享 Redis，各节点限额独立计数 |
| 主从角色 | `NODE_TYPE=slave` 关闭仅主节点运行的后台任务，避免多节点重复执行 |
| 配置同步 | `model.SyncOptions` 定期从数据库刷新全局配置，使配置变更在各节点间传播 |

这里有三个可直接借鉴的判断：

**第一，缓存是可选的，而不是必需的。** 项目支持纯内存模式，也支持 Redis 模式。这说明它把缓存视为性能层而非数据层，无 Redis 时功能仍完整，只是多节点下状态不共享。这是正确的缓存定位。

**第二，文档显式写出了"不用共享 Redis 则各节点限额独立计数"。** 这类架构限制被明确记录，而不是留给人踩坑，是工程上值得学习的做法。

**第三，`NODE_TYPE=slave` 是解决定时任务重复执行的典型手段。** 通过角色配置而非分布式锁来保证唯一执行，实现更简单。

## 七、典型误写与修正

### 会话状态放在进程内存

误写方向：单机测试完全正常，多节点部署时请求被分到别的节点就找不到会话，进程重启则全部丢失。

```python
SESSIONS = {}                                       # 进程内字典

@app.post("/login")
async def login(body: LoginIn):
    user = await repo.verify(body)
    SESSIONS[user.id] = {"login_at": time.time()}   # 只活在这一个进程里
    return {"ok": True}
```

修正：状态外置到 Redis，服务本身保持无状态。

```python
@app.post("/login")
async def login(body: LoginIn):
    user = await repo.verify(body)
    await redis.setex(
        f"sess:{user.id}", 1800, json.dumps({"login_at": time.time()}))
    return {"ok": True, "sid": user.id}
```

同理，任务进度、限流计数、待处理队列都不应存在进程内存里。

### 缓存不设过期时间

误写方向：一次写入错误就无法自愈，且大批键可能同时失效引发雪崩。过期时间是兜底机制，不是可选项。

```python
cached = await redis.get(key)
if cached is None:
    val = await db.fetch_one("select * from cfg where id = $1", key)
    await redis.set(key, json.dumps(val))           # 永不过期
    return val
```

修正：设置过期时间，并加随机抖动避免同时失效。

```python
cached = await redis.get(key)
if cached is None:
    val = await db.fetch_one("select * from cfg where id = $1", key)
    ttl = 300 + random.randint(0, 60)               # 抖动，打散失效时间
    await redis.set(key, json.dumps(val), ex=ttl)
    return val
```

### 分布式锁缺少原子性、过期时间与持有者校验

误写方向：先查再设不是原子操作；没有过期时间，持锁进程崩溃即死锁；删除时不校验持有者，会释放别人的锁。

```python
if not await redis.get(lock_key):                   # 查与设之间有竞态
    await redis.set(lock_key, "1")                  # 没有过期时间
    await do_work()
    await redis.delete(lock_key)                    # 可能删的是别人的锁
```

修正：用单条原子命令加锁并带过期，解锁时用脚本校验持有者。

```python
token = uuid.uuid4().hex
got = await redis.set(lock_key, token, nx=True, ex=30)   # 原子加锁 + 过期
if not got:
    raise Busy("资源繁忙，请重试")

try:
    await do_work()
finally:
    lua = """
    if redis.call('get', KEYS[1]) == ARGV[1]
      then return redis.call('del', KEYS[1]) end
    """
    await redis.eval(lua, 1, lock_key, token)       # 只删自己持有的锁
```

## 八、审查红灯信号

- 用户会话、任务进度、限流计数存在进程内的全局变量或模块级字典里。
- 本地内存缓存被当作唯一数据源，而不是加速层。
- 缓存只写不设过期时间。
- 分布式锁没有过期时间，或不校验持有者就直接删除。
- 采用"更新数据库同时更新缓存"的策略，且没有处理并发写覆盖。
- 热点数据没有防击穿的互斥机制。
- 后台定时任务没有单节点执行的控制。
- 多节点部署但限流使用本地内存计数。

## 九、判断阈值

- 看到把状态存在内存里的代码，能立刻判断它在多节点下会出问题。
- 能区分缓存穿透、击穿、雪崩并说出各自的应对手段。
- 能说明缓存与数据库采用何种一致性策略，以及不一致窗口如何处理。
- 能列出多节点部署下必须共享的状态清单。
