# 板块 01：数据与存储

**核心思想**：AI 应用的数据不是单一形态，而是业务元数据、会话记录、向量、文件对象四种混存。你不需要成为 DBA，但必须能判断表结构是否合理、索引是否用得上、事务范围是否过大、并发更新会不会丢数据。

> 本篇从零讲起。索引部分不背结论，而是先讲清"数据在磁盘上怎么放"，理解了这个前提，最左前缀、回表、覆盖索引都是自然推论，不需要记。

## 一、关系型数据库的基本结构

### 1.1 库、表、行、列

关系型数据库把数据组织成二维表。一个库里有若干表，一张表由行和列组成。列有固定的名称和类型，行是具体的记录。这个模型和 Excel 很像，但有一个根本差异：**数据库对列的约束是强制的**，写错类型会被直接拒绝，而 Excel 不会。

### 1.2 主键

主键是表中唯一标识一行的列或列组合。两个作用：

- **唯一性**：不允许重复，不允许为空。
- **定位**：数据库需要一种方式在物理上找到某一行，主键就是默认的定位依据（原因见第五节）。

主键有两种主流选择，取舍如下：

| 方案 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| 自增整型 | 顺序写入，性能最好，占用小 | 全局唯一性难做，暴露业务量 | 单库单表、内部表 |
| UUID / 雪花 ID | 可提前生成，分布式友好，不暴露业务量 | 随机写入会导致页分裂，索引膨胀 | 分布式、需要对外隐藏规模 |
| 业务字段（如令牌字符串） | 天然唯一，查询直接命中 | 长主键会撑大所有二级索引 | 令牌、渠道这类天然有 key 的表 |

**审查要点**：主键长度会传导到每一个二级索引上（原理见第五节），所以不要让主键太长。用 36 字节的 UUID 字符串做主键，会让所有二级索引都多背 36 字节。

### 1.3 外键与约束

| 约束 | 作用 | 该不该用 |
|------|------|----------|
| 外键 | 保证引用完整性，父表没有的记录不允许写入子表 | 单库可用；分库或高频写入场景常改为应用层维护 |
| 非空 | 禁止写入 NULL | 能用则用，NULL 会带来三值逻辑的坑 |
| 唯一 | 禁止重复值 | 防重复写入的最后防线，应尽量交给数据库 |
| 默认值 | 未提供时填充 | 注意默认值是否安全 |

**一个原则**：能交给数据库校验的，不要只写在应用层。应用层有并发窗口，数据库没有。防止重复注册这件事，应用层的"先查再插"在高并发下必然出现重复，唯一索引才是可靠方案。

### 1.4 数据类型的选择

类型选择直接决定存储开锁和索引效率，几个常见判断：

| 场景 | 选择 | 理由 |
|------|------|------|
| 金额 | `decimal` / `numeric` | `float` / `double` 是二进制浮点，无法精确表示 0.1，累计计算会出现误差 |
| 短文本 | `varchar(n)` | 长度可控，可整套索引 |
| 长文本 | `text` | 不能设默认值，不能整套索引，只能前缀索引 |
| 时间 | `timestamp with time zone`（PG）/ 存 UTC 的 `datetime` | 避免时区混乱，一律存 UTC，展示时再转 |
| 布尔 | `boolean` / `tinyint(1)` | 不要用字符串存 |
| 半结构化 | `jsonb`（PG）/ `json`（MySQL 8） | 可索引、可查询，但不要当主力结构 |
| 枚举 | 小整数 + 字典表 | 直接存字符串会撑大表并让改动困难 |

**审查要点**：看到用 `float` 存金额、用字符串存时间、用 `text` 存需要筛选的字段，都属于需要纠正的设计。

### 1.5 范式与反范式

范式是"如何拆分表以减少冗余"的规则：

| 范式 | 一句话含义 | 违反的例子 |
|------|------------|------------|
| 第一范式 | 每列都是原子值，不能存数组或列表 | 一列里存 `"a,b,c"` |
| 第二范式 | 非主键列必须完全依赖整个主键 | 联合主键下，某列只依赖其中一个主键列 |
| 第三范式 | 非主键列不能依赖另一个非主键列 | 订单表里存了用户手机号，而手机号属于用户表 |

**实践中不必教条**。以读为主的系统会刻意反范式，把常用的关联字段冗余到主表，用一次查询换取一个 JOIN。判断标准是：该字段是否几乎不变、是否高频参与查询。用户手机号在订单表里冗余一份是合理的（下单时的快照，甚至业务上就应该保持历史值）；但用户的余额就不该冗余。

## 二、一行数据在磁盘上怎么放

这一节是理解索引的前提，值得慢读。

### 2.1 读写的最小单位是页，不是行

数据库不会一次只读一行。它和磁盘交互的最小单位叫**页**（page），InnoDB 默认 16KB，PostgreSQL 默认 8KB。

也就是说：你想读一行，数据库至少要读一整页，把这一页从磁盘搬进内存，再从里面挑出你要的那行。

### 2.2 表在磁盘上基本是"乱放"的

如果没有索引，一张表在磁盘上就是一个**堆**（heap）：新行往有空间的地方塞，行与行之间没有按任何业务字段排序。

带来的后果是：**要查 `where user_id = 42`，数据库不知道 42 在哪一页，只能从第一页开始逐页读到最后一页。** 这叫全表扫描。

### 2.3 为什么全表扫描慢

两个原因，第二个才是关键。

**一是量。** 一千万行的表，按一行 1KB 算约 10GB，页大小 16KB 就是约 65 万个页。

**二是随机 IO 与顺序 IO 的巨大差距。** 机械盘上顺序读取能达到 100MB/s 以上，而随机读取受限于磁头寻道，每秒只能做几百次。即使换成 SSD，随机读的吞吐也远低于顺序读。全表扫描需要把 65 万个页都搬进内存，其中绝大多数是白读的。

**索引要解决的就是这件事：把"逐页翻找"变成"按序定位"。**

## 三、索引到底解决了什么问题

### 3.1 索引的本质

索引 = **一份排好序的、只包含部分字段的数据副本 + 指向原数据行的指针**。

最直观的类比是书的目录。没有目录，你要找某个知识点就得从第一页翻到最后一页；有了目录，你按拼音顺序定位到页码，直接翻过去。

**排序是关键。** 排好序之后才能用二分查找，才能把 O(n) 的逐页扫描变成 O(log n) 的定位。

### 3.2 索引的代价

索引不是免费的，这是初学者最容易忽略的一点：

| 代价 | 说明 |
|------|------|
| 占空间 | 索引本身要存一份数据，联合索引和长主键会放大这个开销 |
| 拖慢写入 | 每次 insert / update / delete 都要同步维护所有相关索引，页分裂也要额外开销 |
| 增加优化器负担 | 索引太多时，优化器可能选错索引 |

结论是：**索引是给读换写的交易**。写多读少的表（如日志表）要克制，读多的表可以大胆加。

## 四、B+ 树为什么被选中

### 4.1 先排除两个候选

**为什么不用平衡二叉搜索树（AVL / 红黑树）？** 因为它的每个节点只有两个子节点，树太高。一千万行需要约 24 层，意味着最多 24 次磁盘 IO。而每次 IO 都要从磁盘搬一页，代价极高。二叉树的形状由内存场景设计，不适用于磁盘。

**为什么不用哈希表？** 哈希的等值查询是 O(1)，很快，但它有两个致命限制：**不支持范围查询**（`where created_at > x`），**不支持排序**（`order by`）。而真实业务里范围查询与排序占了大头，所以哈希索引只作为补充（如 Redis 的字典），不能作为主力。

### 4.2 B+ 树的特点

B+ 树是为磁盘 IO 量身设计的结构，三个特点：

1. **多叉，不是二叉。** 一个节点可以有很多子节点，扇出（fan-out）极大，因此树很矮。矮就意味着 IO 次数少。
2. **只有叶子节点存数据，非叶子节点只存"键 + 子指针"。** 这让非叶子节点能塞下更多条目，进一步降低树高。
3. **叶子节点之间用双向链表相连。** 这让范围查询可以顺着链表横向扫描，不必回头走树。

### 4.3 算一下树有多矮

以 InnoDB 为例，页大小 16KB，主键是 `bigint`：

- 非叶子节点每条记录 = 主键 8 字节 + 页指针约 6 字节 = 约 14 字节
- 一个 16KB 的页约能放 `16384 / 14 ≈ 1170` 个条目
- 假设一行数据 1KB（含表头开销），叶子节点一页约放 `16384 / 1024 ≈ 16` 行

| 树高 | 能存多少行 | 查一行最多几次页 IO |
|------|------------|---------------------|
| 2 层 | 1170 × 16 ≈ 1.9 万 | 2 |
| 3 层 | 1170 × 1170 × 16 ≈ 2190 万 | 3 |

**结论：一棵 3 层的 B+ 树可以支撑约两千万行，查一行最多只需要 3 次页 IO。** 而根节点几乎总在内存里（热数据），实际往往只需要 2 次。

这就是索引快的原因：**把一个可能需要几万次 IO 的全表扫描，变成 2 到 3 次 IO。**

### 4.4 一次索引查询的过程

以 `where id = 42` 为例：

1. 从根节点开始，在页内二分查找，判断 42 属于哪个子区间，取到对应的页指针。
2. 读入该子节点（第二次 IO）。
3. 继续二分，直到叶子节点。
4. 在叶子节点内二分，定位到 id = 42 的记录，取出数据。

整个过程是"每次二分都把搜索范围缩小 1170 倍"，所以 3 次就能从上千万行里定位到一行。

## 五、聚簇索引、二级索引与回表

### 5.1 聚簇索引

**InnoDB 的主键索引就是聚簇索引（clustered index）**，特性是：**叶子节点直接存整行数据**。

换句话说，在 InnoDB 里，**表本身就是按主键组织的一棵 B+ 树**。数据即索引，索引即数据。一张表只能有一个聚簇索引，因为数据只能按一种顺序摆放。

MySQL 与 PostgreSQL 在这里有一个重要差异：MySQL 的 InnoDB 强制有聚簇索引（没主键会自建隐藏主键）；PostgreSQL 的表是堆表，所有索引都是独立的、指向物理行位置。**下文以 InnoDB 为例，因为这三个特性（回表、主键长度传导、自增主键友好）都是 InnoDB 的行为，PostgreSQL 下表现不同。**

### 5.2 二级索引与回表

你在 `created_at` 上建的索引叫**二级索引**（也叫辅助索引、非聚簇索引）。它的叶子节点**不存整行数据，只存"索引列的值 + 主键值"**。

为什么只存主键值？因为如果每个索引都存整行，一份数据会被复制很多遍。只存主键，等于把整行数据的查找委托给聚簇索引。

于是产生**回表**：

```sql
select * from messages where user_id = 42;
```

执行过程分两步：

1. 走 `user_id` 的二级索引，找到所有 `user_id = 42` 的叶子节点，取出其中的主键值（假设是 id = 1001、1005、1009...）。
2. **拿着这些主键值，再去聚簇索引查一遍，取出整行数据。** 这一步就叫回表。

回表意味着：走二级索引拿到 N 个主键，就要再做 N 次聚簇索引查找。**这是"索引明明走了，查询还是慢"的头号原因。**

### 5.3 覆盖索引：绕开回表

如果查询需要的列**全部**都在二级索引里，就不需要回表了。这叫覆盖索引。

```sql
-- 假设有索引 (user_id, created_at)

-- 需要回表：select * 要取整行，索引里没有 content
select * from messages where user_id = 42;

-- 不需要回表：两个列都在索引里
select user_id, created_at from messages where user_id = 42;
```

在 `EXPLAIN` 里，覆盖索引会显示 `Extra: Using index`，这是好信号。

**实践推论**：写 `select *` 会让覆盖索引彻底失效。这是"不要用 `select *`"这条规范真正的技术原因，而不是风格问题。

### 5.4 为什么推荐自增主键

因为 B+ 树的叶子节点是按主键顺序排的，新行的主键必须插到固定位置：

| 主键类型 | 插入行为 | 后果 |
|----------|----------|------|
| 自增整型 | 新主键总是最大，直接追加到最后一个叶子页 | 顺序写，页填满后再申请新页 |
| UUID 等随机值 | 新主键随机落在中间某个叶子页 | 该页可能已满，触发**页分裂**：把一页拆成两页，还得移动数据并更新父节点 |

页分裂不仅是一次额外的写入开销，还会让页的填充率下降（每页都只有一半左右的数据），导致同样的数据占用更多页，B+ 树变高，IO 变多。

**这就是"自增主键对写入友好"的底层原因**，不是习惯问题。

## 六、联合索引与最左前缀

### 6.1 联合索引的排序规则

在 `(dept_id, created_at)` 上建索引，叶子节点实际是这样排列的：

```
dept_id | created_at | 主键
--------+------------+------
   1    | 2026-01-01 |  11
   1    | 2026-03-05 |  12
   1    | 2026-08-20 |  13     ← dept_id = 1 内部，created_at 递增
   2    | 2026-02-11 |  21
   2    | 2026-09-01 |  22     ← dept_id = 2 内部，created_at 也是递增的
   3    | 2026-01-30 |  31
```

规则是：**先按第一列排序，第一列相同时再按第二列排序，以此类推。**

注意关键点：`created_at` 只在**同一个 `dept_id` 内部**有序，它在全局是无序的。第 3 行的 8 月排在第 4 行的 2 月前面，就说明了这一点。

### 6.2 最左前缀的原理

理解了上面的排列，最左前缀就不需要背了。

最直观的类比是电话簿按"姓 + 名"排序：

- 查"张"或"张三"：能直接定位，因为整体先按姓排序。
- 查"名字叫三的人"：没法定位，因为名字只在同姓内部有序，全局是乱的。

对应到 SQL：

```sql
-- 能用索引：从 a 开始连续匹配
where dept_id = 1
where dept_id = 1 and created_at > '2026-03'
where dept_id = 1 and created_at > '2026-03' and id = 11

-- 不能用索引定位：跳过了第一列
where created_at > '2026-03'

-- 只有第一列能用：a 相等后按 b 排，但 b 是范围，c 在全局无序
where a = 1 and b > 2 and c = 3
```

### 6.3 三个容易踩的推论

**推论一：范围条件会中断后面的列。** 在上面的第三条例子里，`b > 2` 是范围条件，导致 `c` 无法用于定位。所以联合索引的列顺序应当遵循 **等值条件在前、范围条件在后**。

**推论二：排序也能用索引。** `order by dept_id, created_at` 可以直接顺着索引读，因为索引本身就是这个顺序。但 `order by created_at` 不行，会退化为 `Using filesort`。**这条能省掉大量排序开销，是最容易被忽视的索引收益。**

**推论三：联合索引不要求所有列都用上，但必须从第一列开始连续。** `(a, b, c)` 上，`where a = 1 and c = 3` 只能用上 `a`，中间的 `b` 断了。

### 6.4 索引下推

MySQL 5.6 之后有个优化叫**索引下推**（Index Condition Pushdown，ICP）。在 `where a = 1 and b > 2 and c = 3` 中，虽然 `c` 没法用于定位，但数据库可以在遍历索引条目时就用 `c` 过滤掉不匹配的记录，**减少回表次数**。`EXPLAIN` 中显示 `Extra: Using index condition`。

它不是索引本身的改进，而是"把过滤提前到回表之前做"。

## 七、怎么判断索引有没有用

### 7.1 选择性

**选择性 = 不重复值的数量 / 总行数**，取值 0 到 1，越接近 1 越好。

| 列 | 选择性 | 该建索引吗 |
|----|--------|------------|
| 用户 ID | 接近 1 | 适合 |
| 手机号 | 接近 1 | 适合 |
| 状态（只有几个取值） | 很低 | 单独建索引意义不大 |
| 性别（两个取值） | 极低 | 不该单独建 |

原因很直观：如果一个索引把一千万行只分成两类，那走它还是要读五百万行，不如直接全表扫描（全表扫描还是顺序 IO，比大量随机回表更快）。**选择性低的列适合放在联合索引的后面，不适合单独建索引。**

### 7.2 索引失效的典型写法

| 写法 | 为什么失效 |
|------|------------|
| `where date(created_at) = '...'` | 对索引列做了函数运算，排序被打乱 |
| `where id + 1 = 10` | 同上，列参与了表达式计算 |
| `where phone = 13800138000`（phone 是 varchar） | 字符串列与数字比较，隐式类型转换导致索引失效。反过来（整型列与字符串比较）通常仍可用 |
| `where name like '%abc'` | 前导通配，无法按前缀定位 |
| `where a = 1 or b = 2`（只有 a 有索引） | OR 两边都需要索引，否则整体退化为全表扫描 |
| `where a = 1 and c = 3`（索引是 a,b,c） | 跳过中间列，最左前缀中断 |
| `where status != 1` | 不等于通常意味着要读大部分行，优化器可能直接放弃索引 |

### 7.3 联合索引的列顺序怎么定

三个原则，按优先级：

1. **等值条件在前，范围条件在后**（因为范围会中断后面的列）。
2. **选择性高的在前**（更早缩小扫描范围）。
3. **考虑能否覆盖查询**，把 `select` 里高频用到的列追加到索引末尾，用空间换掉回表。

**举例**：查询是 `where user_id = ? and created_at > ? order by created_at desc`，且只需要 `user_id, created_at` 两列，那么 `(user_id, created_at)` 是理想索引：等值在前、范围在后、而且正好覆盖查询。

## 八、事务：ACID 与隔离级别

### 8.1 为什么需要事务

最经典的例子是转账：从 A 扣 100，给 B 加 100。这两步必须**全部成功或全部失败**，否则钱就凭空消失或凭空产生。

事务就是把这组操作打包成一个不可分割的单元。

### 8.2 ACID 四个特性

| 特性 | 含义 | 靠什么保证 |
|------|------|------------|
| 原子性 Atomicity | 要么全做，要么全不做 | undo log（回滚日志） |
| 一致性 Consistency | 事务前后数据满足业务约束 | 由原子性、隔离性、持久性共同保证，是目的不是手段 |
| 隔离性 Isolation | 并发事务之间互不干扰 | 锁 + MVCC |
| 持久性 Durability | 提交后即使断电也不丢 | redo log（重做日志） |

**一个容易混淆的点**：一致性是目的，另外三个是手段。业务约束（如余额不能为负）最终要由数据库约束或代码逻辑保证，ACID 只保证"不会因为故障或并发看到中间状态"。

### 8.3 隔离级别与三类异常

先理解三个异常分别是什么现象：

| 异常 | 现象 | 例子 |
|------|------|------|
| 脏读 | 读到了别的事务**还没提交**的数据 | 事务 B 改了余额但未提交，事务 A 就读到了新值；B 回滚后 A 读的是幻觉 |
| 不可重复读 | 同一事务内两次读**同一行**，结果不同 | A 第一次读余额 100，B 提交了把它改成 200，A 再读变成 200 |
| 幻读 | 同一事务内两次**范围查询**，行数不同 | A 第一次查"余额大于 100 的用户"有 5 条，B 插入一条并提交，A 再查变成 6 条 |

区别记忆法：**不可重复读针对同一行的"值"变了；幻读针对范围查询的"行数"变了。**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|----------|------|------------|------|------|
| 读未提交 | 可能 | 可能 | 可能 | 几乎不用 |
| 读已提交 | 不可能 | 可能 | 可能 | Oracle / PostgreSQL 默认 |
| 可重复读 | 不可能 | 不可能 | 多数实现下不可能 | MySQL InnoDB 默认 |
| 串行化 | 不可能 | 不可能 | 不可能 | 完全串行执行，性能最差 |

**MySQL 的 InnoDB 在"可重复读"下也能避免大部分幻读**，靠的是 MVCC 快照加间隙锁，这也是它把这个级别设为默认值的原因。标准只要求"可重复读"解决不可重复读，幻读是 MySQL 额外做到的。

### 8.4 MVCC 一句话

**MVCC（多版本并发控制）让"读"不加锁**：每一行数据保留多个历史版本，读操作根据自己的快照去选一个可见的版本，因此读不会被写阻塞，写也不会被读阻塞。这就是"读已提交"和"可重复读"的实现基础。

不展开实现细节，只需要建立这个直觉：**数据库的读性能靠 MVCC，不靠"读的时候没人写"。**

## 九、并发更新：丢失更新与锁

### 9.1 丢失更新是怎么发生的

这是最容易出事、又最难在测试中发现的问题。

```
时刻 1  请求 A 读出 quota.used = 100
时刻 2  请求 B 读出 quota.used = 100
时刻 3  请求 A 写入 used = 100 + 10 = 110
时刻 4  请求 B 写入 used = 100 + 20 = 120    ← A 的 +10 被覆盖，凭空丢失
```

结果应该是 130，实际是 120。**这就是丢失更新。**在 AI 应用里，额度扣减、配额统计、并发计数都是重灾区。

### 9.2 两种解法

**解法一：数据库端原子更新（最简单，优先用）。** 不要"先读后写"，直接把运算写进 `update`：

```sql
update quota set used = used + $1 where user_id = $2;
```

数据库在执行这条语句时会对该行加锁，运算和写入是原子的，不存在中间窗口。

**解法二：乐观锁（适合有业务判断的场景）。** 加一个版本号列：

```sql
update quota
   set used = used + $1, version = version + 1
 where user_id = $2 and version = $3;

-- 返回影响行数 0，说明这一行在你读取之后被别人改过，需要重新读取并重试
```

**解法三：悲观锁（适合冲突频繁、业务逻辑复杂的场景）。**

```sql
select * from quota where user_id = $1 for update;   -- 锁住这一行
-- 期间其他事务对这行的 for update 会阻塞等待
```

| 方案 | 适用 | 代价 |
|------|------|------|
| 原子更新 | 运算能写进 SQL 的场景 | 无，首选 |
| 乐观锁 | 冲突少、需要基于旧值做判断 | 冲突多时重试开销大 |
| 悲观锁 | 冲突频繁、逻辑复杂 | 持锁期间阻塞他人，事务必须短 |

**悲观锁有一个隐藏陷阱**：`for update` 的加锁范围取决于索引。如果 `where` 条件没有走索引，InnoDB 会**锁住扫描过的所有行**，极端情况下等于锁表。所以悲观锁必须配合索引使用。

### 9.3 事务范围的两条铁律

**铁律一：事务里不放网络调用。** 事务持锁期间去等一个模型返回（可能几十秒），会把这行锁住几十秒，高并发下直接雪崩。

**铁律二：事务尽量短。** 事务越长，持锁时间越长，冲突概率越高。把准备工作（参数校验、外部调用、数据拼装）全部移到事务之外，事务里只留真正的写入。

## 十、SQL 的执行过程与执行计划

### 10.1 一条 SQL 走过了什么

```
客户端 → 连接器（认证、权限）
       → 解析器（语法解析，生成语法树）
       → 优化器（选索引、决定 JOIN 顺序）   ← 索引选得好不好在这里决定
       → 执行器（按执行计划调存储引擎取数据）
       → 返回结果
```

**优化器是索引是否生效的决策者**。它基于统计信息估算成本，估算可能出错，所以会出现"明明有索引却没用"的情况，也可能出现反之。统计信息来自数据库的后台采样，可能滞后。

### 10.2 EXPLAIN 怎么看

在 SQL 前加 `EXPLAIN` 可以查看执行计划。只需要关注五个字段：

| 字段 | 看什么 |
|------|--------|
| `type` | 访问类型，**从好到坏**：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。出现 `ALL` 是全表扫描，`index` 是扫整个索引树，两者都需要警觉 |
| `key` | 实际用了哪个索引。为 `NULL` 说明没走索引 |
| `rows` | 预估扫描行数。明显偏大说明索引选择性差或没用上 |
| `filtered` | 过滤后剩余行的百分比。偏低说明扫描了大量无效行 |
| `Extra` | 关键信息，见下表 |

`Extra` 常见取值：

| 值 | 含义 | 好还是坏 |
|----|------|----------|
| `Using index` | 覆盖索引，不需要回表 | 好 |
| `Using index condition` | 索引下推，过滤提前 | 较好 |
| `Using where` | 拿到数据后还要过滤 | 中性 |
| `Using filesort` | 需要额外排序，无法利用索引顺序 | 坏 |
| `Using temporary` | 使用了临时表，常见于 group by / distinct | 坏 |

**审查时的用法**：把 AI 生成的复杂查询拿去过一遍 `EXPLAIN`，看到 `ALL`、`filesort`、`temporary` 就要求它优化。

## 十一、JOIN 与关联查询

| 类型 | 含义 |
|------|------|
| `inner join` | 只保留两边都匹配的行 |
| `left join` | 保留左表全部行，右表没有匹配则填 NULL |
| `right join` | 反之 |

**JOIN 慢的原因**：执行时先选一张表作**驱动表**，然后对它的每一行去另一张表（被驱动表）里找匹配。如果被驱动表的关联列**没有索引**，每次查找都是全表扫描，N 行驱动 × 全表扫描 = 灾难。

**实践结论**：**所有被 JOIN 的关联列都应该有索引。** 这是 JOIN 性能的唯一关键点。其次要注意驱动表尽量小，返回列尽量少。

不过对 AI 应用更实用的建议是：**优先避免 JOIN**。先查出主表数据，再用 `IN` 批量查关联表，在应用层拼装（就是 N+1 的修正写法）。这比让数据库做复杂 JOIN 更好控制和优化。

## 十二、AI 应用的数据分层

### 12.1 四层结构

| 层 | 存什么 | 典型选型 | 关键考量 |
|----|--------|----------|----------|
| 业务元数据 | 用户、配额、渠道、配置 | PostgreSQL / MySQL | 事务与一致性 |
| 会话与消息 | 对话历史、prompt 记录 | 同上，或对象存储归档 | 写入频繁，需要冷热分离 |
| 向量 | embedding 与元数据 | pgvector / Milvus / Qdrant | 索引类型决定召回质量与速度 |
| 文件对象 | 图片、音频、模型文件 | S3 / OSS | 不进数据库，只存引用 |

**一句话判断**：RAG 的召回质量有一半取决于存储与索引设计，不是只由 embedding 模型决定。分块策略、元数据字段、向量索引类型三者共同决定上限。

### 12.2 向量检索与 B+ 树的根本差异

向量检索和普通索引是两个不同的世界，值得单独理解：

| 维度 | B+ 树 | 向量索引 |
|------|-------|----------|
| 查询语义 | 精确匹配、范围、排序 | 找"最相似"的 K 个 |
| 结果 | 精确 | **近似**（ANN，近似最近邻） |
| 能否保证全对 | 能 | 不能，用召回率换速度 |

常见的向量索引类型：

| 类型 | 思路 | 特点 |
|------|------|------|
| 暴力检索 | 逐个算距离 | 100% 召回，但 O(n)，只适合小数据量 |
| HNSW | 构建分层的可导航小世界图，从粗到细逐层搜索 | 查询快、召回高，内存占用大 |
| IVF | 先聚类，查询时只搜最近的几个簇 | 省内存，召回略低，需要调参 |

距离度量通常用余弦相似度、内积或欧氏距离，**必须与 embedding 模型训练时使用的度量一致**，否则召回质量会莫名下降。

**审查要点**：涉及向量检索时，要确认三件事——索引类型是否明确、距离度量是否与模型匹配、以及"近似检索"这个前提是否被业务感知（不能让业务以为结果是精确的）。

## 十三、New API 中的落点

| 概念 | 落点 |
|------|------|
| 核心数据模型 | USER（quota）、TOKEN（key / status / quota）、CHANNEL（models / weight）、ABILITY、LOG |
| 主键设计 | 用户、令牌、渠道均使用业务内唯一的 key 或 ID，而非纯自增 |
| 唯一索引 | 令牌校验走 `key` 字段查找，是典型的唯一索引命中场景，O(log n) 定位 |
| 日志库分离 | `LOG_SQL_DSN` 把日志写入独立库，避免日志的高频写入拖垮主库，也避免索引维护开销影响业务表 |
| 事务边界 | 额度扣减走数据库端原子更新，与写日志分离，避免长事务 |
| 连接池 | `SQL_MAX_OPEN_CONNS`、`SQL_MAX_IDLE_CONNS`（属板块 02） |
| Schema 管理 | `model.InitDB` 与 `model.InitLogDB` 执行自动迁移 |
| 多数据库支持 | 同一套 GORM 模型适配 SQLite / MySQL / PostgreSQL |

`ABILITY` 表值得单独看：它是渠道与模型的能力关联表，把"哪个渠道支持哪个模型"从渠道表里的嵌套结构（如 JSON 数组）拆成扁平行。这是**用冗余换查询效率**的典型设计——反范式的一种形式。原来的写法（在渠道表存一个模型数组）无法被索引，拆成扁平行之后"查某个模型有哪些可用渠道"就变成了一个带索引的等值查询。

## 十四、典型误写与修正

### 14.1 N+1 查询

误写方向：查出一批主记录后，在循环里逐条查关联表。10 条订单变成 11 次数据库往返。

```python
orders = await db.fetch_all("select * from orders where user_id = $1", uid)
for o in orders:
    o["items"] = await db.fetch_all(
        "select * from order_items where order_id = $1", o["id"])   # 循环内查库
```

修正：一次批量查出再用 `IN` 取回，在内存里分组。

```python
orders = await db.fetch_all("select * from orders where user_id = $1", uid)
ids = [o["id"] for o in orders]
items = await db.fetch_all(
    "select * from order_items where order_id = any($1)", ids)      # 一次往返
grouped = {}
for it in items:
    grouped.setdefault(it["order_id"], []).append(it)
for o in orders:
    o["items"] = grouped.get(o["id"], [])
```

### 14.2 事务范围包含网络调用

误写方向：事务里等模型返回，事务期间一直占着数据库连接和行锁。

```python
async with db.transaction():
    await db.execute("update quota set used = used + $1 where user_id = $2", cost, uid)
    resp = await call_llm(prompt)               # 网络调用在事务内，持锁等几十秒
    await db.execute("insert into messages (content) values ($1)", resp.text)
```

修正：网络调用放在事务外，事务只包住真正的写入。

```python
resp = await call_llm(prompt)                   # 先算
async with db.transaction():                    # 再写，事务范围最小
    await db.execute("update quota set used = used + $1 where user_id = $2", cost, uid)
    await db.execute("insert into messages (content) values ($1)", resp.text)
```

### 14.3 先读后写导致丢失更新

误写方向：把"读出来、加一下、写回去"拆成两个语句。并发下后写入的会覆盖先写入的。

```python
row = await db.fetch_one("select used from quota where user_id = $1", uid)
new_used = row["used"] + cost
await db.execute("update quota set used = $1 where user_id = $2", new_used, uid)
```

修正：把运算交给数据库，一条语句完成，由数据库保证原子性。

```python
await db.execute(
    "update quota set used = used + $1 where user_id = $2", cost, uid)

# 如果需要基于旧值做业务判断，用版本号做乐观锁
affected = await db.execute(
    "update quota set used = used + $1, version = version + 1 "
    "where user_id = $2 and version = $3", cost, uid, expect_version)
if affected == 0:
    raise Conflict("配额已被其他请求修改，请重试")
```

### 14.4 索引列上套函数或隐式类型转换

误写方向：`created_at` 上有索引，但对列做函数运算后索引失效，退化为全表扫描。

```sql
select * from logs where date(created_at) = '2026-09-28';
select * from tokens where token = 12345678;      -- token 是 varchar，与数字比较
```

修正：改写成范围条件；字符串列与字符串比较。

```sql
select * from logs
 where created_at >= '2026-09-28 00:00:00'
   and created_at <  '2026-09-29 00:00:00';

select * from tokens where token = '12345678';
```

### 14.5 前导通配的模糊查询

误写方向：`like '%关键词'` 无法按前缀定位，索引完全用不上。

```sql
select * from documents where title like '%连接池%';
```

修正：能改后缀匹配就改（可用索引）；确实需要全文检索时换专用方案。

```sql
-- 后缀匹配，索引可用
select * from documents where title like '连接池%';

-- 真需要中间匹配，用全文索引或搜索引擎
-- PostgreSQL：to_tsvector + GIN 索引
-- 通用方案：Elasticsearch / OpenSearch
```

### 14.6 深分页

误写方向：`offset` 很大时，数据库必须先扫描并丢弃前 N 行才能拿到目标行。

```sql
-- 需要先扫出 100000 行再丢掉，越翻越慢
select * from messages where user_id = 1
 order by id desc limit 10 offset 100000;
```

修正：用游标（基于上一页最后一条的排序键）翻页，扫描量与页码无关。

```sql
-- 记住上一页最后一条的 id，直接定位
select * from messages where user_id = 1 and id < 123456
 order by id desc limit 10;
```

配套条件是 `(user_id, id)` 上要有联合索引。**审查时看到 `offset` 后面跟着很大的数字，就该要求改成游标分页。**

### 14.7 用浮点类型存金额

误写方向：`float` / `double` 是二进制浮点，无法精确表示 0.1 这类十进制小数，累计计算会出现分位误差。

```sql
create table billing (
    amount float          -- 累加 100 次 0.1 可能得到 9.999999999998
);
```

修正：金额一律用定点类型，并在应用层用对应的十进制类型。

```sql
create table billing (
    amount numeric(12, 4) not null      -- PostgreSQL
    -- MySQL：decimal(12, 4)
);
```

```python
from decimal import Decimal
amount = Decimal("0.1")                 # 不要用 float
```

### 14.8 缺唯一约束，靠应用层防重复

误写方向：应用层"先查再插"有并发窗口，两个请求可能同时通过检查，产生重复数据。

```python
if not await db.fetch_one("select 1 from users where email = $1", email):
    await db.execute("insert into users (email) values ($1)", email)
```

修正：把唯一性交给数据库，捕获冲突异常。

```sql
create unique index uk_users_email on users (email);
```

```python
try:
    await db.execute("insert into users (email) values ($1)", email)
except UniqueViolationError:
    raise Conflict("邮箱已注册")
```

## 十五、审查红灯信号

看到以下写法时应停下来确认：

**表设计方面**

- 主键用长字符串（如 36 字节的 UUID 字符串），会撑大所有二级索引。
- 用 `float` / `double` 存金额。
- 用字符串存时间，或时间不统一存 UTC。
- 把可变长、无上限的字段（如整段对话历史 JSON）和需要频繁筛选的字段放在同一张表。
- 需要唯一性的字段没有唯一约束，靠应用层判断防重复。

**索引方面**

- 在循环体内调用数据库查询，形成 N+1。
- 对索引列套函数，或字符串列与数字隐式比较。
- 使用前导通配的模糊匹配。
- 联合索引的列顺序与真实查询条件不匹配（范围条件排在了等值条件前面）。
- 只建了索引，但 `select` 用了 `select *`，导致覆盖索引失效且大量回表。
- 选择性极低的列（如状态、性别）单独建索引。
- 写入密集的表上堆了很多索引。

**事务方面**

- 事务块里包含 HTTP 请求或模型调用。
- 先读后写做运算，而不是在 SQL 里原子更新。
- `for update` 的 `where` 条件没有走索引（会退化为锁大量行甚至锁表）。
- 事务里做参数校验、数据拼装等本可前置的工作。

**查询方面**

- 列表接口没有分页上限，返回全量数据。
- `offset` 后面跟着很大的数字（深分页）。
- 复杂查询没有过 `EXPLAIN`。
- 被 JOIN 的关联列没有索引。

## 十六、判断阈值

达到以下程度即可认为该板块够用：

**能解释原理，而不只是背结论**

- 能说清为什么索引快（页 + 排序 + 二分 + 树矮），以及全表扫描为什么慢。
- 能说清最左前缀是怎么从联合索引的排序规则推出来的，而不是背"必须从第一列开始"。
- 能说清回表是什么、覆盖索引为什么能避免回表、为什么不要用 `select *`。
- 能说清自增主键为什么对写入友好（顺序插入 vs 页分裂）。

**能审查具体设计**

- 看到建表语句，能判断主键选择、类型选择、是否缺约束。
- 看到查询代码，能识别是否会走索引、是否存在 N+1、是否需要覆盖索引。
- 看到事务代码，能判断事务范围是否过大、是否需要加锁、是否会丢失更新。
- 看到分页代码，能识别是否存在深分页问题。

**能写出准确约束**

- 能在 prompt 中写出"为 `(user_id, created_at)` 建联合索引，等值列在前、范围列在后，并按 `created_at` 倒序用游标分页"这类可执行的约束。
- 能要求 AI"不要用 `select *`，只列出实际需要的列，让查询走覆盖索引"。
- 能要求 AI"额度扣减必须用数据库端原子更新，禁止先读后写"。
