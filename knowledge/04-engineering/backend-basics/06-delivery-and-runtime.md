# 板块 06：交付与运行

**核心思想**：交付环节的核心是"配置与代码分离"和"密钥不进仓库"。这一板块不需要深挖，达到能审查的水平即可。

上级索引：[AI 应用后端知识地图](./00-overview.md)

## 一、容器的基础认识

| 概念 | 要点 |
|------|------|
| 镜像与容器 | 镜像是只读模板，容器是镜像的运行实例，写操作在可写层 |
| 分层的意义 | 每一层单独缓存，把变动少的内容（依赖）放前面、变动多的（业务代码）放后面，重建才快 |
| 数据持久化 | 容器内写入在重建后丢失，数据必须挂载到卷或外部存储 |
| 端口映射 | 容器内监听端口与宿主机端口是两回事，需显式映射 |
| 环境变量注入 | 这是配置进入容器的主要方式 |

**最常见的部署事故**：数据库文件写在容器内部而没挂载出来，容器重建后数据全部丢失。审查部署配置时，第一件事就是确认有持久化挂载。

## 二、配置与密钥管理

**十二要素应用的核心几条**：

| 原则 | 含义 | 违反的表现 |
|------|------|------------|
| 配置与代码分离 | 环境相关的参数通过环境变量注入 | 数据库地址硬编码在代码里 |
| 无状态进程 | 进程内不保存需长期保留的状态 | 见板块 04 |
| 日志作为事件流 | 输出到标准输出，由外部收集 | 自己按日期写文件并管理轮转 |
| 开发与生产一致 | 环境差异尽量小 | 本地 SQLite、生产 PostgreSQL，行为不一致 |

**密钥管理的三条底线**：

1. **密钥不进仓库**。包括不以明文写入配置文件后提交。
2. **密钥不写进日志**。请求日志、异常堆栈里出现完整密钥是常见疏漏，需要显式脱敏。
3. **密钥有独立的作用域与轮换路径**。上游密钥泄露时应能单独作废，不影响其他部分。

**为配置项提供安全默认值**：不安全的默认值（如默认空密码、默认允许所有来源）在生产环境会成为漏洞。审查时应确认默认值是否安全。

## 三、编排与多机部署

编排工具解决的是"多个服务如何一起启动、依赖顺序如何保证、配置如何分发"。

| 关注点 | 说明 |
|--------|------|
| 依赖顺序 | 应用应在数据库与缓存就绪后再启动，通常通过健康检查与重试等待实现 |
| 数据卷 | 数据库与缓存的数据目录必须持久化 |
| 网络 | 服务间的访问地址在编排环境内使用服务名而非 IP |
| 密钥注入 | 通过环境变量文件或密钥管理服务注入，文件本身不提交 |
| 数据库独立 | 数据库通常不应与应用容器放在同一编排生命周期内 |

**多机部署的四个必要动作**：

1. 所有节点共享同一套会话与加密密钥，否则登录态与密文无法跨节点使用。
2. 所有节点共享同一套外部状态存储（Redis），否则限流、缓存各自为政。
3. 后台定时任务只在一个节点执行，其余节点关闭该角色。
4. 反向代理要正确传递真实客户端地址，并配置可信代理来源。

**升级与回滚**：确认数据库迁移是否向后兼容（新版本写入的数据，旧版本能否读取）。如果迁移不可逆，回滚就必须依赖数据备份。上线前先备份数据库，是成本最低的保险。

## 四、New API 中的落点

| 概念 | 落点 |
|------|------|
| 编排 | 仓库内的 `docker-compose.yml` 默认启动 new-api + PostgreSQL + Redis 三个服务，另有 MySQL 与 ClickHouse 日志库的示例 |
| 持久化 | Docker 部署必须挂载 `/data` 目录，否则 SQLite 数据库与配置随容器消失 |
| 配置注入 | `.env.example` 作为环境变量模板，`.env` 不提交 |
| 密钥生成 | 文档明确要求用 `openssl rand -hex 32` 生成随机的 `SESSION_SECRET` 并持久保存 |
| 多机密钥一致 | 文档明确写出：多机部署必须设置 `SESSION_SECRET`，共享 Redis 时必须设置 `CRYPTO_SECRET` |
| 多节点角色 | `NODE_TYPE=slave` 关闭仅主节点运行的后台任务 |
| 可信代理 | `TRUSTED_PROXIES` 配置反向代理的 IP 或网段，另有 `none` 选项 |
| HTTPS 下的 Cookie 安全 | `SESSION_COOKIE_SECURE` 与 `SESSION_COOKIE_TRUSTED_URL` 配合使用 |
| 镜像与架构 | 官方镜像同时提供 amd64 与 arm64，CI 中用 cosign 做签名 |
| 供应链安全 | 文档建议固定镜像版本而非使用 latest，升级前备份 |

**文档里的三处提示值得单独记下**，因为它们就是本板块的核心结论：

第一，"复制 `.env.example` 不会自动把变量注入容器，必须在编排配置里显式设置"。这是配置注入最常见的误解。

第二，"最新标签会随发布变化，升级前必须评估迁移与兼容性并备份"。这是版本固定与回滚意识的直接体现。

第三，"未配置共享 Redis 时，各节点的限流器独立计数"。架构限制被写在文档里，而不是留给使用者踩坑。

## 五、典型误写与修正

### 密钥硬编码在代码里

误写方向：密钥进入 Git 历史后就永久留在那里，即使后续删除也仍在历史提交中。上游密钥泄露时也无法单独作废。

```python
DB_DSN = "postgres://admin:P@ssw0rd@10.1.2.3:5432/app"
OPENAI_KEY = "sk-xxxxxxxxxxxxxxxx"
```

修正：从环境变量读取，缺失即启动失败。启动失败好过带着错误配置静默运行。

```python
DB_DSN = os.environ["DB_DSN"]                       # 缺失直接抛 KeyError
OPENAI_KEY = os.environ["OPENAI_API_KEY"]
```

同时要确保日志与异常堆栈里的密钥经过脱敏，否则等于换个位置泄露。

### 部署配置缺少持久化与依赖就绪判断

误写方向：数据库文件写在容器内部，容器重建即数据全丢；应用比数据库先启动，靠反复重启碰运气。

```yaml
services:
  app:
    image: myapp:latest                             # 浮动标签，升级不可控
    environment:
      DB_DSN: postgres://app:pw@postgres:5432/app
  postgres:
    image: postgres:16                              # 数据在容器内，重建即丢
```

修正：固定版本、外置配置、挂载持久化卷、显式声明依赖就绪条件。

```yaml
services:
  app:
    image: myapp:1.4.2                              # 固定版本，升级可控
    env_file: .env                                  # 配置与密钥外置，.env 不提交
    volumes:
      - ./data:/data                                # 应用自身数据持久化
    depends_on:
      postgres:
        condition: service_healthy                  # 等依赖就绪再启动
  postgres:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data             # 数据库数据持久化
volumes:
  pgdata:
```

### 多机部署未统一密钥

误写方向：各节点使用不同的默认密钥，表现为登录状态随机失效、共享缓存中的密文无法解密。

```bash
# 各节点各自生成，互不一致
SESSION_SECRET=
```

修正：显式生成一次随机密钥，持久保存，所有节点使用同一值。

```bash
openssl rand -hex 32        # 生成一次
# 写入统一的密钥管理位置，各节点注入同一值
```

同时，后台定时任务需要通过角色配置只在单一节点执行，否则每个节点都会跑一遍。

## 六、审查红灯信号

- `.env` 或含明文密钥的配置文件被提交进仓库。
- 容器部署但数据库或缓存目录没有挂载持久化。
- 启动时没有任何等待依赖就绪的机制，靠重启碰运气。
- 使用 latest 或浮动标签部署生产环境。
- 镜像把密钥在构建时烘焙进去，运行期无法更换。
- 配置项存在不安全的默认值，且文档未提示。
- 日志中可能打印完整密钥或令牌，没有脱敏。
- 多机部署未统一会话与加密密钥。
- 没有回滚方案，或数据库迁移不可逆但无备份流程。

## 七、判断阈值

- 能判断一份部署配置是否会丢失数据。
- 能确认配置与密钥是否与代码分离、是否进过仓库。
- 能说清多机部署需要统一哪些参数。
- 能判断升级是否有回滚路径。
