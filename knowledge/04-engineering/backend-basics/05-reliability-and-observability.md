# 板块 05：可靠性与可观测

**核心思想**：可靠性要回答的是"依赖出问题时，服务会不会整体垮掉"；可观测要回答的是"出问题时，能不能在几分钟内定位到原因"。前者靠主动防御，后者靠数据留存。

上级索引：[AI 应用后端知识地图](./00-overview.md)

## 一、五种防御手段

| 手段 | 做什么 | 缺失后果 |
|------|--------|----------|
| 超时 | 给每次外部调用设时间上限 | 慢依赖拖垮自身，连接被占满 |
| 重试 | 对可恢复的失败再试 | 偶发抖动放大为业务失败 |
| 熔断 | 失败率超阈值后直接拒绝调用，过一段时间再放行探测 | 持续向已故障的依赖发请求，白白消耗资源 |
| 降级 | 依赖不可用时返回降级结果 | 一个非核心依赖挂掉导致整个功能不可用 |
| 背压 | 队列或并发超限时主动拒绝新请求 | 请求无限堆积，最终内存耗尽 |

**熔断与重试的关系**：重试是"再试一次"，熔断是"暂时别试了"。二者配合使用。如果只有重试没有熔断，上游持续故障时会形成重试风暴。

**降级的设计要点**：需要在设计阶段就明确"哪些能力可以降级"。例如缓存不可用时直接查数据库、模型调用失败时返回预设兜底文案。降级逻辑要在代码里显式存在，而不是靠异常兜底。

**背压是最后一道防线**：当队列长度或并发数超过上限时，应当快速失败并返回明确的错误码，而不是继续接收。让请求在入口被拒绝，好过让服务在内部被压垮。

## 二、幂等：重试的前提

任何允许重试的操作都必须是幂等的，否则会把一次失败变成两次写入。

三种实现思路：

| 思路 | 做法 | 适用 |
|------|------|------|
| 唯一约束 | 数据库层面加唯一索引，重复插入直接失败 | 创建类操作 |
| 幂等键 | 客户端携带请求 ID，服务端记录处理结果 | 扣费、下单 |
| 状态机 | 仅允许特定状态流转，重复流转无效果 | 订单、任务状态变更 |

## 三、可观测三支柱

| 支柱 | 回答什么问题 | 关键要求 |
|------|--------------|----------|
| 日志 | 这一次请求发生了什么 | 结构化，带请求 ID，能串起整条链路 |
| 指标 | 整体健康度如何 | 有基线与告警阈值，能看时间趋势 |
| 链路追踪 | 请求在各服务间怎么走、哪里慢 | 跨服务传递 trace ID |

**日志的最低要求是能串联**：同一次请求在网关、服务、数据库各层的日志，必须带同一个请求 ID。否则并发场景下日志互相交错，无法阅读。这需要请求 ID 从入口生成并逐层透传。

**必须监控的几个指标**：

| 指标 | 含义 | 为什么重要 |
|------|------|------------|
| QPS | 每秒请求数 | 判断负载与容量 |
| P99 延迟 | 99% 请求的耗时上限 | 平均值会掩盖长尾，长尾才是用户体感 |
| 错误率 | 失败请求占比 | 最直接的告警指标 |
| 队列积压 | 待处理任务数 | 异步系统过载的最早信号 |
| 连接池使用率 | 已用连接占池大小的比例 | 池是否成为瓶颈 |

**健康检查要区分两类**：存活检查（进程是否还在）和就绪检查（是否能正常处理请求）。混为一谈会导致依赖短暂不可用时容器被反复重启。

**优雅关闭**：收到终止信号后，先停止接收新请求，等待正在处理的请求完成，再退出。否则滚动发布时会有请求被直接切断。

## 四、AI 应用特有的观测指标

在通用指标之外，AI 应用还需要关注：

| 指标 | 用途 |
|------|------|
| Token 消耗量与成本 | 成本控制与预算告警 |
| 模型调用成功率与失败原因分布 | 区分限流、超时、上游错误 |
| 首字延迟 | 流式体验的核心指标，与总时长分开看 |
| 缓存命中率 | 提示缓存是否生效，直接影响成本 |
| 单次请求的模型调用轮次 | Agent 场景下判断是否陷入无效循环 |

Token 与成本的度量还有一个额外用途：它是 AI 生产力指标采集的基础数据。网关层是这类数据最完整的采集点，因为所有请求都必经此处。

## 五、New API 中的落点

| 概念 | 落点 |
|------|------|
| 重试 | 运营设置中可配置渠道重试次数 |
| 健康检查 | `controller.AutomaticallyTestChannels` 定时自动测试渠道可用性 |
| 故障转移 | 渠道测试失败或调用失败时，可在其他可用渠道间切换 |
| 负载均衡 | 渠道加权随机，配合可用性筛选 |
| 日志存储 | 独立日志库 `LOG_SQL_DSN`，支持 ClickHouse，避免拖累主库 |
| 错误日志开关 | `ERROR_LOG_ENABLED` 控制错误日志是否记录与展示 |
| 性能剖析 | Pyroscope 持续性能分析，以及 pprof 接口 |
| 限流与告警 | 三层限流，另有通知频率限制 `NOTIFY_LIMIT_COUNT` 与 `NOTIFICATION_LIMIT_DURATION_MINUTE` |
| 后台维护 | 订阅额度重置、渠道测试等定时任务 |
| 多节点角色 | `NODE_TYPE=slave` 避免后台任务重复执行 |

**渠道自动测试**是这里最值得借鉴的设计：把"依赖是否健康"做成后台持续探测，而不是等请求失败才发现。这样上游异常时，流量可以在用户无感知的情况下切走。

**通知限流**也值得注意：告警本身也需要限流，否则上游持续故障会触发海量告警通知，造成二次伤害。

## 六、典型误写与修正

### 外部调用不设超时

误写方向：下游挂死时调用方会永久阻塞。Python 的 `requests` 默认无超时，这是最容易忽略的一个默认值。

```python
resp = requests.get(UPSTREAM)                       # 默认无超时，永久阻塞
```

修正：连接与读取分别设超时，且读取超时才是长调用场景的关键。

```python
resp = requests.get(UPSTREAM, timeout=(5, 60))      # (连接超时, 读取超时)

# httpx 的等价写法
timeout = httpx.Timeout(60, connect=5)
async with httpx.AsyncClient(timeout=timeout) as c:
    ...
```

超时还要满足收敛关系：外层必须大于内层，否则外层先断、内层白干。同时重试预算要满足 `重试次数 × 单次超时 + 退避时间 < 外层超时`。

### 对非幂等操作自动重试

误写方向：一次超时重试变成两次扣费。重试的前提是操作幂等。

```python
@retry(times=3)
async def charge(uid, amount):
    return await pay_api.charge(uid, amount)        # 超时后重试，可能扣两次
```

修正：只对可安全重试的异常重试，写操作必须携带幂等键。

```python
@retry(times=3, only_on=(ConnectError, TimeoutError))
async def charge(uid, amount, idem_key):
    return await pay_api.charge(uid, amount, idempotency_key=idem_key)
```

### 队列无上限、无背压

误写方向：入队不做任何检查，请求持续堆积直到内存耗尽，服务彻底不可用。

```python
await queue.put(task)                               # 无上限，堆到内存爆掉
```

修正：超过积压上限时快速失败，返回明确状态码，让入口承担拒绝责任。

```python
if await queue.size() > MAX_BACKLOG:
    raise HTTPException(status_code=503, detail="服务繁忙，请稍后重试")
await queue.put(task)
```

### 只上报平均值指标

误写方向：平均值会掩盖长尾，而长尾才是用户体感。十个正常请求加一个卡死请求，平均值可能看不出异常。

```python
metrics.gauge("latency_avg", total_time / count)    # 只有平均值
```

修正：用直方图上报，从而可计算 P50/P95/P99，并对 P99 单独告警。

```python
hist.labels(route=route).observe(elapsed)           # 直方图，可算出各分位
```

### 告警本身没有频率限制

误写方向：上游持续故障时触发海量告警通知，把值班人员淹没，形成二次伤害。

```python
if err:
    await notify.send(f"调用失败: {err}")            # 每次失败都发
```

修正：同一告警源在时间窗内只发一次，或限制单位时间内的通知总数。

```python
if await redis.set(f"alert:{key}", "1", nx=True, ex=600):   # 10 分钟内只发一次
    await notify.send(f"调用失败: {err}")
```

## 七、审查红灯信号

- 外部调用没有超时参数。
- 有重试但没有熔断，或重试没有次数上限与退避。
- 对非幂等操作的失败进行自动重试。
- 队列没有长度上限，也没有背压策略。
- 日志是纯文本拼接，不带请求 ID，无法串联。
- 只监控平均值延迟，没有 P99。
- 只做存活检查，依赖不可用时会触发容器反复重启。
- 没有优雅关闭，发布时直接切断在途请求。
- AI 应用没有 token 与成本指标，也没有区分首字延迟与总时长。
- 告警没有频率限制。

## 八、判断阈值

- 能列出一次外部调用应当配备的全部防护参数。
- 能判断一次重试是否安全，是否需要幂等键。
- 能说清某个依赖挂掉时服务会如何表现，是否有降级路径。
- 能判断现有日志能否定位到具体一次请求的完整链路。
- 能说出 AI 应用相比普通服务需要额外监控哪些指标。
