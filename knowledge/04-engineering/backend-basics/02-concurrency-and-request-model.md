# 板块 02：并发与请求模型

**核心思想**：并发的核心不是"会写多线程"，而是认清 IO 密集与 CPU 密集的区别，以及协程的传染性。AI 生成后端起服务时，最高频的事故是把同步阻塞函数混进异步服务，把整个事件循环卡住。

上级索引：[AI 应用后端知识地图](./00-overview.md)

这是六个板块中最值钱的一块，也是本套笔记第一个该看的。

## 一、三种并发模型

| 模型 | 切换开销 | 内存占用 | 适用负载 |
|------|----------|----------|----------|
| 进程 | 最大 | 最大，隔离性最好 | CPU 密集，需要隔离 |
| 线程 | 中等 | 约 MB 级栈 | 混合，受 GIL 或锁限制 |
| 协程 | 最小 | KB 级 | IO 密集，即绝大多数后端服务 |

判断负载类型的方法：任务大部分时间在等外部返回（数据库、模型、网络）就是 IO 密集；任务大部分时间在算（加解密、图像处理、向量计算）就是 CPU 密集。后端服务绝大多数是 IO 密集。

实践结论：**IO 密集用协程，CPU 密集交给独立进程或任务队列**。不要在协程服务里做重计算，那会阻塞其他所有请求。

## 二、协程的传染性

这是本板块最需要建立的直觉。

在 Python 的 asyncio 里，事件循环是单线程的。任何一处同步阻塞调用，会让整个循环停住，所有其他并发请求一起被拖死。常见的阻塞源：

- 同步的数据库驱动或 HTTP 客户端。
- `time.sleep` 而不是 `asyncio.sleep`。
- 同步的文件读写。
- CPU 密集的循环或大 JSON 序列化。

因此异步是**会传染的**：一旦服务入口是 `async`，调用链上每一层都必须是异步的。判断 AI 生成的代码是否正确，就看这条链有没有被同步函数打断。

Go 的模型不同：goroutine 由运行时调度，遇到阻塞的系统调用时运行时会挂起该 goroutine 并调度其他任务，不存在"一处阻塞全体停摆"的问题。这是 New API 选 Go 的底层原因之一。但 Go 里仍要避免无限制创建 goroutine，以及共享状态的竞态。

## 三、连接池

**为什么需要**：建立一个数据库连接需要 TCP 握手、认证、会话初始化，成本是毫秒级。每个请求新建连接，会在高并发下把时间全花在建连上，同时迅速打满数据库的 `max_connections` 上限。

**连接池的两个核心参数**：

| 参数 | 含义 | 设错的后果 |
|------|------|------------|
| 最大连接数 | 池内允许同时打开的连接上限 | 设太大打满数据库，设太小请求排队 |
| 最大空闲连接数 | 保持空闲不被回收的连接数 | 设太小则频繁重建，设太大则占资源 |

**池大小的判断逻辑**：池的上限应当匹配服务的实际并发能力。如果池只有 10 个连接，却有 100 个并发请求，多出来的 90 个全部在等池，此时瓶颈在池而不在数据库。反过来把池调到 500，数据库侧会被打爆。

**两个必须知道的坑**：

- 池要设置**获取连接的超时**。否则池耗尽时请求会无限等待，表现为服务整体挂住但没有任何错误日志。
- 池要设置**连接最大存活时间**，避免使用已被数据库或中间网络设备单方面关闭的连接。

## 四、并发控制四件套

调用外部服务（尤其是模型接口）时，必须有这四样：

| 手段 | 作用 | 缺失后果 |
|------|------|----------|
| 信号量 | 限制同时在飞的请求数 | 无限并发把上游打限流 |
| 令牌桶限流 | 限制单位时间内的请求数 | 超出配额，被上游封禁 |
| 超时 | 给每次调用设上限 | 慢请求堆积，连接与线程被占满 |
| 指数退避重试 | 失败后按倍数延长间隔重试 | 上游抖动时重试风暴，雪上加霜 |

**重试的边界**：只对幂等操作重试。写操作重试必须配合幂等键，否则会产生重复数据。重试次数要有上限，并配合抖动，避免所有客户端同时重试。

## 五、长任务异步化

**判断标准**：一个请求的处理时间超过几秒，就不应该占用 HTTP 连接同步返回。

Agent 类应用是典型场景。一次 agent 执行可能跑几分钟，包含多轮模型调用和工具调用，同步等待会同时消耗掉客户端连接、服务端协程、以及上游的连接配额。正确做法是：

1. 接口立即返回一个任务 ID。
2. 任务扔进队列，由独立 worker 消费。
3. 客户端用任务 ID 轮询结果，或通过 SSE 接收进度。

**队列要解决的三个问题**：任务堆积时如何限流、worker 崩溃时任务如何恢复、同一任务重复入队时如何幂等。选型上 Celery 功能最全但重，arq 与 RQ 更轻。

## 六、流式响应

大模型场景下流式是默认要求，因为首字延迟直接决定体验。

| 方案 | 特点 | 适用 |
|------|------|------|
| SSE | 单向、基于 HTTP、自动重连 | 模型流式输出，主流选择 |
| WebSocket | 双向、全双工 | 需要客户端持续上行，如实时语音 |

**流式引入的三个新问题**：

- **上游超时判断要改**。不能只看总时长，要看"多久没有收到新数据块"。上游还活着但一直不吐字，和上游已断开，是两种不同的故障。
- **扫描缓冲要有上限**。SSE 逐块读取时需要缓冲区，若单块数据异常巨大而不设上限，会直接吃掉内存。
- **连接断开要能续传**。客户端断线后，服务端要知道任务继续还是终止，已生成的部分如何保留。

## 七、New API 中的落点

| 概念 | 落点 |
|------|------|
| 数据库连接池 | `SQL_MAX_IDLE_CONNS`、`SQL_MAX_OPEN_CONNS` 两个环境变量直接控制池参数 |
| 并发模型 | Go 的 goroutine，每个中继请求独立协程，阻塞系统调用不拖累全局 |
| 上游超时 | `RELAY_TIMEOUT` 控制上游请求的总体超时 |
| 流式超时 | `STREAMING_TIMEOUT` 控制 SSE 流多久没收到数据块才算超时，与上一条是两个不同维度 |
| 请求体保护 | `MAX_REQUEST_BODY_MB` 限制请求体大小，防止超大请求打爆内存 |
| 流式缓冲保护 | `STREAM_SCANNER_MAX_BUFFER_MB` 限制 SSE 扫描缓冲区上限 |
| 限流 | `middleware/rate-limit.go` 实现 API / Web / Critical 三层限流，且可选用 Redis 或内存存储 |
| 重试 | 运营设置中的渠道重试次数 |
| 长任务 | 异步任务适配器（`service.GetTaskAdaptorFunc`）处理图片、视频等耗时任务 |

这里最值得细看的是**超时被拆成两个**：`RELAY_TIMEOUT` 管总体，`STREAMING_TIMEOUT` 管流式间隙。这个拆分本身就说明了流式场景下超时语义的不同，是很好的设计参考。

另外注意 `MAX_REQUEST_BODY_MB` 与 `STREAM_SCANNER_MAX_BUFFER_MB` 这一对：前者防入口，后者防出口，但思路一致——**凡是长度由外部决定的地方，都必须设上限**。

## 八、典型误写与修正

### 同步阻塞调用进入异步服务

误写方向：这是异步服务里最严重的写法，一处阻塞会让所有并发请求一起停摆。

```python
async def get_answer(q: str):
    time.sleep(1)                                   # 阻塞整个事件循环
    r = requests.get(UPSTREAM, params={"q": q})     # 同步 HTTP 客户端
    return r.json()
```

修正：整条调用链都必须是异步的，不能中途出现同步函数。

```python
async def get_answer(q: str):
    await asyncio.sleep(1)                          # 让出控制权
    async with httpx.AsyncClient(timeout=60) as c:  # 异步客户端
        r = await c.get(UPSTREAM, params={"q": q})
    return r.json()
```

### 每个请求新建数据库连接

误写方向：建连包含 TCP 握手、认证、会话初始化，高并发下时间全花在建连上，同时迅速打满数据库连接上限。

```python
async def query(sql):
    conn = await asyncpg.connect(DSN)               # 每次请求建连
    try:
        return await conn.fetch(sql)
    finally:
        await conn.close()
```

修正：全应用共用一个连接池，并显式设置获取超时与连接存活上限。

```python
pool = await asyncpg.create_pool(
    DSN,
    min_size=5,
    max_size=20,                                    # 与并发能力匹配
    timeout=5,                                      # 池耗尽时快速失败，不无限等待
    max_inactive_connection_lifetime=300,           # 避免用到已被关闭的连接
)

async def query(sql):
    async with pool.acquire() as conn:
        return await conn.fetch(sql)
```

### 无并发上限地调用模型

误写方向：把所有请求一次性打给上游，触发限流甚至封禁，且没有退路。

```python
tasks = [call_llm(p) for p in prompts]              # 1000 个同时在飞
await asyncio.gather(*tasks)
```

修正：用信号量限制在飞请求数，并给每次调用加超时。

```python
sem = asyncio.Semaphore(10)                         # 并发上限

async def guarded(p):
    async with sem:
        return await call_llm(p, timeout=60)

results = await asyncio.gather(*[guarded(p) for p in prompts])
```

### 长任务同步返回

误写方向：agent 跑几分钟，期间 HTTP 连接、服务端协程、上游连接配额全部被占住。

```python
@app.post("/agent/run")
async def run(body: TaskIn):
    return await run_agent(body)                    # 阻塞数分钟
```

修正：立即返回任务 ID，执行交给队列，客户端轮询或订阅进度。

```python
@app.post("/agent/run", status_code=202)
async def run(body: TaskIn):
    task_id = await queue.enqueue("run_agent", body.model_dump())
    return {"task_id": task_id, "status": "pending"}
```

### 流式接口用总时长判断超时

误写方向：上游仍在正常吐字，却因为总时长超过阈值被切断。

```python
resp = await client.get(url, timeout=60)            # 总时长超时，长输出必被切
```

修正：区分总时长与数据块间隙，流式场景以后者为主。

```python
timeout = httpx.Timeout(None, connect=5, read=30)   # read 计量两次读之间的间隔
async with client.stream("GET", url, timeout=timeout) as resp:
    async for chunk in resp.aiter_bytes():
        ...
```

## 九、审查红灯信号

- 异步服务的调用链里出现同步阻塞函数、`time.sleep` 或同步 HTTP 客户端。
- 每个请求都新建数据库连接或模型客户端，没有复用池。
- 连接池没有获取超时，或池大小与并发量明显不匹配。
- 模型调用没有超时参数，或超时设得极大。
- 失败重试没有次数上限、没有退避、或对非幂等写操作重试。
- 长耗时任务直接同步返回，占着 HTTP 连接不放。
- 流式接口用总时长判断超时，而不是用数据块间隔。
- 无限制地并发发起模型调用，没有信号量或并发上限。
- 协程或 goroutine 无限制创建。

## 十、判断阈值

- 能指出一段异步代码中哪一处会阻塞事件循环。
- 能根据并发量估算连接池大小是否合理，并说出池耗尽时的表现。
- 能判断一次模型调用需要配哪些控制参数（并发上限、超时、重试、退避）。
- 能判断一个接口应该同步返回还是走任务队列。
- 能在 prompt 中写出"为模型调用加并发上限 10、超时 60 秒、指数退避重试 3 次且仅对幂等操作重试"这类约束。
