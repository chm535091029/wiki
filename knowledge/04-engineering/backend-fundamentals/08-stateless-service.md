# 无状态服务

## 1. 概念定义

十二要素应用第 VI 节的原文表述：十二要素的进程是**无状态且无共享（stateless and share-nothing）**的，任何需要持久化的数据都必须存放在有状态的后端服务中，通常是数据库。

该节同时给出两条精确边界：

- 进程的内存空间或文件系统**可以用作短暂的、单事务的缓存**（例如下载大文件、处理、把结果存库），但应用绝不能假定内存或磁盘上缓存的任何内容在未来的请求或任务中仍然可用。
- 此处的"状态"**不包括构建期产物**。资源打包器一类把文件系统当作编译资产缓存的做法，十二要素倾向于在构建阶段完成。

可操作的判定标准：**任意请求交给任意副本处理，结果必须一致；任意副本被销毁，不造成用户可感知的数据丢失。**

## 2. 为什么无状态才能水平扩容

无状态不是审美偏好，而是四项能力的前提条件：

| 能力 | 依赖的机制 | 有状态时的失效表现 |
|------|-----------|-------------------|
| 负载均衡 | 请求可路由到任意副本 | 必须引入路由约束，路由表本身成为新状态 |
| 故障转移 | 状态不在副本内，副本失效不丢数据 | 副本崩溃即丢失该批用户的会话与中间结果 |
| 弹性伸缩 | 扩容无需迁移状态，缩容无需排空状态 | 扩容需要状态再平衡，缩容需要先迁移 |
| 滚动发布 | 新旧版本并存，请求上下文不依赖特定进程 | 请求必须被钉在特定版本实例上，发布窗口被拉长 |

十二要素对此的论述是：由于每类进程都运行着多个实例，未来请求大概率由另一个进程处理；即使只运行一个进程，一次重启（代码部署、配置变更、或执行环境把进程迁移到另一台物理机）通常也会清空全部本地状态。

## 3. 状态外置的四种去处

| 去处 | 适用状态 | 代价与约束 |
|------|----------|-----------|
| 数据库 | 强一致、需持久化的业务态 | 吞吐与延迟代价最高；是"正确性"的归属地 |
| 缓存（Redis / Memcached） | 会话态、带过期时间的中间态 | 需接受失效与丢失的可能；不能作为唯一真相源 |
| 对象存储 | 大二进制、产物、用户上传文件 | 延迟高，不适合热路径；需处理一致性窗口 |
| 客户端（令牌 / Cookie） | 无服务端存储的会话，签名 Cookie、JWT | 体积受限；**不可即时吊销**是主要代价 |

十二要素明确：**会话状态数据适合放到提供过期时间的存储中**，例如 Memcached 或 Redis。

## 4. 会话保持：为什么它是妥协方案

**定义**：把同一客户端的后续请求固定路由到同一后端实例。Kubernetes 的对应实现是 Service 的 `sessionAffinity: ClientIP`，其 `sessionAffinityConfig.clientIP.timeoutSeconds` 默认值为 **10800 秒（3 小时）**，取值必须大于 0 且不超过 86400 秒。

**十二要素的立场极为明确**：粘性会话是对十二要素的违背，**绝不应使用或依赖**。

称其为妥协方案，理由有四：

1. **它把状态的可用性绑定到进程的可用性。** 副本崩溃即等于该批用户会话丢失，故障转移能力被抵消——这正是引入水平扩容想解决的问题。
2. **它破坏负载均衡的均衡性。** NAT 出口、移动网络 IP 漂移会把大量不同用户聚合到同一客户端 IP，形成热点实例。
3. **它与弹性伸缩、滚动发布直接冲突。** 缩容或发布时，被固定路由的副本下线即造成会话失效，等于为每次发布附加一次用户可见的中断。
4. **它延后问题，而非解决问题。** 真正需要的是状态外置；粘性会话只是让"状态在内存里"这件事暂时不暴露。

**可接受的使用场景**：仅作为**性能优化**而非正确性依赖。例如灰度期间用亲和性降低缓存击穿。判断标准是：摘掉粘性后功能是否仍然完全正确——可随时摘除，是检验这一点的唯一标准。

## 5. 常见陷阱

| 陷阱 | 表象 | 后果 | 正确做法 |
|------|------|------|----------|
| 进程内缓存 | 命中率随副本数上升而下降 | 多副本间不一致，扩副本反而降低命中率 | 外置缓存，或明确接受冗余 |
| 本地文件写入 | 容器重启后文件消失 | 数据丢失；多副本互相看不到 | 对象存储 |
| 内存计数器与限流 | 单机限流看似生效 | **实际总阈值 = 设定值 × 副本数**，且随扩缩容动态漂移 | 集中式限流（Redis / 网关层） |
| 误把内存当队列 | 进程退出即丢任务 | 无 ack、无重试、无持久化 | 真正的消息中间件 |
| 内存锁 / 内存互斥 | 单副本下有效 | 跨副本完全失效，形同虚设 | 分布式锁，且需处理锁超时与业务超时的关系 |
| 后台定时任务随副本重复执行 | 每副本各跑一次 | 重复副作用 | 选主或外部调度器 |

其中第三条在多副本环境下最隐蔽：单机测试时限流精确生效，上线后总阈值被放大 N 倍，而 N 还会随 HPA 变化。

## 6. AI Agent 场景的张力与划界

这是本主题最需要厘清的部分。**Agent 天然有状态**：会话历史、中间推理步骤、工具调用结果、待执行计划，都是跨请求存活的数据。若因此放弃无状态约束，则水平扩容、故障转移、滚动发布全部失效。

**划界原则：服务进程无状态，任务状态外置。** 进程只是"执行器"，任务是被持久化的实体，二者解耦。

| 状态类型 | 归属 | 存放 |
|----------|------|------|
| 会话历史 / 消息列表 | 任务态 | 外置存储，按 `session_id` 寻址 |
| 中间步骤、工具调用参数与结果、trace | 任务态，同时是审计证据 | 持久化存储，不可只放内存 |
| 长期记忆、向量索引 | 全局态 | 专用后端服务 |
| 限流计数、断路器状态 | 控制态 | 外置（Redis / 网关） |
| 进程内 tokenizer、模型权重、预热索引 | **非用户态，可重建** | 可留进程内，属预热资产 |

由此推出四条工程结论：

1. **任意副本必须能接管任意 session。** 这要求会话具备**检查点**：Agent 的每一步完成后即落盘，恢复时从最后一个已提交步骤续跑，而非从头重来。
2. **长任务不能跑在 HTTP 请求连接上。** 请求连接会被负载均衡器超时、Pod 终止、客户端断连三者中任意一个打断。正确形态是"提交任务 → 返回 `task_id` → 轮询 / 回调 / SSE 拉取进度"，任务由 worker 池执行。
3. **流式输出（SSE / WebSocket）是连接级状态，不是业务状态。** 它可以丢，但必须可续：客户端应携带游标（`Last-Event-ID` 或 offset）重连续传。
4. **幂等与可重入是硬要求。** 无状态执行器意味着同一步骤可能被不同副本重复执行（重试、故障转移），因此每个不可逆的工具调用都必须带幂等键。
