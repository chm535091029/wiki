# 配置管理

## 1. 十二要素 Config 一节的核心主张

十二要素对 config 的定义：**一切在各次部署之间可能发生变化的东西**。具体包括三类——数据库、Memcached 及其他后端服务的资源句柄；外部服务的凭据；以及每次部署各自不同的值（如该次部署的规范主机名）。

核心主张可归纳为四点。

**第一，严格分离配置与代码。** "配置在各次部署间差异很大，代码不变"是这一分离的依据。

**第二，判定标准（litmus test）**：代码库能否在任意时刻开源，而不泄露任何凭据。这是唯一可执行的检验，也是判断"某个值到底该放哪"的实用标准。

**第三，把配置存入环境变量。** 官方理由是：env var 可在部署间轻松变更而无需改代码；几乎不可能被误提交进代码仓库；且是与语言、操作系统无关的标准。相对地，未纳入版本控制的配置文件（如 `config/database.yml`）虽有改进，但仍存在三个弱点——容易误提交、配置文件散落各处且格式不一、格式往往是语言或框架特定的。

**第四，反对"环境分组"。** 把配置打包成 `development` / `test` / `production` 这类命名组的方式"无法干净地扩展"：随着部署数量增长，需要新增 `staging`、`qa`，甚至 `joes-staging`，最终产生组合爆炸。十二要素要求把每个 env var 视为**彼此完全正交的细粒度控制项**，独立管理。

官方同时给出了边界：**此处的 config 不包括应用内部配置**（如路由表、模块装配方式），后者不随部署变化，留在代码中最合适。

## 2. 配置分层

| 层 | 载体 | 变更成本 | 适用 |
|----|------|----------|------|
| 代码内默认值 | 常量 | 需发版 | 结构性默认值、不随部署变化的值 |
| 环境变量 | 进程环境 | 需重启进程 | 端点、功能开关、非敏感的每部署值 |
| 密钥管理服务 | Secret Manager / Kubernetes Secret | 可轮换 | 凭据、证书私钥 |
| 远程配置中心 | 配置服务 | 可热更新 | 需动态调整的限额、灰度开关 |

覆盖规则为后层覆盖前层，且**每次覆盖都应可追溯**——记录生效来源与最终取值，否则线上行为无法归因。这在 Agent 系统中尤其重要，因为模型版本与提示词版本的漂移是典型的"改了什么不知道"故障。

## 3. 环境变量的适用与不适用

**适用**：短标量、非敏感或敏感性可接受、每次部署不同的值（DSN、功能开关、日志级别、超时数值）。

**不适用**：

- **大段结构化配置**。YAML / JSON 的嵌套结构塞进单行变量后失去 schema 校验与可读性，且转义容易出错。
- **证书与私钥**。多行内容含换行与特殊字符，塞进 env 易被截断或转义损坏；更关键的是 env 会被 `docker inspect`、`/proc/<pid>/environ`、崩溃上报、子进程继承等路径带出。
- **需要热更新的配置**。改 env 意味着重启进程，无法用于需要即时调整的控制面参数。
- **会被日志或错误堆栈打印的值**。

对结构化数据与密钥材料，**以文件路径挂载（Secret 卷）由进程读取**是更稳妥的形态。

## 4. 密钥管理

### 4.1 为什么不入库、不入镜像

密钥一旦进入 Git 历史，撤销需要重写历史，而泄露已经发生；镜像层会被分发到镜像仓库与节点缓存，任何能拉取镜像的人都能解出其中内容。十二要素把"可随时开源"作为判定线，正是这两条风险的直接映射。

### 4.2 Kubernetes Secret 的现实约束

官方文档明确列出以下前提，任何使用 K8s Secret 的方案都必须以此为基础：

- Secret **默认以未加密形式存储在 etcd 中**。
- 任何有 API 访问权的人都能检索或修改 Secret，任何能访问 etcd 的人亦然。
- 任何被授权在命名空间中创建 Pod 的主体，都能读取该命名空间内的任意 Secret（含间接途径，如创建 Deployment）。
- **base64 不是加密方法**，官方原文表述为它相比纯文本"不提供任何额外的机密性"。

官方要求的最低动作有四项：启用静态加密；按最小权限配置 RBAC（**授予 `list` 权限即隐含允许获取全部 Secret 内容**）；把 Secret 访问限制到特定容器；考虑使用外部 Secret 存储提供者（如 Secrets Store CSI Driver）。

此外，应用在读取后仍需保护机密信息——不得明文记日志，不得传输给不可信方。

### 4.3 轮换

密钥必须是可替换的。工程上要求应用支持多版本并存（当前值 + 上一值），并支持不重启更新或滚动重启。

轮换的前提是能枚举"这个密钥在哪里被使用"，因此**禁止把同一密钥复制到多处配置**——复制即意味着轮换路径不可枚举，也就意味着轮换实际上无法进行。

## 5. 多环境管理与配置漂移

**漂移的成因**：各环境靠人工维护各自的配置副本；配置散落在多处、多种格式。这正是十二要素指出的配置文件方案的固有弱点。

**治理手段**：单一配置源 + 各环境只提供"差异集"；配置 schema 化并做校验；部署时记录配置快照或版本号，与代码版本共同构成可回溯的发布单元。

## 6. 常见陷阱

| 陷阱 | 说明与后果 |
|------|-----------|
| 把密钥提交进 Git | 撤销成本极高，等同于永久泄露 |
| 环境变量与 `.env` 文件混为一谈 | `.env` 只是"从文件加载 env"的便利机制，文件本身仍需不入库；它常在 IDE 缓存、CI 缓存、容器层中被带出 |
| 配置类型错误 | 环境变量值一律是字符串，`"false"`、`"0"` 在弱解析下为真；布尔与数值必须显式解析 |
| 启动时未校验必填项 | 缺失配置要到运行到某个分支才暴露，表现为偶发 500 或静默走默认值 |
| 配置无 schema | 拼写错误静默生效，无告警 |
| 敏感值进入日志 | 启动时打印全量配置、异常堆栈携带 DSN |

对"启动时未校验"一项，正确做法是**启动即 fail-fast，并一次性列出全部缺失项**，而非遇到第一个缺失即退出——后者会让修复变成多轮往返。

## 7. AI Agent 场景注意点

1. **多家模型 API Key 必须按 provider 维度命名**（`OPENAI_API_KEY`、`ANTHROPIC_API_KEY` 等），不要复用单一的 `LLM_API_KEY`。轮换通常是按 provider 分别进行的，共用变量会让轮换无法进行。

2. **端点差异必须配置化。** 官方直连、网关代理、私有化部署（vLLM / TGI）的 `base_url` 应作为独立配置项，而不是硬编码在 SDK 初始化代码中。需注意不同 provider 的 SDK 对 `base_url` 的语义（是否包含 `/v1` 前缀）并不一致，这是迁移时的常见故障点。

3. **成本限额配置应放在远程配置中心，而非环境变量。** 这是 Agent 系统特有的控制面配置：超预算时需要立即下调，重启进程的代价过高。至少应区分四个层级——单请求 token 上限、单会话上限、单租户日/月配额、并发上限。

4. **模型与提示词版本需纳入配置并随发布单元记录。** 模型名应固定到快照版本（而非浮点别名），温度、系统提示词版本同理。否则线上行为漂移无法归因。

5. **工具白名单与危险操作开关应配置化，并在启动时做一致性校验。** 例如"开启代码执行"必须同时配置沙箱地址，否则启动直接失败。这类"配置组合的合法性"校验，是防止配置漂移的最后一道防线。
