## 技术背景与动机

### 问题与挑战

大语言模型采用自回归方式生成文本：每生成一个新 token 都需要基于全部前置 token 完成一次完整前向传播，推理延迟随输出长度线性增长。这导致 GPU 利用率低下、用户等待时间过长，是 LLM 线上服务的核心性能瓶颈，在实时对话助手、多轮 Agent 工作流等低时延敏感场景中尤为突出。

**推测解码 (Speculative Decoding)** 是行业公认的解决路径：用轻量级草稿模型 (draft model) 快速生成候选 token，再由目标模型一次前向批量验证。验证是**前缀式**的——一旦某位置被拒绝，后续候选全部作废。其单 token 平均延迟可表示为：

```
L = (T_draft + T_verify) / τ
```

其中 `T_draft` 为草稿生成耗时，`T_verify` 为目标模型验证耗时，`τ` 为平均接受长度 (accepted length)。降低 L 只有三条路：猜得更快（降 T_draft）、猜得更准（升 τ）、验证更聪明（降 T_verify 浪费）。

### 现有方案的两难

| 方案 | 代表 | 生成方式 | 接受率 | 候选块长度 | 核心瓶颈 |
|------|------|---------|--------|-----------|---------|
| 自回归草稿 | Eagle3 | 逐 token 串行 | 高 | 短 (3-5) | 草稿耗时随块长线性增长，只能用短块、浅层网络 |
| 并行草稿 | DFlash | 单次前向全并行 | 后缀衰减严重 | 长 (8-16) | 块内 token 无依赖建模，后半段接受率断崖式下跌 |

并行草稿的质量问题源于**多模态碰撞 (multi-modal collision)**：各位置独立预测，后面的 token 不知道前面实际采样出了什么。例如上下文可续写 "of course" 或 "no problem"，并行模型可能混出 "of problem"。这导致**后缀衰减 (suffix decay)**——以 Chat 任务为例，DFlash 的条件接受率从位置 1 的 0.72 衰减到位置 7 的 0.63。

此外，现有方案普遍采用**静态验证长度**，缺乏负载自适应校验机制。在高并发服务中，目标模型的 batch capacity 是有限资源：不加区分地验证长草稿块，会把宝贵的批处理算力浪费在大概率被拒绝的尾部 token 上，严重拖累整体吞吐。

### 设计目标

- 保留并行生成的高吞吐，同时补齐块内依赖建模，缓解后缀衰减
- 将验证长度从固定超参数变为随请求质量与系统负载动态变化的调度决策
- 严格保持无损解码——输出分布与目标模型完全一致

## 核心架构设计

### 整体流程

```
Prompt ──► 目标模型生成锚点token x₀
              │
              ▼
   ┌─────────────────────────────────────┐
   │  DSpark 草稿模型                     │
   │  ① 并行主干 (Parallel Backbone)      │
   │     单次前向 → 隐藏状态 h₁…hγ         │
   │                + 基础logits U₁…Uγ    │
   │  ② 轻量顺序头 (Sequential Head)      │
   │     逐位置注入前一token信息，采样草稿   │
   │  ③ 置信度头 (Confidence Head)        │
   │     输出各位置条件接受概率 c₁…cγ       │
   └──────────────┬──────────────────────┘
                  ▼
   ┌─────────────────────────────────────┐
   │  硬件感知前缀调度器                    │
   │  置信度 + GPU负载 → 动态决定验证长度 ℓ  │
   │  （剪掉低置信后缀，不送验证）            │
   └──────────────┬──────────────────────┘
                  ▼
   目标模型单次并行前向验证候选前缀
      │ 接受: 累积输出        │ 拒绝: 从拒绝位置
      ▼                      ▼  重采样并进入下一轮
   输出分布与原模型严格一致（无损）
```

DSpark 的核心设计可概括为一句话：**用并行主干保证速度，用轻量串行模块补齐质量，用置信度调度器聪明地分配验证预算**。

### 组件构成

1. **并行主干（Parallel Backbone）**：继承 DFlash 的**非自回归（non-autoregressive）**草稿 Transformer。它把"锚点 + (γ-1) 个占位槽"作为整段输入，**一次前向**并行输出整块候选的隐藏状态 `h₁…hγ` 与基础 logits `U₁…Uγ`，耗时几乎不随块长 γ 增加。关键在于占位槽之间彼此独立、只看锚点，于是 γ 个分布能同时算出（为何这与自回归目标模型不矛盾，见下节「通俗理解」）。锚点 token 本身作为第一个预测位置。
2. **轻量顺序头（Sequential Head）**：叠加在主干之上的极轻量逐步修正模块（Markov Head / RNN Head 两种实现）。主干给出的是"块内独立的第一版猜测"，顺序头在**采样时**把已采样的前一个 token 信息以偏置 `Bₖ` 注回，逐位修正块内依赖（修掉多模态碰撞），且**不重跑主干**——重算力始终只有一次。
3. **置信度头（Confidence Head）**：与草稿生成同步，为每个位置输出条件接受概率 `cₖ`，供硬件感知前缀调度器决定验证长度 ℓ。

## 通俗理解（常见疑问与直觉）

> 本节用直觉与数值示例补充上面的形式化描述，专解三个最常见的困惑：为什么草稿模型能一次出整块、三个头分别干啥、顺序头到底怎么改分布。

### 1. 为什么草稿模型能"一次前向算出整块"？

直觉上 Transformer 推理是逐 token 的——要生成第 k 个字必须先有前 k-1 个字。但那个约束针对的是**目标模型（大模型）**，而此处一次前向出整块的是**另一个模型：草稿模型**。

- **目标模型确实自回归**：每产出一个真实 token 需要一次前向（靠 KV Cache 增量算，不是从零重读全文）。这是慢的根源。
- **草稿模型是非自回归的**：它是一个独立的、轻量的、专门被训练成"给定锚点 `x₀`，一次前向直接输出接下来 γ 个位置的候选分布 `U₁…Uγ`"的模型（类似非自回归翻译，一口气给整句候选）。
- **它为什么能并行**：输入是 `[锚点 x₀, 占位槽₁ … 占位槽_{γ-1}]`，占位槽是特殊嵌入而非真实字；这些槽之间允许并行注意力，于是 γ 个分布同时算出，**不需要块内真实 token**。代价正是"假装块内独立"带来的质量近似（多模态碰撞）——所以才需要顺序头补刀。
- **验证也是一次批量前向**：目标模型把候选前缀整条喂入，一次前向产出所有位置分布，再与草稿逐位比对；验证的"前缀式"是**接受语义**而非**计算方式**。

用公式视角看单 token 平均延迟 `L = (T_draft + T_verify) / τ`：草稿一次小前向 + 验证一次大前向，换回 τ 个 token，远优于纯自回归每 token 一次大前向。

### 2. 三个头一句话类比

| 头 | 角色 | 类比 |
|----|------|------|
| 并行主干 | 一次并行猜出整块（快） | 实习生看着开头，一口气把接下来 5 个空槽都填个第一版草稿 |
| 轻量顺序头 | 采样时注入前一词，修正串味（准） | 写完前一词看一眼再写后一词，避免 "of"+"problem" 串成 "of problem" |
| 置信度头 | 给每个位置标"被接受把握"（估值） | 实习生给每个词打分"资深翻译几成会认可"，供主管决定整段要不要送审 |

### 3. 顺序头如何逐位修正：一个数值示例

设定：锚点 `x₀ = "That's"`，草稿块长 `γ = 3`，两条合理续写路径——路径 A：`of course we`、路径 B：`no problem here`。

**① 并行主干一次前向**，给出相互独立的 `U₁ U₂ U₃`（占位槽彼此不看真实取值，故 U₂ 在 course/problem 上各留 0.40，埋下碰撞隐患）：

| 位置 | Uₖ 分布（并行、独立猜测） |
|------|------------------------|
| U₁ | of 0.50 / no 0.45 / idea 0.05 |
| U₂ | course 0.40 / problem 0.40 / idea 0.20 |
| U₃ | we 0.35 / here 0.35 / now 0.30 |

**② 顺序头逐位采样**，每步用前一个真实采到的词算偏置 `Bₖ = W₁[xₖ₋₁]·W₂`，加到 Uₖ 再采样：

走路径 A（第 1 词采到 "of"）：

```
k=1: 由 U₁ 采样 → x₁ = "of"
k=2: B₂(of) = {course:+0.45, problem:−0.35}
     p₂ → course 0.85 / problem 0.05 → x₂ = "course"   ← 碰撞被修
k=3: B₃(course) = {we:+0.40, here:−0.30}
     p₃ → we 0.75 / here 0.05 → x₃ = "we"
结果：That's of course we  ✓
```

走路径 B（第 1 词采到 "no"）时，`B₂(no)` 反过来把 problem 顶上去，得到 `That's no problem here` ✓。

**③ 对照：没有顺序头（纯并行 DFlash）**——第 2 词直接从 U₂ 独立采样，与 x₁ 脱钩，可能采到 `x₁="of", x₂="problem"` → `That's of problem` ✗（碰撞发生）。顺序头就是让"前一个真字"成为第 2 词分布的开关。

**④ 为何仍轻量**：主干前向只跑 1 次；顺序头每步仅"查前一个词的 embedding + 乘一个 256×词表 的小矩阵 + 加到 Uₖ"，比一层 Transformer 便宜几个数量级。所谓"串行"只是采样顺序串行，**不重跑模型**——这正是文档所述"草稿长度 4→16 仅多 0.2%~1.3% 延迟、换 ~30% 接受长度"的原因。

> 注：上表概率为**教学示意值**，非论文实测；论文中 `Bₖ` 为低秩分解 `W₁[xₖ₋₁]·W₂`（秩 r=256），机制一致。

## 关键技术原理

### 1. 半自回归生成 (Semi-Autoregressive Generation)

**思路**：不抛弃并行，在并行生成之后补一层轻量顺序修正。定义因果块分布：

```
P(X|x₀) = ∏ₖ pₖ(xₖ | x₀, x<ₖ)
pₖ(v | x₀, x<ₖ) = exp(Uₖ(v) + Bₖ(x₀, x<ₖ, v)) / Σᵤ exp(Uₖ(u) + Bₖ(x₀, x<ₖ, u))
```

其中 `Uₖ` 为并行主干的基础 logits，`Bₖ` 为顺序头注入的依赖偏置。

**Markov Head（默认方案）**：只看前一个已采样 token，用低秩分解的一阶转移偏置调整分布：

```
B(xₖ₋₁, ·) = W₁[xₖ₋₁] · W₂ ∈ R^V
其中 W₁ ∈ R^(V×r) 为embedding查找表，W₂ ∈ R^(r×V) 为logit投影，r = 256
```

直观理解：若前一 token 已采样为 "of"，Markov Head 会让后续 token 倾向 "course" 而非另一条语义路径上的 "problem"。

**RNN Head（备选方案）**：维护循环状态 `sₖ` 累积块内完整前缀信息：

```
zₖ = [sₖ₋₁; W₁[xₖ₋₁]; hₖ]
sₖ = σ(W_g·zₖ) ⊙ sₖ₋₁ + (1 - σ(W_g·zₖ)) ⊙ tanh(W_c·zₖ)
Bₖ = W₂ᵀ · tanh(W_o·zₖ)
```

实验显示 RNN Head 相比 Markov Head 收益有限而部署复杂度更高，故默认采用 Markov Head——典型的效果/延迟/部署成本三者均衡的工程决策。

**效果**：
- 仅 2 层的 DSpark 接受长度即超越 5 层 DFlash，体现顺序建模的参数效率优势
- 草稿长度从 4 扩到 16，顺序头仅带来 0.2%~1.3% 额外延迟，换来约 30% 接受长度提升
- 条件接受率同时具备"高起点"（继承并行主干深层优势）与"稳定后缀"（继承自回归依赖建模优势），全程几乎不衰减

### 2. 置信度调度验证 (Confidence-Scheduled Verification)

#### 置信度头 (Confidence Head)

对每个草稿位置 k 输出标量 `cₖ ∈ (0,1)`，估计"在前缀均被接受条件下该位置被接受的概率"：

```
cₖ = σ(wᵀ [hₖ; W₁[xₖ₋₁]])
```

训练监督信号基于草稿分布与目标分布的总变差距离 (TV distance)：

```
cₖ* = 1 - ½ ‖pₖᵈ - pₖᵗ‖₁
```

关键预测量是**前缀存活概率** `a_{r,j} = ∏ᵢ≤ⱼ cᵢ`——由于验证是前缀式的，第 5 个 token 是否值得验证不仅取决于自身，还取决于前 4 个能否连续通过。

#### 顺序温度缩放 (Sequential Temperature Scaling, STS)

原始置信分普遍过度自信，导致联合存活概率被高估。STS 在验证集上从左到右逐位置做 1D 温度网格搜索，最小化累积乘积的 ECE 且保持排序不变。校准后平均 ECE 从 **3%~8% 降至约 1%**，为调度器提供可靠概率估计。

#### 硬件感知前缀调度器 (Hardware-Aware Prefix Scheduler)

将调度建模为全局吞吐量最大化问题：

```
max_{ℓ₁,…,ℓ_R}  Θ = τ · SPS(B)
其中  B = Σᵣ(1 + ℓᵣ)              # 验证批次大小
      τ = Σᵣ(1 + Σⱼ a_{r,j})     # 期望接受token数
      SPS(B)                     # 引擎吞吐曲线（初始化时profiling为查找表）
```

**求解**：贪心排序 + 早停。将所有请求的所有候选按前缀存活概率降序排列，逐一纳入验证批次并查表计算 Θ，一旦吞吐开始下降立即停止。复杂度 O(γR·log(γR))，且严格**非预期 (non-anticipative)**——不利用未来信息做决策（论文附录给出反例证明：提前偷看未来 token 会破坏无损推测解码的理论保证）。

**调度行为**：轻负载时分配 4-6 个验证 token（超过 MTP-1 的静态方案），高负载时自动收缩预算防止 batch 容量争抢——始终在当前硬件状态下寻找最优工作点。

### 3. 训练与工程实现

**训练设置**：
- 数据：Open-PerfectBlend（130 万样本，math 39.4% / code 38.9% / chat 17.6% / IF 4.1%），仅用 prompt，响应由目标模型以非思考模式生成，训练 10 epoch
- 损失函数：`L = 0.1·L_ce + 0.9·L_tv + 1.0·L_conf`，位置权重 `wₖ = exp(-(k-1)/γ)`
- 目标模型冻结，仅训练并行主干、顺序头与置信度头
- 生产配置：γ=5，并行主干 3 个 MoE 层 + mHC + 滑动窗口 128，Markov Head

**两大工程挑战与解法**：

| 挑战 | 问题 | 解法 |
|------|------|------|
| 训练通信开销 | 草稿训练需目标模型输出分布监督，朴素实现按词表传输 O(V)（V≈10⁵） | 只传目标模型最后一层 hidden state，本地做 LM head 投影，通信降至 O(d)；配合锚点有界序列打包降低内存 |
| 异步调度与 ZOS 兼容 | 实际 SPS 曲线锯齿非单调，朴素早停陷入局部最优；ZOS 要求下一步 batch size 提前确定 | 异步调度：用前两步的置信度预测确定当前步验证容量上限 (top-K)，异步设计天然形成因果屏障，去早停做全局搜索仍满足无损约束 |

## 性能对比分析

### 离线基准：草稿质量

评测设置：目标模型 Qwen3-4B/8B/14B、Gemma4-12B；基准覆盖数学推理 (GSM8K/MATH500/AIME25)、代码生成 (MBPP/HumanEval/LiveCodeBench)、日常对话 (MT-Bench/Alpaca/Arena-Hard-v2)；指标为平均接受长度 τ（含 bonus token）。

**宏平均相对提升**：

| 目标模型 | vs. Eagle3 (自回归 SOTA) | vs. DFlash (并行 SOTA) |
|---------|------------------------|----------------------|
| Qwen3-4B | +30.9% | +16.3% |
| Qwen3-8B | +26.7% | +18.4% |
| Qwen3-14B | +30.0% | +18.3% |
| Gemma4-12B | 一致增益（跨模型泛化） | 一致增益 |

**代表性绝对数值**（Qwen3-4B，GSM8K / HumanEval / MT-Bench）：

| Drafter | Math (GSM8K) | Code (HumanEval) | Chat (MT-Bench) |
|---------|-------------|------------------|-----------------|
| Eagle3 | 5.14 | 4.16 | 2.39 |
| DFlash | 5.40 | 4.74 | 3.07 |
| **DSpark** | **6.11** | **5.38** | **3.64** |

**领域差异效应**：结构化任务的可接受长度天然更高（Qwen3-4B 数学平均 5.57、代码 5.12），开放式对话明显偏低（3.49）——这也印证了置信度调度的必要性：Chat 场景经置信度阈值过滤后接受率可从 45.7% 提升至 95.7%。

### 生产环境：DeepSeek-V4 线上实测

DSpark (γ=5) 已部署于 DeepSeek-V4-Flash/Pro 在线服务系统，基于真实用户流量对比生产基线 **MTP-1**（单 token 草稿）：

| 模型 | SLA 档位 | 聚合吞吐量提升 | 单用户生成速度 (TPS) 提升 |
|------|---------|--------------|------------------------|
| V4-Flash | 中等 (80 tok/s/user) | +51% | +60% |
| V4-Flash | 严格 (120 tok/s/user) | +661%（MTP-1 接近崩溃） | +85% |
| V4-Pro | 中等 (35 tok/s/user) | +52% | +57% |
| V4-Pro | 严格 (50 tok/s/user) | +406%（MTP-1 严重退化） | +78% |

**核心结论**：在匹配吞吐条件下，DSpark 将单用户生成速度提升 **60%~85%**；更重要的是，在严格交互时延约束下避免了吞吐率大幅滑坡，解锁了 MTP-1 无法达到的性能档位，**推高了整套服务系统的吞吐-交互性 Pareto 前沿**。

### 与相关工作对比

| 方法 | 草稿架构 | 验证调度 | 生产验证 |
|------|---------|---------|---------|
| Eagle3 | 自回归 (TTT) | 静态长度 | 无 |
| DFlash | 完全并行 | 静态长度 | 无 |
| SpecDec++ | 任意 | 静态置信阈值 | 无 |
| **DSpark** | **半自回归** | **硬件感知动态调度** | **DeepSeek-V4 生产系统** |

DSpark 是目前已知唯一同时解决草稿质量衰减（半自回归）与系统级吞吐优化（置信调度），并在超大规模生产系统中完成验证的方案。

---

## 应用场景

1. **高并发在线推理服务**：已通过 DeepSeek-V4 真实流量验证，可直接替换 MTP 类生产方案，在严格 SLA 下维持非退化服务能力
2. **低时延敏感场景**：实时对话助手、多轮 Agent 工作流、工业代码生成、金融舆情等对交互时延敏感的规模化落地场景
3. **结构化任务优先**：数学推理、代码生成等任务接受长度天然更高，加速效果最显著
4. **中小企业私有化部署**：DSpark 兼容 Qwen、Gemma 等主流开源基座，配套 DeepSpec 全栈开源仓库（数据准备、草稿模型实现、训练与评估脚本，MIT 许可）与全部模型权重，无需底层算法团队即可复用成熟推理优化方案

**开源资源**：
- DeepSpec 仓库支持 Eagle3 / DFlash / DSpark 三种算法，评测覆盖 gsm8k、math500、aime25、humaneval、mbpp、livecodebench、mt-bench、alpaca、arena-hard-v2
- 已发布 Qwen3-4B/8B/14B、Gemma4-12B 对应的三种算法草稿模型 checkpoint
- 注意：默认 checkpoint 基于非思考模式数据训练；若目标模型以思考模式运行或用于特定领域，建议重新微调草稿模型

---

## 局限性

1. **草稿侧固定开销不可回收**：对可预测性极低、接受率偏低的复杂查询，仍须生成完整 γ 块草稿，这部分前置算力无法回收
2. **调度依赖近似假设**：生产环境的异步调度使用前两步历史置信度做决策，依赖负载平滑性假设
3. **数据准备成本高**：DeepSpec 训练管线需缓存目标模型输出，存储开销大（默认 Qwen3-4B 配置约 38 TB）
4. **开放域收益相对有限**：开放式对话的接受长度（~3.5）显著低于结构化任务（~5.5），加速上限受任务本征可预测性约束

**未来方向**：在草稿模型内部引入难度感知的早退出机制 (difficulty-aware early exiting)，使低接受率请求能够跳过完整块生成流程。

---

## 总结

DSpark 通过**半自回归架构**（并行主干 + 轻量 Markov Head，以 ~1% 延迟开销换取 ~30% 接受长度提升）与**置信度调度验证**（校准置信度 + 硬件感知前缀调度器，把验证预算动态分配给期望收益最高的前缀）两项互补机制，同时击中了推测解码的草稿质量与验证效率两大痛点。在 DeepSeek-V4 生产系统中，相较 MTP-1 基线将单用户生成速度提升 60%~85%，并推高了服务系统的 Pareto 最优边界。

其更深层的意义在于验证了两个工程哲学：**"一点点自回归，价值巨大"**——完全并行与完全串行都不是最优解；以及推理优化正从单纯的算法层优化走向**算法-系统协同设计**——将目标模型的验证算力视为需要动态分配的稀缺资源。配合 DeepSpec 全栈开源，DSpark 正在将推测解码从学术概念推向生产标配。
