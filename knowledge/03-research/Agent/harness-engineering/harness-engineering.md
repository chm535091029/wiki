# Harness Engineering（挽具工程）

## 概念定义

Harness（挽具/马具）的核心思想是：**你不是在训练马怎么想，而是用缰绳和围栏去确保它不跑偏**。

不是靠调 prompt 也不是管上下文，而是搭一套执行框架，让系统可靠运转。AI 可能会犯错，但我们的框架会成为最终的兜底方案，保证在 AI 出错时及时介入并要求 AI 修正。

## 领域演变历程

### 阶段一：Prompt Engineering（提示词工程）

AI 和人的主要互动形式是问答，agent 概念还没出来，没有什么工具。

- **核心假设**：AI 的表现取决于提示词写得好不好
- **优化方向**：调措辞、加约束、写示例
- **核心问题**：大模型可能错误理解语义，上下文太大时会压缩要求

### 阶段二：Context Engineering（上下文工程）

随着 Agent 概念火起来（2023 年 AutoGPT 出现），AI 可以自主调工具、搜索、写文件、把大任务拆成小步骤链式执行。

- **新问题**：光靠好的提示词不够产出一个好的结果
- **需要**：知道项目背景、看到相关代码、理解之前做的决定
- **结果**：暴涨的上下文
- **优化方向**：从"怎么写好提示词"转移到"怎么管理好 AI 能看到的所有信息"
- **典型案例**：Skills 的渐进式披露（只在需要时才读取对应技能定义）

### 阶段三：Harness Engineering（挽具工程）

随着模型能力增强和上下文容量增大，上下文问题逐渐解决，但新问题出现：

- **AI 的本质是不确定的**：同样的输入这次做好下次可能就漏了一步
- **Agent 做的事情越来越复杂**：经常是几十步连在一起跑，中间只要有一步出问题后面就跟着全崩
- **无法通过调整 prompt 和上下文消除这种不确定性**：这是大模型的本质特性

**解决思路**：在 AI 的外层打保障机制，不是告诉 AI 请你别犯错，而是直接通过框架去验收或限制 AI。

## 四层保障体系

目前没有公认的业界标准，根据实践经验主要有四层：

```
┌────────────────────────────────────────────┐
│           Harness Engineering              │
├────────────────────────────────────────────┤
│  Layer 4: Hook（钩子）                      │
│  在 AI 执行操作前后自动触发检查              │
├────────────────────────────────────────────┤
│  Layer 3: 测试验证                          │
│  AI 说他写完了，但跑不跑过测试才是真的         │
│  测试就是验收标准的代码化                    │
├────────────────────────────────────────────┤
│  Layer 2: 自动检查                          │
│  用 Ruff/Lint 检查代码规范                  │
│  不符合规范的当场就被拦下来                   │
├────────────────────────────────────────────┤
│  Layer 1: 结构化定义（Spark）                │
│  把 SQL 文件从自然语言改成结构化定义          │
│  输入是什么、输出是什么、验收标准是什么        │
│  用确定性代码写出流程，AI 按结构填跑程序       │
└────────────────────────────────────────────┘
```

### Layer 1: Spark 结构化定义

把需求从一大段自然语言改成结构化的定义：

| 要素 | 说明 |
|-----|------|
| 输入 | 明确的输入参数定义 |
| 输出 | 明确的输出格式要求 |
| 验收标准 | 可量化、可验证的标准 |
| 执行流程 | 用确定性代码写出完整流程 |

**优势**：AI 不用试图理解你的意图，只要按结构填跑程序就可以保证一致性。

### Layer 2: 自动检查

用 Ruff/Lint 等工具在 AI 每次改完代码之后自动跑：

- 不符合规范的当场就被拦下来
- 不需要人工 review
- 规则明确，AI 无法绕过

### Layer 3: 测试验证

测试是验收标准的代码化：

- AI 说他写完了 ≠ 真的写完了
- 跑不跑过测试才是真的测试
- 用测试来验证输出对不对

### Layer 4: Hook

在 AI 执行操作的前后自动触发检查（详见 [Hook 机制详解](./hook.md)）：

- 生命周期事件：Session Start、Pre Tool Use、Post Tool Use、Stop 等
- 通过退出码控制 AI 行为
- 支持条件拦截（Conditional Hook）

## 核心逻辑

```
AI Output ──→ 自动检查 ──→ 测试验证 ──→ Hook 检查
     │              │             │
     │              │             └── 不合格 → 要求重试
     │              └── 不合格 → 当场拦下
     └── 合格 → 继续执行
```

四层叠加在一起形成完整的 Harness：

1. AI 可能会犯错
2. 但框架成为最终的兜底方案
3. 保证在 AI 出错时及时介入并要求修正

## 与 Prompt Engineering 的区别

| 维度 | Prompt Engineering | Harness Engineering |
|-----|-------------------|---------------------|
| 核心依赖 | 文字描述 | 代码执行 |
| 确定性 | 低（依赖模型理解） | 高（代码强制） |
| 错误处理 | 告诉 AI 请你别犯错 | 直接验收/限制 AI |
| 可绕过性 | 高（模型可能忽略） | 低（框架强制） |
| 优化方向 | 调措辞、写约束 | 搭执行框架 |

## 总结

Harness Engineering 的核心价值：

- **不是训练 AI 怎么想，而是用框架确保它不跑偏**
- **不调 prompt，不管上下文，而是搭执行框架让系统可靠运转**
- **四层保障叠加**：结构化定义 → 自动检查 → 测试验证 → Hook
- **本质**：AI 可能会犯错，但框架会成为最终的兜底方案
