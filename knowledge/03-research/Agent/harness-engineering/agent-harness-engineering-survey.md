# Agent Harness Engineering: A Survey — 可靠 AI Agent 背后的七层基础设施

## 论文基本信息

- **论文标题**: Agent Harness Engineering: A Survey
- **作者**: Anonymous Authors
- **发表**: Under review, TMLR, May 2026（综合 170+ 开源 Agent 系统及 ai-eval.org 深度解读）

---

## 一、技术背景

### 核心论断

> **对于长视距（long-horizon）LLM Agent，约束瓶颈往往不是基座模型本身，而是包裹模型的执行 Harness。**

一个能力强大的模型，如果 Harness 提供的上下文不足、工具接口脆弱、无持久化状态、沙箱不稳定、可观测性缺失、验证浅薄、或权限不安全，仍然会失败。反之，一个固定的模型，在 Harness 改善了规划、中间件、自验证、环境设置或故障恢复后，性能会显著提升。

**关键含义**：Agent 的基准测试分数是一个 **模型-Harness-环境** 系统的测量值，而不仅仅是模型性能。每次评估结果必须同时描述 Harness，而非仅描述模型和基准。

### 三阶段范式转换

| 阶段 | 优化目标 | 说明 |
|------|----------|------|
| **Prompt Engineering** | 发送给模型的词句 | 优化提问方式 |
| **Context Engineering** | 模型每步看到的信息 | 优化信息供给 |
| **Harness Engineering** | 整个运行时系统 | 执行环境、工具、记忆、编排、追踪、验证器、策略、预算、人工交接 |

### 认知外化理论

论文 *"Externalization in LLM Agents"*（Zhou et al., arXiv 2026.04）将 Harness 工程框架化为**认知外化**：

> Harness 将需要模型维护内部状态的任务——记忆、错误恢复、策略合规——转化为 Harness 以确定性方式管理的外部结构。

这就是为什么 Harness 工程能在不改变模型的情况下提升可靠性：**它将非确定性的认知负担卸载到确定性的基础设施上**。

## 二、技术内容详解

### ETCLOVG：七层 Harness 分类法

| 层级 | 全称 | 中文 | 类别 |
|------|------|------|------|
| **E** | Execution Environment | 执行环境 | 结构核心 |
| **T** | Tool Interface | 工具接口 | 结构核心 |
| **C** | Context & Memory Management | 上下文与记忆管理 | 结构核心 |
| **L** | Lifecycle & Orchestration | 生命周期与编排 | 结构核心 |
| **O** | Observability & Operations | 可观测性与运维 | 控制平面 |
| **V** | Verification & Evaluation | 验证与评估 | 控制平面 |
| **G** | Governance & Security | 治理与安全 | 控制平面 |

### 架构关系图

│  ┌─────────────────┐ ┌─────────────────┐ ┌───────────┐  │
│  │ O: 可观测性      │ │ V: 验证         │ │ G: 治理    │  │
│  │ 追踪/监控/成本   │ │ 质量门/错误检测  │ │ 策略/合规  │  │
│  └─────────────────┘ └─────────────────┘ └───────────┘  │
├─────────────────────────────────────────────────────────┤
│                    结 构 核 心                           │
│  ┌─────────────────┐ ┌─────────────────┐                │
│  │ E: 执行环境      │ │ T: 工具接口      │                │
│  │ 沙箱/隔离/资源   │ │ 注册/发现/权限   │                │
│  └─────────────────┘ └─────────────────┘                │
│  ┌─────────────────┐ ┌─────────────────┐                │
│  │ C: 上下文管理    │ │ L: 生命周期      │                │

### 结构核心 vs 控制平面

- **结构核心（E, T, C, L）** — 回答 "Harness 做**什么**"：管理执行、暴露工具、维护上下文、编排生命周期。没有它 Agent 无法运行。
- **控制平面（O, V, G）** — 回答 "Harness 如何随时间**保持正确性**"：使行为可见、在错误传播前捕获、强制执行 Agent 边界。没有它 Agent 无法安全运行。

**完整性判断标准**：
- 缺少任何一层的 Harness 是不完整的
- 缺少任何控制平面层的 Harness 是不适合生产环境的
- **仅包含结构核心（E, T, C, L）的 Agent 是原型；包含全部七层的是生产系统**

### E — 执行环境与沙箱

**职责**：管理运行时隔离、资源分配和沙箱化。这是 Agent 操作与宿主系统之间的物理边界。

#### 沙箱实现层级（隔离强度递增）

```
隔离强度:   弱 ◄──────────────────────► 强
资源开销:   低 ◄──────────────────────► 高

WebAssembly  →  Docker 容器  →  gVisor  →  Firecracker microVMs
(轻量纯计算)     (最常见)       (内核拦截)   (serverless 级)
```

#### 关键发现

- **SandboxEscapeBench**（Marchand et al., arXiv 2026）：量化了前沿 LLM 逃逸容器沙箱的能力——某些模型可机会主义地利用暴露的 Docker API 或过于宽松的挂载点
- **超过 60% 的开源 Harness 完全没有实现步骤上限**——这是一个可靠性缺陷而非功能缺失
- 资源管理关键措施：步骤限制（step ceiling）、递归深度边界、资源上限（CPU/内存/时间）

#### 代表性系统

- OpenHands（ICLR 2025）、AIOS（COLM 2025）、SWE-agent（NeurIPS 2024）

### T — 工具接口与协议

**职责**：控制 Agent 如何注册、发现和调用外部工具和 API。涵盖工具 schema 验证、版本管理、权限作用域、工具调用失败处理。

#### 关键原则

| 原则 | 说明 |
|------|------|
| **最小权限模型** | Agent 仅获得其声明任务所需的工具访问权，而非整个注册表 |
| **语义工具发现** | 生产级 Harness 实现带语义搜索的工具注册表：Agent 仅检索与当前子任务相关的工具 |
| **输出净化** | 在工具输出进入上下文之前进行净化，防御间接提示注入 |

#### 重要研究发现

- **ToolLLM**（Qin et al., ICLR 2024）：将所有可用工具倾倒到上下文中，在超过约 10 个工具时会因选择混淆而显著降低性能
- **Executable Code Actions**（Wang et al., ICML 2024）：允许 Agent 编写和执行任意代码作为工具操作，比限制在预定义函数签名中提升 **20-30%** 的任务成功率
- **Model Context Protocol (MCP, Anthropic 2024)**：已成为工具 schema 序列化的行业标准
- **间接提示注入**（InjecAgent, Zhan et al., 2024）：工具返回值中的恶意内容可以劫持 Agent 动作序列

### C — 上下文与记忆管理

**职责**：处理对话历史、工作记忆、长期记忆存储，以及管理每个推理步骤中上下文窗口内容的策略。

#### 三层记忆架构

```
┌──────────────────────────────────────────────┐
│              上下文管理策略                    │
│                                              │
│   ┌──────────────────────────┐               │
│   │  Working Memory（工作记忆）│              │
│   │  活动上下文窗口            │              │
│   │  滑动窗口 / 近因裁剪 / 压缩│               │
│   └──────────┬───────────────┘               │
│              │                               │
│    ┌─────────┴─────────┐                     │
│    ▼                   ▼                     │
│ ┌──────────┐    ┌──────────────┐             │
│ │Episodic  │    │  Semantic    │             │
│ │Memory    │    │  Memory      │             │
│ │情景记忆   │    │  语义记忆     │             │
│ │对话历史/  │    │  领域知识     │             │
│ │轨迹      │    │  向量存储     │             │
│ │MemGPT/   │    │              │             │
│ │Mem0 模式 │    │              │             │
│ └──────────┘    └──────────────┘             │
└──────────────────────────────────────────────┘
```

#### 关键研究发现

- **"Lost in the Middle"**（Liu et al., TACL 2024）：放置在长上下文中间的内容性能会下降——模型更可靠地关注开头和结尾。近因偏向的上下文裁剪不仅是 token 效率措施，更是可靠性措施
- **A-MEM**（Xu et al., NeurIPS 2025）：引入动态记忆图结构，根据观察到的任务模式主动重组记忆，优于静态检索

### L — 生命周期与编排

**职责**：处理任务调度、重试逻辑、检查点、子 Agent 委派和优雅终止。

#### 关键研究发现

- **"Hell or High Water"**（Wang et al., COLM 2025）：
  - 表征了 200+ 个失败场景的恢复策略
  - **在动作边界检查点**（每次确认的工具调用后保存 Agent 状态）比完全重启**提升 40% 的任务完成率**
  - 大多数开源 Harness 检查点频率过低或完全不实现
- **MetaGPT**（ICLR 2024）和 **CAMEL**（NeurIPS 2023）：结构化角色分配和显式消息传递协议优于自由形式的 Agent 通信

#### 生命周期反模式

> 无限重试失败工具调用——没有退避、断路器或升级——的 Harness 是可靠性隐患。ETCLOVG 调查发现这在 **43%** 的受调查开源系统中存在。

**正确模式**：最大重试次数 + 指数退避 + 优雅降级。

### O — 可观测性与运维

**职责**：涵盖推理步骤的结构化追踪、工具调用延迟、token 消耗、评估指标。

#### 三个可观测性层级

| 层级 | 内容 |
|------|------|
| **1. 轨迹日志** | 每个思考、工具调用和观察，带时间戳和 token 计数 |
| **2. 质量指标** | 任务成功率、步骤效率、幻觉率、工具错误率，按 Agent 版本跟踪 |
| **3. 运营指标** | 端到端延迟、每任务成本、重试率、超时频率（用于 SLO 监控） |

#### 行业现状

- **57%** 的组织在生产中运行 Agent（IJNRD 2025）
- 可观测性仍是 AI 栈中**评分最低**的部分
- 仅 **7-8%** 的公司报告拥有成熟的 Agent 治理
- 理想方向：**追踪原生评估**（trace-native evaluation），将生产追踪变为回归案例

### V — 验证与评估

**职责**：实现验证循环、错误检测和自修正。这是 Harness 的质量门——区别于模型自身的自我评估（在无外部脚手架时不可靠）。

#### 五阶段任务到反馈生命周期

```
┌──────────────────────────────────────────────────────────────┐
│  1. 任务与基准根基  →  2. 执行前就绪验证  →  3. 受控执行与追踪 │
│     定义任务/环境/成功标准     检查沙箱/依赖/权限/预算       捕获输出/工具调用/成本                       │
│                          ↓                                   │
│  4. 多层级评判与失败归因  →  5. 持续回归与部署反馈            │
│     评估结果/轨迹/评分器     将失败转化为回归测试套件           │
└──────────────────────────────────────────────────────────────┘
```

#### PALADIN 四种验证策略

| 策略 | 描述 |
|------|------|
| **语法验证** | 工具调用 schema 在执行前验证，而非之后 |
| **语义验证** | 输出对照预期类型和范围约束检查 |
| **Critic 模型验证** | 独立的轻量级模型在提交前评估动作是否正确 |
| **轨迹回滚** | 验证失败时，回滚到最后一个有效检查点并使用纠正性上下文重试 |

#### 关键发现

- **Life-Harness 系统**（Xu, Wen & Li, arXiv 2026.05）：
  - 将反复出现的交互失败转化为可复用组件
  - 在 126 个模型-环境配置中的 116 个上实现了 **88.5%** 的平均相对改进
  - 在一个模型上训练的 Harness **成功迁移到 17 个其他模型**
- **From Failed Trajectories**（arXiv 2026.06）：1,200 个失败轨迹中，**71% 的失败归因于 Harness 层缺陷**（缺失验证、错误的工具结果处理、上下文损坏），而非模型推理错误

### G — 治理与安全

**职责**：ETCLOVG 中最新的第一类层级，涵盖安全、合规和运营策略执行的全部范围。在**任何操作执行之前**约束 Agent 被允许做什么。

#### 治理的核心定义

> 治理策略是将 Agent 身份、部分执行路径、提议动作和组织上下文映射到策略违规概率的函数。（Kaptein, Khan & Podstavnychy, arXiv 2026.03）

**关键洞见**：治理是路径依赖的——在一个上下文中安全的动作在另一个上下文中是不安全的。静态访问控制和提示级指令只是更广泛运行时评估需求的特例。

#### SAGA 治理架构

```
┌──────────────┐     动作提案      ┌──────────────┐
│              │ ───────────────► │              │
│   Agent /    │                  │  Governance  │
│   LLM 模型   │                  │  Sidecar     │
│              │  ◄───────────── │  进程         │
│              │  批准/修改/阻止   │              │
└──────────────┘                  └──────┬───────┘
                                         │
                                   审计日志
                                         ▼
                                 ┌──────────────┐
                                 │  不可变      │
                                 │  审计 trail  │
                                 └──────────────┘
```

**SAGA**（Syros et al., NDSS 2026）：Sidecar 治理进程拦截每个动作提案，对照活跃策略评估，然后批准、修改或阻止——不经过模型的上下文窗口。

#### 四种核心治理机制

| 机制 | 描述 |
|------|------|
| **动作允许列表/拒绝列表** | 每个 Agent 角色的显式允许和禁止工具调用列表 |
| **数据边界执行** | Harness（非模型）强制执行 Agent 可读/写哪些数据源 |
| **人在环中触发器** | 可配置的阈值，在高风险操作上暂停执行并升级给人工 |
| **不可变审计日志** | 仅追加的追踪记录，捕获每个治理决策、其策略依据和结果 |

## 三、特别标签观点与核心关联内容

### 观点 1：瓶颈是 Harness 而非模型

- **标签**: `Harness-Bottleneck`, `Not-Model-Bottleneck`
- **核心论点**: 长视距 Agent 的约束瓶颈往往是包裹模型的执行 Harness，而非基座模型本身
- **关键证据**: 固定模型在 Harness 改善规划/中间件/自验证/环境设置/故障恢复后性能显著提升；71% 的失败归因于 Harness 层缺陷
- **深层含义**: Agent 性能优化的首要杠杆不是换模型，而是改进 Harness

### 观点 2：认知外化——Harness 工程的本质

- **标签**: `Cognitive-Externalization`, `Deterministic-Offload`
- **核心论点**: Harness 将需要模型维护内部状态的任务转化为确定性方式管理的外部结构
- **关键证据**: 记忆/错误恢复/策略合规等非确定性认知负担被卸载到确定性基础设施
- **深层含义**: 解释了为什么 Harness 工程能在不改变模型的情况下提升可靠性

### 观点 3：71% 的失败是 Harness 问题而非模型推理

- **标签**: `71Percent-Harness-Defect`, `Failure-Attribution`
- **核心论点**: 1,200 个失败 Agent 轨迹中，71% 归因于 Harness 层缺陷而非模型推理错误
- **关键证据**: 缺失验证、错误的工具结果处理、上下文损坏
- **深层含义**: 调 prompt 或换模型不是正确解法，修 Harness 才是

### 观点 4：模型-Harness 耦合——基准分数不可分离

- **标签**: `Model-Harness-Coupling`, `Benchmark-Inseparability`
- **核心论点**: Agent 的基准测试分数是模型-Harness-环境系统的测量值，无法分离模型性能
- **关键证据**: Harness 改善（工具 schema/上下文检索/沙箱稳定性/验证器严格度/重试循环）都影响分数
- **深层含义**: 每次评估结果必须同时描述 Harness，而非仅描述模型和基准

### 观点 5：结构核心是原型，控制平面是生产

- **标签**: `Prototype-vs-Production`, `Structural-Core-vs-Control-Plane`
- **核心论点**: 仅包含结构核心（E, T, C, L）的 Agent 是原型；包含全部七层的是生产系统
- **关键证据**: 控制平面（O, V, G）负责保持正确性——没有它无法安全运营
- **深层含义**: 控制平面不是可选的，它是 demo 和 deployment 之间的区别

### 观点 6：>60% 开源 Harness 无步骤上限

- **标签**: `60Percent-No-Step-Limit`, `Reliability-Gap`
- **核心论点**: 超过 60% 的开源 Harness 完全没有实现步骤上限
- **关键证据**: ETCLOVG 调查 170+ 开源系统
- **深层含义**: 这是一个可靠性缺陷而非功能缺失——无限循环是安全隐患

### 观点 7：动作边界检查点提升 40% 完成率

- **标签**: `40Percent-Checkpoint-Gain`, `Action-Boundary-Checkpoint`
- **核心论点**: 在动作边界检查点（每次确认的工具调用后保存 Agent 状态）比完全重启提升 40% 任务完成率
- **关键证据**: "Hell or High Water"（Wang et al., COLM 2025）200+ 失败场景
- **深层含义**: 大多数开源 Harness 检查点频率过低或完全不实现

### 观点 8：工具选择混淆——约 10 个工具阈值

- **标签**: `Tool-Choice-Confusion`, `10-Tool-Threshold`
- **核心论点**: 将所有可用工具倾倒到上下文中，在超过约 10 个工具时因选择混淆显著降低性能
- **关键证据**: ToolLLM（Qin et al., ICLR 2024）
- **深层含义**: 语义工具发现（按需检索）优于全量工具暴露

### 观点 9：Harness 跨模型迁移——训练一次部署 17 个模型

- **标签**: `Harness-Transferability`, `Cross-Model-Generalization`
- **核心论点**: 在一个模型上训练的 Harness 成功迁移到 17 个其他模型
- **关键证据**: Life-Harness（Xu, Wen & Li, arXiv 2026.05）——126 个配置中 116 个实现 88.5% 平均相对改进
- **深层含义**: Harness 层不变量具有跨模型通用性——投资 Harness 比投资模型更有复利效应

### 观点 10：治理是路径依赖的

- **标签**: `Path-Dependent-Governance`, `Governance-on-Paths`
- **核心论点**: 治理策略依赖于执行路径——在一个上下文中安全的动作在另一个上下文中是不安全的
- **关键证据**: SAGA（Syros et al., NDSS 2026）——静态访问控制和提示级指令只是运行时评估需求的特例
- **深层含义**: 侧车治理进程（sidecar）拦截动作提案，不经过模型上下文窗口，是比 prompt 指令更可靠的治理方式

## 五、总结与局限

### 总结

该论文是目前对 Agent Harness 工程作为一门生产学科最清晰的图谱之一：

1. **ETCLOVG 七层分类法**：结构核心（E/T/C/L）+ 控制平面（O/V/G）
2. **认知外化理论**：Harness 将非确定性认知负担卸载到确定性基础设施
3. **生产就绪标准**：七层完整 = 生产系统；仅结构核心 = 原型
4. **构建方法论**：每层检查清单 + 三大权衡（成本-质量-速度、能力-控制、框架-平台）

### 局限

- 作为综述，未提出新的实验验证
- ETCLOVG 分类法的层间耦合问题（一层改动影响其他层的测量）是工程挑战
- 可观测性仍是 AI 栈中评分最低的部分（仅 7-8% 公司成熟）

## 七、对实践的启示

1. **报告 Harness**：Agent 评估必须同时描述 Harness 配置
2. **先结构后控制**：先构建结构核心（E/T/C/L），在生产部署前添加控制平面（O/V/G）
3. **步骤上限是必需的**：无步骤上限 = 可靠性缺陷
4. **动作边界检查点**：每次确认的工具调用后保存状态
5. **语义工具发现**：按需检索而非全量暴露
6. **近因偏向的上下文裁剪**：可靠性措施，不只是 token 效率
7. **治理走侧车，不走 prompt**：侧车治理进程不经过模型上下文窗口，更可靠
8. **Harness 投资 > 模型投资**：Harness 可跨模型迁移，有复利效应
