## 1. 总体架构：两层主循环

```
┌────────────────────────────────────────────────────────────────────────────┐
│ 用户视角的"轮次" (turn)                                                     │
│  = 一对 (用户消息, 助手最终消息)                                            │
│  = 一次 submitMessage() 调用                                                │
│  = 可能包含 1..N 次 API 调用（query iteration）                            │
└────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ QueryEngine.submitMessage() — 一次 submit 包含的"内层循环"                  │
│  src/QueryEngine.ts:209                                                      │
│  启动：fetchSystemPromptParts() → 取 system prompt + user context           │
│  入口：for await (const message of query({...})) { yield message }          │
│  一个 submitMessage 通常会消费 query() 里的多次 iteration，                 │
│  直到模型不再 needFollowUp（即 stop_reason != tool_use 且无 tool_use 块）  │
└────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ query() 内的 while(true) iteration — "内层每一圈"                          │
│  src/query.ts:307                                                            │
│  每一圈 = 一次完整的"准备消息→发 API→执行工具→拼回 messages"                │
│  每一圈结束有 7 种 continue 路径（见 §12），决定是否继续下一圈               │
└────────────────────────────────────────────────────────────────────────────┘
```

**关键认识**：

- 用户输入一次 prompt，模型常常会触发 1~N 个 `tool_use` 块、每块都执行后回传 `tool_result`，模型基于新的 messages 再产生下一轮响应。
- 这"1 轮用户消息"在系统里被展开成 N 次 `queryLoop` 迭代。每次迭代都会重新拼 messages、调 API。
- **每次迭代都重新计算一次"该发给 API 的 messages"**，但绝大多数上下文是缓存命中复用，只有局部（新增的 tool_result、附件）会变化。

## 2. turn 与 query iteration 的区别

| 维度 | 用户视角的 "turn" | 内部的 "query iteration" |
|------|------------------|--------------------------|
| 触发者 | 用户输入（或子 agent 完成） | query.ts 的 while(true) |
| 入口 | `QueryEngine.submitMessage()` | `queryLoop` 的一圈 |
| 一次可能有多少 | 1 | 1..N（典型 1，可能 5-20，长任务可能上百） |
| 一次有多少 API call | N | 1 |
| 包含什么 | 用户文本 + 助手最终消息 + 中间所有 tool 消息 | 一次完整的"准备→发→收→执行→拼回" |
| 计数变量 | `turnCount` | 也是 `turnCount`（query.ts:213，每轮 +1） |
| 上限控制 | `maxTurns` 在 QueryEngine 层 | 也是 `maxTurns` 在 query.ts:1705 检查 |

**一个完整 turn 的事件序列**（典型场景：用户问"修一下 foo.ts 里的 bug"）：

```
turn 1: 用户消息
  iter 1:  send {user, claudeMd_prefix}
            ← {assistant: "我看一下 foo.ts", tool_use(Read)}
            → execute(Read)
            → 拼回 tool_result
  iter 2:  send {user, claudeMd, ..., assistant, user(Read result)}
            ← {assistant: "问题是 X，我来改", tool_use(Edit)}
            → execute(Edit)
  iter 3:  send {..., Edit result}
            ← {assistant: "改完了,顺便跑一下测试", tool_use(Bash)}
            → execute(Bash)
  iter 4:  send {..., Bash result}
            ← {assistant: "测试通过"}         ← stop_reason !== tool_use
            → query() return { reason: 'completed' }
            → submitMessage() 结束
turn 2: 用户消息 "再看看 bar.ts"
  ... 重新走一遍
```

## 4. 多轮复用：state.messages 与 mutableMessages

> 这是理解"多轮上下文"的根本：**state 是单一持续增长的数据结构，API 看到的 messages 是它的派生视图**。

### 4.1 两套状态指针

| 名称 | 位置 | 作用 | 是否影响 prompt cache |
|------|------|------|---------------------|
| `state.messages` | `src/query.ts:269`（query loop 内） | 当前 query() 内部累积的全部 messages | 是核心 cache prefix |
| `this.mutableMessages` | `src/QueryEngine.ts:186` | QueryEngine 整个生命周期内的 REPL 历史 | **不直接发 API**，但每次 submitMessage 时把它作为新 query() 的入参 → 直接变成 state.messages |

### 4.2 mutableMessages 的写入规则

`mutableMessages.push(...)` 仅在以下情况发生（`src/QueryEngine.ts:757-893`）：

- `case 'assistant'` — 真实 assistant 消息
- `case 'progress'` — bash/mcp 进度消息（**注意 push，写 transcript**）
- `case 'user'` — 真实 user 消息（real 文本或 tool_result）
- `case 'attachment'` — 各种附件（memory/conditional rules/skill discovery 等）
- `case 'system'` — 主要是 `compact_boundary`（push，且触发 splice 清空边界前内容）
- `case 'tombstone'` — **不 push**（控制信号，用于移除消息）

**关键点**：

- `prependUserContext` 插入的 Rules 消息是 `isMeta`，**永远不 push 到 mutableMessages** —— 它只作为每轮 API 调用的参数。
- Tool result 也不直接 push：它是从 query() 内部 yield 上来后被 `case 'user'` 分支 push 进去。
- 同样的，附件消息（`attachment` type）也 push —— 它们就成为了历史的一部分。

### 4.3 跨 submitMessage 的状态延续

```
submitMessage #1:
  this.mutableMessages = [u0]               // 用户初始消息
  → query() 内部把 state.messages 初始化成 [u0]
  → 走 N 圈后，appendCompactBoundary 触发 splice
  → mutableMessages = [boundary, summary, ...u0, ...全部新消息]
  → submitMessage 结束
submitMessage #2:
  this.mutableMessages = [boundary, summary, ...]   // 继承上次末尾
  → query() 拿它做入参
  → 走 M 圈后 yield 出来更多消息
  → mutableMessages 继续增长
```

**这就是"上下文管理"的核心**：每轮 iteration 的 messages 列表 = `getMessagesAfterCompactBoundary(state.messages)`，但 state.messages 本身是**单调增长**的（只有 compact boundary 触发 splice 才收缩）。

## 7. 工具调用：流式 vs 批量、并发、断流

### 7.1 两条调度路径

| 路径 | 启用条件 | 入口 | 行为 |
|------|---------|------|------|
| **流式执行** | `config.gates.streamingToolExecution`（Statsig gate）| `StreamingToolExecutor` (`src/services/tools/StreamingToolExecutor.ts`) | tool_use 块**一到达**就入队并执行（不等流结束） |
| **批量执行** | 默认 | `runTools` (`src/services/tools/toolOrchestration.ts`) | 等完整 assistant 消息收齐后，**一次性**调度所有 tool |

流式是性能优化：模型还在流下一个 tool_use 块时，前面的 Read 已经在跑了，节省 wall-clock 时间。

### 7.2 流式执行器的状态机

`StreamingToolExecutor` 对每个 tool_use 块维护一个状态机：

```
   addTool(block)
      │
      ▼
  ┌─────────┐
  │ queued  │ ──→ 检查 canExecuteTool()
  └─────────┘          │
      │               ├── exclusive (non-concurrent) 工具在前
      ▼               │       └── 等所有 executing 完才执行
  ┌──────────┐         │
  │executing │ ←───────┘
  └──────────┘
      │
      ▼
  ┌──────────┐  getCompletedResults() yield 出 result + 置 'yielded'
  │completed │
  └──────────┘
```

**关键约束**：

- `isConcurrencySafe` 返回 true 的工具（如 Read/Grep/Glob）和别的 concurrency-safe 工具**并行**。
- `isConcurrencySafe` 返回 false 的工具（Edit/Write/Bash）**独占**一批——必须等所有正在执行的工具结束。
- Bash 失败 → 整批 sibling 工具收到 `sibling_error`，提前 cancel。

### 7.3 异常处理与"missing tool_result"兜底

当流被打断或 fallback 时，必须保证 `tool_use ↔ tool_result` 配对（API 强制要求）。机制：

- **Streaming abort**: `src/query.ts:1015-1052` — 若 abort 触发，生成 `<tool_use_error>` 形式的 synthetic tool_result。
- **Streaming fallback** (e.g. 模型从 1P 切到 fallback): `src/query.ts:712-741` — 用 `tombstone` 移除所有已 part-collected 的 assistant 消息，discard executor，重建。
- **正常完成但有部分工具失败**: `createSyntheticErrorMessage(toolId, 'sibling_error')` 生成 isError=true 的 tool_result。
- **用户拒接 (ESC)**: 用 `REJECT_MESSAGE`（不是通用 error 文本）让 UI 知道是用户行为而非系统错误。

### 7.4 工具执行后的状态更新

`runToolUse`（`src/services/tools/toolExecution.ts`）每执行一个工具：

1. 调用工具的 `call()`，yield `MessageUpdate { message, newContext? }`
2. 每个 message push 到 `toolResults` 数组（在 query.ts 内）
3. contextModifier（如果工具提供）合并到 `toolUseContext`（影响后续工具）
4. **进度消息**（bash output、agent progress）会走 `pendingProgress`，立即 yield，**不进 toolResults**，不进 API，但写 transcript

`toolUseContext` 的关键字段：

- `messages` — 当前的 `messagesForQuery`（query.ts 末尾更新）
- `options.tools` — 可用工具列表（`refreshTools()` 可热更新）
- `readFileState` — Read 工具写入此缓存，其他工具可以查"模型是否读过这个文件"
- `nestedMemoryAttachmentTriggers` / `loadedNestedMemoryPaths` — nested CLAUDE.md 注入
- `dynamicSkillDirTriggers` / `discoveredSkillNames` — 动态技能发现
- `contentReplacementState` — tool_result 持久化状态

## 8. tool_result 的多层预算机制

> 这是"上下文"层面最复杂的部分。tool_result 体积常常爆炸（Read 整个 src/、Bash 输出 100K 行），所以有**5 层递进的预算**。

### 8.1 第 1 层：单工具自身的 `maxResultSizeChars`

每个工具在 `Tool` 接口里声明 `maxResultSizeChars`（参见 `src/Tool.ts`）。例如 Read 是 `Infinity`（由 Read 自己的 `maxTokens` 控制），Bash 有具体上限。

`src/utils/toolResultStorage.ts:55-78` 的 `getPersistenceThreshold` 决定此工具的结果超过多少字符就持久化到磁盘。

### 8.2 第 2 层：每 message 的总预算

`applyToolResultBudget`（`src/utils/toolResultStorage.ts:769-909`）：

```
每个 user message 内 所有 tool_result 块的总字符数
   > MAX_TOOL_RESULTS_PER_MESSAGE_CHARS (默认 50000 字符)
      → 选最大的 fresh tool_result 持久化到磁盘
      → 替换为 preview（"<persisted-output>\n... first 2KB ..."
                          + path hint\n...</persisted-output>"）
```

**关键设计**：

- **Stable 状态**：`ContentReplacementState`（`seenIds` + `replacements`）跨轮持久。一旦一个 tool_use_id 被处理过，它的命运就 frozen：
  - 被替换过 → 之后每轮从 `replacements.get(id)` 重新 apply，**byte-identical**
  - 没被替换过 → 之后每轮都跳过（避免破坏 cache prefix）
- **分组逻辑**：必须按 wire-level 消息分组（合并相邻 user 消息），否则并发 tool 结果会被误判。
- **Skip 集合**：`maxResultSizeChars = Infinity`（如 Read）的工具永远不被这一层持久化。

### 8.3 第 3 层：Time-based Microcompact

`src/services/compact/microCompact.ts:446-529`：

- 触发：`now - lastAssistantTimestamp > 60 min`（cache TTL 已冷）
- 效果：清空所有可压缩 tool_result（除了最近 keepRecent=5 个），content 设为 `"[Old tool result content cleared]"`
- **关键**：不动 message 数组，但清空 content 字段——wire 上更轻

### 8.4 第 4 层：Cached Microcompact（ant-only）

`src/services/compact/cachedMicrocompact.ts` (stubs 显示 ant-only)：

- **不修改 messages 本体**
- 在 API 调用时插入 `cache_reference` 和 `cache_edits` 块，让服务端删除旧 tool_result 而**保留 cache prefix**
- 触发阈值由 GrowthBook 配置（triggerThreshold）
- 状态：模块级 `cachedMCState` 跟踪已注册的工具 ID、删除状态
- 跨轮：同 ID 不会重复删除

### 8.5 第 5 层：Context Collapse（ant-only）

`src/services/contextCollapse/index.ts` (stubs 显示 ant-only)：

- **最细粒度**：可对单个 tool_result commit 折叠
- 投影视图：`projectView()` 在读时按需展开已折叠的内容
- 90% 上下文时 commit，95% 时 blocking spawn 折叠
- 跨轮：commit log 持久化，REPL 状态继续增长但 API 视图不增长

### 8.6 第 6 层：Auto-Compact（最重）

`src/services/compact/autoCompact.ts` + `compact.ts`：

- 触发：token count ≥ `effectiveContextWindow - 13k`
- 流程：`trySessionMemoryCompaction`（优先）→ `compactConversation`（fork agent 生成 summary）
- 输出：`buildPostCompactMessages()` 构造的 `[boundary, summaryMessages, messagesToKeep, attachments, hookResults]`
- 边界后**清空** REPL state 的 pre-boundary 部分（src/QueryEngine.ts:925-933）

### 8.7 总结：预算层级

```
每轮 iteration 顺序执行：

1. toolResultBudget  ──  超 50K/msg  → 持久化到磁盘
                                  (这层最细粒度、最先)
2. snip compact      ──  长程历史的 message 投影掉
3. microcompact      ──  旧 tool_result 清空（time-based）
                     ─  旧 tool_result 标记 cache_edits（cached）
4. context collapse  ──  按需 commit 单个 tool_result 折叠
5. auto-compact      ──  超 13K 缓冲   → fork agent 总结
                     (这层最重、最后)
```

每一层都不重做上层的事；越往上越暴力。

## 9. 压缩栈：microcompact / autocompact / reactive / snip / collapse / token-budget

### 9.1 全景对比

| 机制 | 文件 | 触发条件 | 影响范围 | 持久性 | 风险/权衡 |
|------|------|---------|---------|--------|----------|
| **Tool Result Budget** | `src/utils/toolResultStorage.ts` | 每 message 工具结果 > 50K 字符 | 单个 user message | 持久化到磁盘；state frozen 跨轮 | 替换预览可能丢失细节 |
| **Time-based MC** | `src/services/compact/microCompact.ts:446` | 距 lastAssistant > 60 min | 所有可压缩 tool_result | 清空 content（[Old tool result cleared]） | 模型看不到旧内容 |
| **Cached MC** (ant) | `src/services/compact/cachedMicrocompact.ts` | 累计数 > GrowthBook 阈值 | API 层删旧 tool | cache_edits 服务端做 | 1P ant-only |
| **Context Collapse** (ant) | `src/services/contextCollapse/index.ts` | 90%/95% 上下文 | 按需 commit 单 tool | commit log 持久 | ant-only |
| **Snip Compact** (ant) | `src/services/compact/snipCompact.ts` | 由 snip tool 显式触发 | 整条 message 投影 | projection-based | ant-only |
| **Auto-Compact** | `src/services/compact/autoCompact.ts` | token > threshold - 13K | 整段历史 fork 总结 | splice mutableMessages | 损失细粒度 |
| **Reactive Compact** (ant) | `src/services/compact/reactiveCompact.ts` | API 返回 413 prompt-too-long | 整段历史 | splice + retry | 抢救失败 turn |
| **Token Budget** | `src/query/tokenBudget.ts` | turn tokens < budget × 0.9 | 注入 nudge | nudge message | 提示继续 |

`checkTokenBudget` (`src/query/tokenBudget.ts:45`)：

- 行为：注入 `nudgeMessage`（如"you're at 60% of budget, keep going"）到 messages 末尾，continue 下一圈
- 终止条件：达到 90% 或 diminishing returns → 停止

### 9.5 状态机：每圈的 continue 决策

`src/query.ts:307-1729` 的 while 循环每圈有 **7 种 continue 路径**：

| 决策 | 触发 | 处理 | 来源 |
|------|------|------|------|
| `next_turn` | 正常 — tool 跑完要再发 API | 把 assistant+tool_results 拼回 | 末尾默认 |
| `collapse_drain_retry` | 收到 413，先尝试 drain 阶段折叠 | drainContextCollapses + retry | line 1114 |
| `reactive_compact_retry` | reactive 压缩成功 | 用 postCompactMessages 重试 | line 1162 |
| `max_output_tokens_escalate` | model 输出到 8K cap 上限 | 用 ESCALATED_MAX_TOKENS (64K) 重试 | line 1217 |
| `max_output_tokens_recovery` | 输出到顶 | 注入"Resume directly"提示继续 | line 1246 |
| `stop_hook_blocking` | stop hooks 阻塞 | 注入 blocking errors 继续 | line 1302 |
| `token_budget_continuation` | turn tokens < 90% budget | 注入 nudge message 继续 | line 1338 |

**重要的"不要继续"路径**：

- `aborted_streaming` / `aborted_tools` — 用户 Ctrl+C
- `completed` — 正常完成（无 tool_use）
- `blocking_limit` — 接近 hard limit（无 auto-compact）
- `prompt_too_long` — reactive 也救不了
- `image_error` — 媒体错误
- `max_turns` — 到达上限
- `stop_hook_prevented` — stop hook 阻止
- `model_error` — 模型错误
- `hook_stopped` — 工具 hook 阻止继续

## 10. prompt caching：边界、scope、失效检测

### 10.1 Cache Scope 决策

`src/utils/api.ts:321` 的 `splitSysPromptPrefix`：

```typescript
export function splitSysPromptPrefix(
  systemPrompt: SystemPrompt,
  options?: { skipGlobalCacheForSystemPrompt?: boolean },
): SystemPromptBlock[]
```

行为取决于：

1. **MCP 工具是否存在** → `skipGlobalCacheForSystemPrompt = true`
   - 3 块：attribution(org) + prefix(org) + rest(org)
2. **Global cache + boundary marker found** (1P only)
   - 4 块：attribution(null) + prefix(null) + static(global) + dynamic(null)
3. **3P providers / no boundary**
   - 3 块：attribution(org) + prefix(org) + rest(org)

### 10.2 Dynamic Boundary Marker

`SYSTEM_PROMPT_DYNAMIC_BOUNDARY`（`src/constants/prompts.ts`）作为静态/动态段的分隔符：

```
[attribution header]
[CLI prefix]
────────────  SYSTEM_PROMPT_DYNAMIC_BOUNDARY  ────────────
[intro section]        ← static
[system section]       ← static
[doing tasks section]  ← static
[actions section]      ← static
[tools section]        ← static
[output style]         ← static
────────────  之后是动态段  ────────────
[session_guidance]     ← dynamic (含 skill list)
[memory]               ← dynamic
[env_info_simple]      ← dynamic
[language]             ← dynamic (若用户设了语言)
[mcp_instructions]     ← dynamic (DANGEROUS_uncached)
```

`session_guidance` 包含 **skill 元数据列表**（每轮重新扫描），所以必须在 dynamic 段，不能进 global cache。

### 10.3 Cache 失效检测

`src/services/api/promptCacheBreakDetection.ts` (隐含引用)：

- **正常 cache read drop 视为** break
- `notifyCompaction(querySource, agentId)` 在 compact 后调用 → 重置 baseline
- `notifyCacheDeletion(querySource)` 在 cached MC 后调用 → 重置 baseline
- `notifyCacheWrite(trackingKey, ...)` 在新 turn 写入时

**目的**：监控 5xx env 下的"实际 cache 命中率"，把正常的"compact 必然导致 read drop"和真实的"env bug 导致的 cache 失效"区分开。

### 10.4 Tools 缓存策略

`src/utils/api.ts:119-209` 的 `toolToAPISchema`：

- **Session-stable base schema** 通过 `getToolSchemaCache()` 缓存（name + description + input_schema + strict + eager_input_streaming）
- **Per-request overlay**：`cache_control`（含 scope/ttl）、`defer_loading` 每次可以不同
- 这避免了 mid-session GrowthBook flip（`tengu_tool_pear`、`tengu_fgts`）或 `tool.prompt()` 漂移把整个 tools 数组重写

### 10.5 Tool Schema 缓存键

```typescript
const cacheKey =
  'inputJSONSchema' in tool && tool.inputJSONSchema
    ? `${tool.name}:${jsonStringify(tool.inputJSONSchema)}`
    : tool.name
```

- 普通工具 → `tool.name`
- StructuredOutput 工具（同名不同 schema）→ `name:jsonStringify(schema)`（PR#25424 修复 5.4% → 51% 错误率）

### 10.6 整体 cache 命中策略

| 数据 | 缓存策略 | 失效时机 |
|------|---------|---------|
| System prompt 静态段 | `cacheScope='global'` 跨 session | DCE/growthbook flip |
| System prompt 动态段 | `cacheScope=null` 不缓存 | 每轮 |
| User context (Rules) | `cacheScope=null`（per-call） | `/clear`、`/compact` |
| Tools schema base | `toolSchemaCache` per session | per turn 重新组装 |
| Tool result 替换 | `replacements.get(id)` byte-identical | 永不 |
| Compact boundary 后 messages | 由 API 缓存自动管理 | 每次微调 |
| File state (Read 缓存) | `fileStateCache` LRU，per session | 100 entry / 25MB cap |

## 11. 附件注入：每轮根据"刚刚发生了什么"动态拼入

> 这是除了 Rules/Skills/Commands 之外的另一类"per-turn 动态注入"。每轮 iteration 末尾（src/query.ts:1580-1628）会从 `getAttachmentMessages` 拿到一组"上下文相关的附件"。

### 11.1 附件来源

`src/utils/attachments.ts` 集中管理。`getAttachmentMessages()` 是个 AsyncGenerator，依次 yield：

| 附件类型 | 触发 | 作用 |
|---------|------|------|
| **memory** | 有 AutoMem 路径 | 注入 MEMORY.md 内容 |
| **conditional_rules** | 本轮涉及新路径 | 匹配 paths globs 的 rules 注入 |
| **nested_memory** | 本轮 Read/Edit 进入新子目录 | 子目录的 CLAUDE.md 注入 |
| **skill_discovery** | EXPERIMENTAL_SKILL_SEARCH | 基于任务上下文的 skill 提示 |
| **agent_listing** | AgentTool 可用 | 当前可用 agent 列表 |
| **deferred_tools_delta** | 工具集变化 | 新连接 MCP / 新加载工具 |
| **mcp_instructions_delta** | MCP 客户端变化 | 新 MCP 服务器指令 |
| **edited_text_file** / **edited_image_file** | 文件操作 | 变更摘要（防止 stale edit） |
| **max_turns_reached** | 到达 maxTurns | 通知用户 |
| **queued_command** | 用户排队了 prompt | 作为新 user 消息 |
| **todo_reminder** | N turns 没更新 todo | 提醒更新 todo |
| **plan_mode_reminder** | plan mode 持续 | 提醒还处于 plan 模式 |
| **auto_mode_reminder** | auto mode 持续 | 提醒模式 |
| **ide_selection** | IDE 选中文字 | 注入选中内容 |
| **hook_additional_context** | hook 注入 | 任意附加上下文 |
| **brief** | KAIROS 简报 | 任务简报 |

### 11.2 条件 Rules 的特殊处理

`src/utils/claudemd.ts`（参见前作报告）：

- `paths: "src/**/*.ts"` 声明的 rules **不直接进 system prompt**
- 而是在每轮 attachment 阶段，根据本轮 Read/Write/Edit 的文件路径匹配 globs
- 匹配成功的 rule 才作为附件注入当前轮

这样可以避免无条件 Rules 占用大量 context，而按需激活。

### 11.3 已读/已编辑文件状态

`readFileState`（`src/utils/fileStateCache.ts:30-142`）：

- LRU cache（默认 100 entries / 25MB）
- 每次 Read/Write 工具写入
- 在 Edit/Write 工具里被 check：模型是否"见过"这个文件
- 在 compact 后被 clear（compact 后模型对历史文件状态不可见）
- 同一文件重复 Read 不会重新注入内容（仅显示 "Already read"）

### 11.4 Conditional Skill 激活

`src/skills/loadSkillsDir.ts:997` 的 `activateConditionalSkillsForPaths(filePaths, cwd)`：

- 类似 conditional rules，但针对 skills
- 本轮 Read/Edit 涉及的路径若匹配 skill 的 `paths` glob，则把 skill 标记为"已激活"
- 在 `getSkillToolCommands()` 中激活的 skill 会被模型看到

### 11.5 Memory Prefetch (异步优化)

```typescript
// src/query.ts:301-304
using pendingMemoryPrefetch = startRelevantMemoryPrefetch(
  state.messages, state.toolUseContext,
)
```

`pendingMemoryPrefetch` 是一个 `using`-managed 资源：

- 在 query() 入口**启动**后台 prefetch（基于本轮消息预测哪些 memory 会被需要）
- 在工具执行**期间**继续 prefetch
- 在每轮 iteration 末尾**消费**（如已 settled 且本轮未消费）

类似地 `skillPrefetch?.startSkillDiscoveryPrefetch(...)` 处理 skill discovery 的预取。

### A.1 关键时序点

- **mutableMessages 增长节奏**：每个 assistant / user / attachment / progress / system 都 push（tombstone 不 push）
- **每轮 API request 是"临时视图"**：从 mutableMessages 派生，做了 5-6 层 shrink，再拼回用户上下文
- **压缩是"重置"边界**：compact boundary 之前的所有 mutableMessages 元素被 splice 删掉
- **跨 turn 状态只通过 ToolUseContext 传递**：replacement state / read state / nested memory paths / skill discoveries

### A.2 性能开销

每轮 iteration 都要做的同步操作：

1. `getMessagesAfterCompactBoundary` — O(n) 反向 scan 找 boundary
2. `applyToolResultBudget` — O(n×blocks) scan messages 找 candidates
3. `normalizeMessagesForAPI` — O(n) 多 pass：过滤、合并、规范化
4. `ensureToolResultPairing` — 反向 walk 检查
5. `validateImagesForAPI` — 检查图片
6. `getToolPermissionContext` — async fn
7. `getCLISyspromptPrefix` — 字符串组装
8. `splitSysPromptPrefix` — 字符串切分
9. JSON.stringify 整条 messages 数组（请求体）

异步操作：

- `getAttachmentMessages` — 各种 dynamic context 的 I/O
- `getMainLoopModel` / `getRuntimeMainLoopModel` — model 解析
- `mcp.tools` / `appState.mcp.clients` — 状态读取
- `getMainLoopModel` — 视情况读 Statsig

每轮 overhead 大约 1-5ms（不计算 API 调用）。长 session（>1000 messages）时这部分可能成为瓶颈。

## 附录 D：投影 / 替换 / 压缩 —— 一个具体例子的完整走查

> 本附录用一个最简单的例子，帮读者把"投影 / 替换 / 预算 / 压缩"这几个容易混淆的概念理清。

### D.1 场景设定

```
turn 1:  "请阅读 src/api.ts, src/db.ts, src/auth.ts, src/utils.ts, src/types.ts 这 5 个文件"
turn 2:  "第 3 个文件里的 handleAuth 函数有什么问题？"
turn 3:  "改一下"
```

执行后，REPL state 里躺着 5 个 Read tool_result，每个 80KB 字符（共 400KB）。
现在你问：**"系统是怎么把这一堆东西喂给模型的？"**

### D.2 工具的预算（Tool Result Budget）

**核心思想**：单条消息里的 tool_result 加起来不能超过 ~50K 字符。

假设某条 user message 长这样：

```
[
  { type: 'tool_result', tool_use_id: 'tu_1', content: '<文件 1 的 80KB 内容>' },
  { type: 'tool_result', tool_use_id: 'tu_2', content: '<文件 2 的 80KB 内容>' },
  { type: 'tool_result', tool_use_id: 'tu_3', content: '<文件 3 的 80KB 内容>' },
]
   共 240KB >> 50K
```

`applyToolResultBudget` 处理：

```
1. 系统挑出最大的 tool_result（这里 3 个一样大，挑 tu_1）
2. 把 tu_1 的完整内容写入磁盘：
   ~/.cline/data/workspaces/<hash>/tool-results/tu_1.txt
3. 把 tu_1 在消息里替换成 preview：

   原：
   content: '<import { foo } from "...";\n ... 80KB 完整代码 ...>'

   改为：
   content: '<persisted-output>
              Output too large (80.0 KB). Full output saved to:
              /Users/you/.cline/data/.../tool-results/tu_1.txt
              Preview (first 2.0 KB):
              <import { foo } from "...";
               ... 只保留前 2KB ...
              </persisted-output>'

4. 把"已处理过 tu_1"记到 seenIds Set 里
5. 把"tu_1 的替换字符串"记到 replacements Map
   （用于下轮 byte-identical 重放，详见 D.4）
```

### D.3 投影（Projection）

**核心思想**：REPL state 里**仍然保留**完整数据，但**这次不发**给 API。下次需要时再"投影回来"。

打个比方：你书架上有 1000 本书，但你现在写作只需要参考其中 50 本。你**没有把另外 950 本扔掉**（扔了就没了），只是**暂时从桌面上收起来**到看不见的柜子里。

代码里三种"投影"：

#### (a) Snip 投影

`projectSnippedView(messages)` —— 拿 messages 数组，过滤掉"被 snip 标记"的，剩余的返回。但 **REPL state 完全没动**。

```
REPL state 实际内容（你看 UI 时）:
  [u0, asst1, tu_1(read result), asst2, tu_2(grep result), asst3, tu_3, asst4, ...]
   ~~~~~~~~~  ★ 这一段被 snip 工具标记为"可剪"  ~~~~~~~~~~

发给 API 的视图（投影后）:
  [u0, asst1, [id:abc123], asst4, ...]   ← 整段被一个短 ID 替代

模型看到的 [id:abc123] 标记，仍然能引用到被 snip 掉的 tu_2 内容
（如果它还记得的话）—— 投影是"把细节藏起来"而不是"删除"
```

#### (b) Context Collapse 投影

`projectView()` —— 类似的"读时投影"，把已 commit 折叠的 tool_result 在这次 API 调用里替换成短 placeholder。

```
REPL state 实际:
  [u0, asst1, tu_readFile_1(80KB), asst2, tu_readFile_2(80KB), ...]

投影前（看到的样子）:
  [u0, asst1, "Preview of file 1 (2KB)...", asst2, "Preview of file 2 (2KB)..."]

投影后（实际发给 API）:
  [u0, asst1, [id:fold1], asst2, [id:fold2], ...]
```

**REPL state 完全没变**，但 API 看到的消息"短了"。

#### (c) Compact boundary 投影

`getMessagesAfterCompactBoundary(messages)` —— 严格说是切片，但思想类似：

```
REPL state 实际:
  [u0, asst1, ..., asst100, BOUNDARY, summary, asst_after_1, asst_after_2, ...]
                                  ↑ 这里之前都被 fork agent 总结过

切片结果（发 API）:
  [BOUNDARY, summary, asst_after_1, asst_after_2, ...]
```

### D.4 替换（Replacement）—— 与投影的根本区别

替换是**真的改了 state**（不可逆），跟投影完全不同。

对比：

| 操作 | 数据在 REPL 还在吗？ | 数据在磁盘？ | 发给 API？ |
|------|------------------|----------|----------|
| **预算+替换**（applyToolResultBudget）| ✅（preview 字符串）| ✅（完整内容）| ✅（小预览）|
| **投影**（snip / collapse）| ✅（完整内容）| ❌ | ❌（短 ID 代替）|
| **压缩**（autoCompact）| ❌（被 splice 删除）| ❌（除非 session log）| ✅（summary）|

**关键点**：`applyToolResultBudget` 的"替换"是**单向、永久**的。一旦 tu_1 被替换成 preview：

- 之后每轮 iteration 都会从 `replacements.get('tu_1')` 取回**同样的字符串**塞回去
- 绝不会重新计算 preview（否则 prompt cache 会因为 byte mismatch 而 miss）
- 这就是 `ContentReplacementState.frozen` 的设计

### D.5 压缩（Compression）—— 最暴力的一层

**核心思想**：**真的把旧内容扔掉**，换成一段 summary。

```
turn 1: 读 5 个文件，REPL state 增长到 400KB
turn 2: 改文件
turn 3: 跑测试
...
turn 30: REPL state 累计 1MB, token 数 = 950K（假设窗口 1M）

→ tokenCountWithEstimation(messages) >= 980K 阈值
→ 触发 autoCompact：

   1) fork 一个临时 agent（独立 context）
   2) 把整个 messages 喂给它
   3) 让它生成一段"对话摘要"（~3-5K tokens）
   4) 拿到 summary 后，主循环 yield:
      - SystemMessage { type: 'compact_boundary', ... }
      - UserMessage { isCompactSummary: true, content: '<summary>' }
      - 一些 hooks 结果 / attachments

   REPL state 改造前后：
   改造前: [u0, asst1, tu1, asst2, tu2, ..., asst30]   ← 1MB
   改造后: [BOUNDARY, summary, asst30]                  ← 5KB

   关键: BOUNDARY 之前的 [u0, asst1, ..., asst29] 全部从 mutableMessages 里 splice 删除
         （src/QueryEngine.ts:925-933）
```

### D.6 总结：执行顺序（每轮 iteration 开头）

```
state.messages（原始 REPL 状态）
  ↓ ① applyToolResultBudget
     大的 tool_result → 替换成 preview + 写磁盘
     （这是"替换"，不是"投影"）
  ↓ ② snip 投影（默认不启用）
     被 snip 的 message → 投影掉（state 不变）
  ↓ ③ microcompact
     旧的 tool_result.content → 清成 "[Old cleared]"
     （这是"清空"，也不完全是"替换"或"投影"）
  ↓ ④ collapse 投影（ant-only，90% 触发）
     已 commit 折叠的 tool_result → 投影掉（state 不变）
  ↓ ⑤ autoCompact（token > 阈值时触发）
     整段历史 → 总结 + splice 删除
     （这是"压缩"，不可逆）
  ↓ ⑥ normalizeMessagesForAPI（12 步规范化）
  ↓ ⑦ prependUserContext（Rules 注入为 isMeta user 消息）
  ↓ 发 API
```

### D.7 现实类比

| 机制 | 类比 |
|------|------|
| **投影** | 看书时把不相关的章节用书签夹起来放一边，没翻到就先不看 |
| **替换** | 翻拍一张照片存档，桌上只放小照片（原始细节在硬盘）|
| **压缩** | 写一份读书笔记，原始章节扔进废纸篓 |
| **预算** | 桌面上只允许摊开 5 本书，否则必须先把某本收起来 |

希望这能把这几个概念彻底分开！

## 附录 E：压缩顺序与 Read 工具豁免——避免"永远看不到大文件"的设计决策

> 本附录回答三个常见的"想通了还是绕不出来"的问题：压缩/替换的顺序是什么？re-read 同一个文件会再压缩吗？为什么 Read 工具是个例外？

### E.1 顺序：先压缩，再给模型思考

**模型在 tool_result 产生的下一圈**就会看到压缩后的内容。从未在 API 上看到过 80KB 完整内容。

```
Turn 1 iter 1:
  Read(auth.ts)  →  80KB tool_result (tu_1)
                   ↓  push 到 state.messages
  iter 1 结束

Turn 1 iter 2 开始:
  B. messagesForQuery = [...getMessagesAfterCompactBoundary(state.messages)]
         ↑ 包含 80KB tu_1

  C. applyToolResultBudget(messagesForQuery, ...)
     发现 tu_1 80KB  >  50K 阈值
     → 写入磁盘：~/.cline/data/.../tool-results/tu_1.txt
     → 替换为 2KB preview
     → seenIds.add('tu_1')，replacements.set('tu_1', preview)

  I. API call
     messages = [userContext_meta, u0, asst, u(preview 2KB)]
                                ↑ 模型看到这个，不是 80KB
```

### E.2 重新读大文件：Read 工具的豁免

`src/utils/toolResultStorage.ts:60-65`：

```typescript
export function getPersistenceThreshold(
  toolName: string,
  declaredMaxResultSizeChars: number,
): number {
  // Infinity = hard opt-out. Read self-bounds via maxTokens; persisting its
  // output to a file the model reads back with Read is circular. Checked
  // before the GB override so tengu_satin_quoll can't force it back on.
  if (!Number.isFinite(declaredMaxResultSizeChars)) {
    return declaredMaxResultSizeChars
  }
}
```

**Read 工具的 `maxResultSizeChars = Infinity`**。`src/query.ts:389-393` 把这类工具加进 `skipToolNames`，在 `applyToolResultBudget` 里**跳过**。

```
模型 Read(/.../tool-results/tu_1.txt)  →  80KB tool_result (tu_2)
   ↓
下一圈 applyToolResultBudget
   tu_2 的工具是 Read → 在 skipToolNames 里 → 跳过！
   80KB 完整传给模型 ✅
```

**这是有意为之**：如果 Read 工具自己的输出也被压缩，那"压缩→读 txt→再压缩→再读 txt"就成了**真正死循环**——模型永远看不到完整内容。注释里就直说了。

### E.3 re-read 同一源文件：fileStateCache 短路

**但是**，如果模型对**同一源文件**（如 auth.ts）再次 Read：

```
Read(auth.ts) [第一次]
   ↓
fileState.set('/path/auth.ts', { content, timestamp })
   ↓
返回 80KB

Read(auth.ts) [第二次]
   ↓
fileState.get('/path/auth.ts') → 命中
   ↓
返回简短 "Already read"
   不返回 80KB
```

`fileStateCache` 是 LRU 100 entries / 25MB，专门挡"读过的再读"。

### E.4 用 Bash 读 txt 会怎样？

如果模型不用 Read 而用 `Bash("cat /.../tu_1.txt")`：

```
Bash 输出 80KB → tool_result (tu_N)
   ↓
下一圈 applyToolResultBudget
   tu_N 的工具是 Bash，不在 skipToolNames → **被替换！**
   又一次 80KB → 2KB preview，写到 tu_N.txt（新文件）
```

**但 SHELL_TOOL_NAMES 在 COMPACTABLE_TOOLS 里** → 60 分钟后被 Time-based MC 清成 "[Old cleared]"。

### E.5 完整流程图

```
                Read 工具（豁免）
                      ↓
    ┌──────── tool_result 80KB ────────┐
    │                                  │
    │ fileStateCache 命中              │ fileStateCache 不命中
    │ （同源文件）                      │ （新文件，如持久化的 txt）
    │                                  │
    ↓                                  ↓
"Already read"                  80KB 完整
简短状态                          ↓
不占 token                       applyToolResultBudget
                                 检查 Read 豁免 → 跳过
                                      ↓
                                 模型看到 80KB ✅
                                      ↓
                                 fileStateCache 缓存这条
                                      ↓
                                 下次再读 → "Already read"
```

### E.6 关键设计决策表

| 问题 | 答案 | 原因 |
|------|------|------|
| 截断和替换的顺序？ | **先压缩，再给模型思考** | applyToolResultBudget 在 API call 之前 |
| 80KB 完整内容如何被看到？ | 模型用 Read 工具读 preview 里写的路径 | preview 透明地提供路径 |
| Read 工具结果会被再次压缩吗？ | **不会**（`maxResultSizeChars: Infinity`） | 防止"压缩→读→再压缩"死循环 |
| 用 Bash 读 txt 会被二次压缩吗？ | **会**（Bash 不豁免） | 但 60 分钟后被 Time-based MC 清成 "[Old cleared]" |
| 模型陷入 re-read 死循环？ | 不会 | fileStateCache 第二次起返回 "Already read" |

### E.7 三个机制合起来的效果

1. **先压缩后给模型思考** + 2. **Read 工具豁免** + 3. **fileStateCache 短路** = 既保护了 prompt cache，又保证模型不会陷入"永远看不到完整内容"的死循环。

这是整个上下文管理栈里**最微妙**的三个设计决策：去掉了任何一个都会出问题。
